# 接收哪些 issue

> 这一篇管：什么样的 issue 会被处理，什么样的不会，判断不过时怎么办。每条规则后面写依据。各项阈值（清晰度、人工时间、代码量、运行时长、安全类排除）2026-10-24 定为先按这些数值执行，实测后可能调整。第二节程序拦下的几项 2026-10-30 在测试仓库跑过；第三节的接收规则还没在真实仓库里实测。

## 一、为什么需要这些规则

RepoAegis 被打上标签后只处理一次，中途没有人可以回答它的问题。它读到的是打标签那一刻 issue 的内容，运行中还可以按需读本仓库的其他 issue，做完开一个草稿 PR，然后撤掉标签。所以一个 issue 能不能交给它，取决于一件事：**只凭正文，一个不能追问的工程师能不能把它做完，并且知道什么时候算做完。** 不满足这一点的 issue，agent 做出来的只会是一个靠猜的 PR，既浪费运行时间和模型费用，也浪费评审的人的时间。

规则分三层：

1. **触发条件**：开着的 issue、打标签的人有权限。由工作流条件和开工前检查判断，见 [触发与叫停](触发与叫停.md)。
2. **内容检查**：由程序按规则判断，不调用模型（第二节）。
3. **接收规则**：调用一次模型判断，不满足就不改代码、说明原因后结束（第三到五节）。

## 二、程序直接拦下的内容（2026-10-26 定）

下面几种，程序在开工前就拦下，不交给模型判断。具体怎么认、边界在哪，见 [agent 读到的内容](agent读到的内容.md)。

- **带图片的 issue 暂不处理。** 截图、设计图里的信息只有能看图的模型才读得懂。现在不引入看图能力：一是还没学这部分；二是图片和文字合在一起后模型的效果不一定好，需要专门评估。抽样统计中约 12% 的 issue 带图片，有界面的应用类仓库约 29%，通用库约 4%。**以后会重新考虑**：主体流程做完后，再评估成本和效果。
- **带其他附件的 issue 也不处理。** 视频、pdf、日志文件、压缩包、录音等，出现就终止、不开工。抽样里这类附件只占约 1.8%，以 zip 和 log 为主；官方的同类项目也都不处理。
- **打标签前最后由没有权限的人改过的不处理。** 留言请维护者看过后重新打标签。防止有人在维护者看过之后偷改正文、塞入指令。
- **已经有关联的 PR 或提交**：有就不开工，在 issue 里说明（学 SWE-agent 开 PR 前的检查）。这一项代码里还没有，放在哪一步待定。

引用其他 issue 不会让 issue 被拦下，引用多少层都行，agent 运行中按需去读（2026-11-01 定），见 [agent 读到的内容](agent读到的内容.md) 第五节。

## 三、接收规则

agent 动手改代码之前，按顺序检查下面五条，**任何一条不通过，就不改代码**，按第四节的方式回应。

### 规则 1：必须是在要求改代码

提问、讨论、求助、感谢、汇报情况，都不处理。

**依据：** 各家官方产品的定位都是"把一个开发任务交给 agent"。RepoAegis 只开 PR，对非开发类的 issue 没有可交付的结果。

### 规则 2：描述必须足够清楚——清晰度 ≤ 1 分

用下面这把四档的尺子给 issue 打分，只处理 0 分和 1 分的：

- 0 分：写清楚了，怎样才算成功解决一目了然。
- 1 分：有些空白要自己补，但有一个合理的理解，能看出成功的解法该是什么样。
- 2 分：含糊，可以有不同理解，看不出成功的解法该是什么样。
- 3 分：没有更多信息的话，几乎不可能明白要做什么。

1 分的 issue 可以做，但 agent 必须把自己补上的假设写进 PR 描述和 issue 汇报里。打分时要点出 issue 里具体提到的文件、函数或现象，作为打分的理由。

**依据：** 这把尺子来自 OpenAI 整理 SWE-bench Verified 时的人工标注准则。它给标注员的设定是"只看 issue 正文，不能要求对方澄清"，和 RepoAegis 的处境完全一样。SWE-bench 自己的做法也是剔除 2 分及以上的。参考数据：即使是热门 Python 项目里已经被修好的 issue，也有约 38% 被至少一位标注员判为 2 分以上，所以预计会有相当一部分 issue 过不了这一条。

### 规则 3：必须能验证

issue 里至少要有下面一项，让人和 agent 都能检查"到底改对了没有"：

- 复现步骤加实际现象（报错信息、错误输出）；
- 明确的期望行为；
- 可以写成测试或命令来检查的验收标准，比如"某个输入应该返回某个结果"。

**依据：** 这是各家官方建议里重合度最高的一条。Copilot 要求验收标准，Codex 要求写明"做到什么程度算完成"，Devin 要求清楚的成功标准，OpenHands 的判断流程里有一问"能不能验证结果"。

### 规则 4：规模不能超过阈值

下面两个阈值都是**开工前的估计**，超过任何一个就不处理：

- **人工时间：一个熟悉代码库的工程师估计 1 小时以内能完成。** 估计在 1 到 4 小时、或超过 4 小时的，不处理。
- **代码量：预计改动（新增加删除）不超过 100 行，不含新增的测试代码。** 这只是挑 issue 时的软限制，agent 交卷时不再按行数拦（2026-10-30 定）。

此外运行中还有**硬上限**：单次处理累计最长 60 分钟，token 总量也有上限，到了就停止，不开 PR，在 issue 里说明原因。细则见 [agent 怎么干活](agent怎么干活.md) 第一节。

**依据：**
- 各家的经验值都落在"人工一小时左右，最多三小时以内"：OpenAI 介绍 Codex 内部用法时说适合"你或同事大约一小时能做完"的任务；Devin 企业指南建议 90 分钟以内，入门页说三小时以内；Copilot 单次运行硬上限 59 分钟。RepoAegis 只处理一次、不能中途对话，所以取较保守的一端。
- SWE-bench 标注准则里的难度分四档：少于 15 分钟、15 分钟到 1 小时、1 到 4 小时、超过 4 小时。建议值相当于只接前两档。那批真实 issue 里，前两档占约 78%（417 + 906，共 1699 个）。
- 100 行来自 OpenHands 的判断流程，原文写的就是"少于 100 行代码"。SWE-bench 的"超过 4 小时"一档也以"改动超过 100 行"为特征。不含测试代码，是因为补测试本身是被鼓励的；这一点是我们自己的设计，没有官方依据。
- 60 分钟参考 Copilot 的 59 分钟上限。GitHub Actions 默认允许一个作业跑 360 分钟，所以必须在配置里改短。

**注意：** 这两个阈值靠模型自己估计，而 Devin 的官方文档承认"agent 容易高估自己"，调研中没有找到任何一家公开过 agent 自评准确率的数据。所以规定：**拿不准是否超过阈值时，按超过处理**。

### 规则 5：不属于排除的类型

下面几类即使写得很清楚、规模也很小，也不处理：

- **涉及安全、身份认证、权限、个人隐私的改动**：目前一律不做，以后再考虑放开"扫描工具报出的具体漏洞"；
- **大范围重构、架构调整**，没法拆成单独可验证、可合并的一小块的；
- **主观的设计或视觉调整**，比如"让界面更好看"；
- **依赖或框架的大版本升级**；
- **需要额外权限的改动**：任务本身就要改 CI 工作流（`.github/` 下的文件）、动密钥、改仓库设置或改别的仓库。这和正文里顺带夹一句越权要求不同：顺带的那句跳过、其余照做（见 [agent 读到的内容](agent读到的内容.md)）；而这类任务整个做不了，因为改 `.github/` 的补丁在发布前一律拦下，Actions 自带的 `GITHUB_TOKEN` 也没有改工作流文件的权限。

**依据：**
- 安全类：Copilot 的最佳实践建议涉及安全、个人身份信息、认证的任务由人自己做；OpenHands 把安全审计、高度敏感的代码列为不适合。实证研究也显示，agent 提的安全相关 PR 合并率约 61.5%，非安全的约 77.3%，评审时间中位数 3.92 小时对 0.11 小时。
- 重构和架构：Copilot 建议别交；Devin 和 OpenHands 都说必须拆成能单独验证和合并的小块。
- 主观任务：Copilot、Devin、OpenHands、Jules 四家举的反例几乎一样："让它更好看""把问题都修了""看看哪里坏了"。
- 大版本升级：OpenHands 把框架和大版本依赖升级列为需要拆分的复杂任务。

## 四、判断不通过时怎么做

1. **不改代码，不开 PR。**
2. 由外层程序按模板在 issue 里留一条评论，写明：没通过哪一条规则、具体缺什么信息、需要回答的问题，并告诉对方"补充正文后重新打一次 `agent-fix`"。模型只提供问题列表等字段，不原样贴模型的回复；垃圾类不引用原文。评论末尾注明"本条由 AI 生成"，用 issue 的语言写。
3. 撤掉 `agent-fix` 标签，本次处理结束。

**依据：** 和 RepoAegis 最像的是 OpenHands 的 issue 转 PR 工具。它的提示词写明 issue 太模糊时"什么都不改，说清楚缺什么"；留言由外层程序根据事实决定，不让 agent 自己发。多数官方 agent 没有"判断不做"这条路，结果是含糊的 issue 也会得到一个靠猜的 PR。GitHub 文档推荐过的一个"AI 评估打标签"工具把模型回复原样发成评论、把回复标题直接变成标签，issue 里藏的指令就能影响评论内容，这是反面例子。

**不设"跳过检查直接开工"的标签。** 被误拒时，改好正文、重新打标签即可，少一个可能被滥用的口子。

## 五、接收规则在哪一步判断

**在 agent 开工前单独检查一步。** 只调用一次模型，读清洗过的内容，按固定格式输出下面这些字段，由外层程序严格校验（字段不多不少、取值必须在规定选项里、前后要一致，学 OpenHands 分诊工具的做法）：

- `decision`：做 / 不做；
- `request_type`：改代码、提问、讨论、垃圾、不归本仓库；
- `failed_rules`：没通过的规则编号；
- `clarity_score` 和 `clarity_evidence`：清晰度分数，以及点出具体文件、函数或现象的打分理由；
- `verification`：用什么来验证改对了没有；
- `size_bucket` 和 `estimated_lines`：规模估计；
- `exclusion`：属于规则 5 的哪一类排除；
- `assumptions`：自己补上的假设（清晰度 1 分时必填）；
- `questions`：要对方回答的问题（没通过规则 2 或 3 时必填；正文依赖另一个 issue 却没给编号时，也列进这里）；
- `ignored_requests`：正文里不会照做的要求，只用来汇报，本身不构成拒绝理由。

**理由：** 被拒的 issue 只花一次模型调用的钱；这一步可以单独拿真实仓库的 issue 去测，和人的判断对照，看它准不准（没有任何一家公开过 agent 自我判断的准确率）；它写出"忽略了哪些内容"，人能看到客套话、无关内容确实被跳过了。agent 读了代码才发现做不了的情况，由 agent 在干活过程中结束，外层程序看到"没有改动"按事实留言来兜住。

**各种情况的归口：**

- 乱码、垃圾、辱骂、提问、讨论：规则 1。
- 正文为空、模板没填、内容自相矛盾：规则 2、规则 3。正文为空时不由程序直接拒，交给检查步骤，因为有的 issue 标题一句话就说清楚了。模板的下拉框和正文冲突时以正文为准（学 Claude Code 自己仓库的分诊）。
- 超长：规则 2、规则 4。非英文：不因语言拒绝。
- 只说问题出在默认分支以外的分支上（例如只在某个 release 分支）：不处理，说明只处理默认分支（见 [agent 怎么干活](agent怎么干活.md)"克隆"）。
- 检查步骤自己出错（模型报错、输出格式不合法）：在 issue 里说明"检查出错"并附运行链接，撤掉标签；重新打标签即重试。

## 六、给使用者：怎么写一个会被处理的 issue

一个容易通过的 issue 最好包含：

- 要解决什么问题，或者要做成什么样；
- bug 的话，复现步骤和实际现象，报错信息贴文字，不要只贴截图；
- 做到什么程度算完成，最好能写成"某个测试应该通过"或"某个命令应该输出什么"；
- 知道的话，写上涉及的文件或函数；
- 不能动的地方和要遵守的写法。

适合交给 agent 的典型例子：有报错或复现步骤的 bug、给已有代码补测试、改文档和注释、小范围的配置和样式修改、照着已有写法做的改动。不适合的：含糊或主观的需求、大范围重构、安全和认证相关的改动、关键信息只在截图里的、提问和讨论。

**给维护者：打标签之前看什么（2026-11-03 定）。** 打上 `agent-fix` 就等于替这个 issue 当时的内容担保，agent 会照着它干活。

- 先把正文从头到尾看一遍，包括折叠起来的部分。
- agent 能读本仓库里任意一篇 issue，正文提到的、被提到的 issue 里再提到的都能读。一篇 issue 能不能给它看，只看"最后写或改它的人有没有写权限"。所以，**修改外人写的 issue 时（哪怕只改一个错别字），也要先把全文看过**：你改过以后，这一版就算你写的，里面外人写的内容也会被当成可信的交给 agent。
- 正文引用了别的 issue 时，挑主要的几篇看一眼，尤其是外人写、后来被人改过的。

这条提醒代替了"被引用的 issue 要求每一次修改的人都有写权限"的更严规则：用户 2026-11-03 定，不改程序，由维护者甄别。

## 七、待定和待实测

- 各种情况下的留言具体怎么写，待讨论。
- 遇到带图片的 issue 具体怎么回应，尚未确定。
- GitHub 的子 issue（父 issue 下挂着的一串 issue）和"被某个 issue 阻塞"的依赖关系不在正文里，用接口能查到。要不要处理、怎么处理，没定。
- 在真实开源仓库里抓一批 issue，让检查步骤逐条判断，和人的判断对照，看规则和阈值是否合理、模型的估计准不准。
