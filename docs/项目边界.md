# 项目边界：RepoAegis 不做什么

> 这里列的是讨论中已经定下"不做"的事情，每条写明原因，以及以后会不会重新考虑。哪些情况不触发、哪些 issue 不接，见 [触发与叫停](触发与叫停.md) 和 [接收哪些 issue](接收哪些issue.md)；项目要做什么，见 [README](../README.md)。

RepoAegis 只做一件事：有权限的人给一个开着的 issue 打上专用标签 `agent-fix`（名字暂定），GitHub Actions 处理一次，agent 在隔离环境里改代码、开草稿 PR、在 issue 里汇报，最后撤掉标签。下面这些事情都在这条线之外。

## 一、开出 PR 以后不做的事

**不根据评审继续修改。** agent 开出草稿 PR、汇报、撤标签之后，这个 issue 的处理就结束了。人在 PR 上评论、提交评审（要求修改、只留意见、批准）、在代码行上留"建议修改"、@ 机器人，agent 都不响应，也不订阅这些通知。PR 怎么改、要不要合并，全部由人决定。人想让 agent 重来一次，可以再给 issue 打一次标签。**可能以后重新考虑**：按评审结论继续修改的方案已经讨论过（关闭即结束、要求修改就改、多轮上下文怎么带），目前搁置。

**不合并 PR，不直接改主分支。** agent 只在自己的新分支上提交，只开**草稿** PR。合并永远由有权限的人来做。

**处理被叫停时，不自动清理。** 已经推上去的分支或开出的草稿 PR 不会自动删除或关闭，由人处理。开 PR 前的复查已经把残留压到很小的时间窗口里。

## 二、运行控制上不提供的

**不靠 Actions 暂停。** GitHub Actions 只能取消一次运行，没有暂停功能。我们的"暂停"是自己做的：取消前把进度存档，之后有权限的人重新打标签、内容没变，就从存档接着做（见 [暂停存档与监控](暂停存档与监控.md)）。在 Actions 页面上直接点取消，不经过我们的程序，不保证留下存档。

## 三、不自己搭的基础设施

**不自己搭接收通知的服务。** 用 GitHub Actions：筛选事件、记录每次运行、保存日志，都由 GitHub 完成。所以也**不自建事件存档或数据库**，监控也不自建服务。

**不用 Kubernetes。** Actions 每次运行都开一台用完即毁的临时机器，本身就起到了隔离的作用。抽样的国内 agent 实习岗位描述里也基本没有要求 Kubernetes。

**不训练模型。** 直接使用现成的模型，而且只用一个（暂定 DeepSeek），不做微调或强化学习。精力放在 agent 本身：循环、工具、上下文、失败处理和安全。

## 四、不处理的仓库

**不面向大型仓库。** 目标是中小型仓库，准确地说，是"装依赖加跑测试几分钟内能完成"的仓库。大型单体仓库、测试要跑很久或要特殊环境（数据库、GPU、内部服务）的仓库不在范围内。这类仓库遇到时，如实在 issue 里说明跑不起来。

## 五、旧定位里有、现在不做的功能

项目在 2026-10-16 曾定位为"事件驱动的仓库维护平台"，后来放弃了。下面这些当时规划过的功能，现在都不做：

- 对新 issue 自动分类、查重、追问缺失信息、打标签；
- 主分支 CI 失败后自动判断和修复；
- 依赖更新的评估和升级；
- 对外部 PR 做预审；
- 定时提醒长期没人回应的 issue；
- 网页控制台。

这些功能需要监听更多种类的事件，也要处理更多的人机交互，和现在"只做一次性修复"的定位不符。

## 六、评测和数据上不做的事

**不和大团队的产品比总分。** 个人项目不宣称"超过 OpenHands 或某个商业产品"。不同产品的模型、预算、提示词都不一样，单次运行的差距又常在噪声范围内，这种比较站不住。要比，就和同一模型、同一预算下自己重跑的基线比，并多次重复。

**产品没做完不跑基线。** 基线是成品的成绩，什么时候算做完由项目作者决定。

**不用公司私有仓库当公开的测试数据。** 私有仓库只能做本地实验，从中得到的数字不作为结果展示；这个开源仓库里也不出现任何公司相关的名字和内容。
