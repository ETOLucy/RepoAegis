# 项目边界：RepoAegis 不做什么

> 记录日期 2026-10-24。这里列的是讨论中已经定下"不做"的事情，每条写明原因，以及以后会不会重新考虑。项目要做什么，见 [README](../README.md)。

RepoAegis 只做一件事：有权限的人给一个开着的 issue 打上专用标签 `agent-fix`（名字暂定），GitHub Actions 运行一次，agent 在隔离环境里改代码、开草稿 PR、在 issue 里汇报，最后撤掉标签。下面这些事情都在这条线之外。

## 一、哪些情况不触发

**新建 issue 本身不触发。** 新建一个 issue，不管有没有带别的标签，都不会启动 agent，只有打上 `agent-fix` 才算"交给 agent"。新建时直接选了 `agent-fix` 的，按 GitHub 官方文档会同时产生一次"打标签"事件，所以会被处理，这和规则一致。

**打别的标签、撤标签、编辑、评论都不触发。** 只有"打上 `agent-fix`"这一个动作是开始的信号。撤标签不会启动新的处理，它只用来取消正在进行的那一次（见 [中途撤标签与重复触发](中途撤标签与重复触发.md)）。

**已关闭的 issue 不处理。** 已经关掉的 issue 即使被打上标签也直接跳过，因为问题要么已解决，要么已决定不做。正在处理时 issue 被关闭，开 PR 前的复查会发现，不再开 PR。

**给 PR 打标签不处理。** 专用标签只针对 issue。给一个 PR 打上 `agent-fix` 不会让 agent 去改那个 PR。

**机器人自己的操作不触发自己。** 处理结束时撤标签用的是 GitHub Actions 自带的令牌，按 GitHub 规定这类操作不会再启动新的运行，从根上避免自己触发自己。

## 二、哪些内容不处理

**带图片的 issue 暂不处理。** 截图、设计图里的信息只有能看图的模型才读得懂。现在不引入看图能力（多模态），原因有两个：一是还没有学这部分；二是图片和文字合在一起后模型的效果不一定好，需要专门评估。抽样统计显示，约 12% 的 issue 带图片，有界面的应用类仓库约 29%，通用库约 4%。**以后会重新考虑**：主体流程做完后，再评估成本和效果，决定要不要加。遇到带图片的 issue 具体怎么回应，尚未确定。

**图片以外的附件一律跳过。** 视频、pdf、日志文件、压缩包、录音等都不读取。抽样里这类附件只占约 1.8%，以 zip 和 log 为主，没有音频；官方的同类项目也都不处理。

## 三、开出 PR 以后不做的事

**不根据评审继续修改。** agent 开出草稿 PR、汇报、撤标签之后，这个 issue 的处理就结束了。人在 PR 上评论、提交评审（要求修改、只留意见、批准）、在代码行上留"建议修改"、@ 机器人，agent 都不响应，也不订阅这些通知。PR 怎么改、要不要合并，全部由人决定。人想让 agent 重来一次，可以再给 issue 打一次标签。**可能以后重新考虑**：按评审结论继续修改的方案已经讨论过（关闭即结束、要求修改就改、多轮上下文怎么带），目前搁置。

**不合并 PR，不直接改主分支。** agent 只在自己的新分支上提交，只开**草稿** PR。合并永远由有权限的人来做。

**处理被取消时，不在 issue 里留言，也不自动清理。** 标签在处理中途被撤掉，正在运行的处理会被取消，只在运行日志里记一行，不在 issue 里发评论；已经推上去的分支或开出的草稿 PR 也不会自动删除或关闭，由人处理。留言本身是对外操作，会引入新的时间差问题；而开 PR 前的复查已经把残留压到很小的时间窗口里。

## 四、运行控制上不提供的

**不提供"暂停后继续"。** GitHub Actions 只能取消一次运行，没有暂停功能。要让 agent 停下，就撤掉标签，或者在 Actions 页面上点取消。

## 五、不自己搭的基础设施

**不自己搭接收通知的服务（webhook 服务）。** 曾经在测试仓库里用转发工具把通知送到本机，验证过通知的内容和字段。最终决定改用 GitHub Actions：筛选事件、记录每次运行、保存日志，都由 GitHub 完成。所以也**不自建事件存档或数据库**。

**不用 Kubernetes。** Actions 每次运行都开一台用完即毁的临时机器，本身就起到了隔离的作用。抽样的国内 agent 实习岗位描述里也基本没有要求 Kubernetes。

**不训练模型。** 直接使用现成的模型（DeepSeek，通过它兼容 OpenAI 的接口调用），不做微调或强化学习。精力放在 agent 本身：循环、工具、上下文、失败处理和安全。

## 六、不处理的仓库

**不面向大型仓库。** 目标是中小型仓库，准确地说，是"装依赖加跑测试几分钟内能完成"的仓库。大型单体仓库、测试要跑很久或要特殊环境（数据库、GPU、内部服务）的仓库不在范围内。这类仓库遇到时，如实在 issue 里说明跑不起来。

## 七、旧定位里有、现在不做的功能

项目在 2026-10-16 曾定位为"事件驱动的仓库维护平台"，后来放弃了。下面这些当时规划过的功能，现在都不做：

- 对新 issue 自动分类、查重、追问缺失信息、打标签；
- 主分支 CI 失败后自动判断和修复；
- 依赖更新的评估和升级；
- 对外部 PR 做预审；
- 定时提醒长期没人回应的 issue；
- 网页控制台。

这些功能需要监听更多种类的事件，也要处理更多的人机交互，和现在"只做一次性修复"的定位不符。

## 八、评测和数据上不做的事

**不和大团队的产品比总分。** 个人项目不宣称"超过 OpenHands 或某个商业产品"。不同产品的模型、预算、提示词都不一样，单次运行的差距又常在噪声范围内，这种比较站不住。要比，就和同一模型、同一预算下自己重跑的基线比，并多次重复。

**产品没做完不跑基线。** 基线是成品的成绩，什么时候算做完由项目作者决定。

**不用公司私有仓库当公开的测试数据。** 私有仓库只能做本地实验，从中得到的数字不作为结果展示；这个开源仓库里也不出现任何公司相关的名字和内容。

## 九、给使用者：什么样的 issue 适合打上 `agent-fix`

> 这一节是摘要。完整的需求（触发条件、五条接收规则及阈值、判断不通过时怎么做、对 issue 内容的处理规则）见 [需求：哪些 issue 交给 agent 处理](什么样的issue适合交给agent.md)。

简单说，agent 只接满足下面条件的 issue（阈值 2026-10-24 定下，先按这些数值执行，实测后可能调整）：

- 在要求改代码，不是提问或讨论；
- 描述清楚：按 SWE-bench 标注用的四档尺子，清晰度 0 分或 1 分；
- 能验证：有复现步骤和实际现象、明确的期望行为，或可以写成测试的验收标准；
- 规模小：熟悉代码库的工程师估计 1 小时以内，预计改动不超过 100 行（不含新增测试）；单次处理最长 60 分钟；
- 不属于安全、认证、权限、隐私相关，不是大范围重构、主观设计或大版本升级。

不满足时，agent 不改代码，在 issue 里说明没通过哪一条、缺什么信息，请补充后重新打标签。
