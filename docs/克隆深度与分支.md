# 克隆带不带历史、看不看其他分支

> 状态（2026-10-24）：全部已定。浅克隆、只用默认分支；现在不做"查提交"的工具，也不给 agent 看其他分支的工具。本文的事实来自 2026-10-24 调研子 agent 读过的原文和它在 WSL 里的实测，本文没有逐条再复核。

## 问题是怎么来的

agent 要改一个仓库，先得把仓库克隆到运行机上。克隆有两种：**完整克隆**把所有历史提交都下载下来；**浅克隆**（`git clone --depth 1`，GitHub Actions 的 `actions/checkout` 默认就是这样）只下载最新的一个提交。

完整克隆的好处是 agent 能自己跑 `git log`（看提交记录）和 `git blame`（看每一行是哪次提交改的），弄清"这段代码为什么这么写""这个 bug 是哪次改动引入的"。代价是大仓库克隆慢。

用户定的规则是：**只有找到"带历史能让 agent 做得更好"的数据，才用完整克隆；找不到，就用浅克隆。**

## 查到的数据

**没有找到直接比较"完整克隆让 agent 自己查历史"和"浅克隆"解决率的数据。** 找到的三项正面数据，测的都是另一件事：框架专门做了一个查提交的工具，或者框架先查好历史再塞给模型。

- Code Researcher（微软，arXiv 2506.11060，第 5.4 节、附录 A 表 3）给 agent 一个按正则搜提交的工具，去掉它以后，Linux 内核崩溃的解决率从 48% 降到 38%。但这个对比只在完整版本来就解出来的 96 题上做，题目是提交说明非常规范的 Linux 内核，模型是 GPT-4o。
- RepoMem（arXiv 2510.01003）用框架整理好的提交检索工具，在 SWE-bench Verified 上把解决率从 37.0% 提到 40.4%（GPT-4o），历史少的仓库反而下降。
- HAFixAgent（arXiv 2511.01047，表 1a）由框架先对出错行跑 blame、把结果放进提示词，出错行是直接告诉 agent 的。在 DeepSeek-V3.2-Exp 上提升 4.4% 和 1.1%，论文自己说不显著。

反过来，agent 很少主动去查历史：SWE-bench 的环境一直保留完整的过去历史，维护者在约 10000 条运行记录里只找到 5 条用了 `git log`（SWE-bench issue #465）。

官方产品的选择也偏浅：Copilot 会强制把克隆深度改成 2（官方文档只说会覆盖，数字来自社区讨论 #163397 里用户贴的运行日志）；claude-code-action 修 issue 的示例用 1；OpenHands 手动版的 issue 转 PR 用 1，注释写的是 agent 要的是代码文件，不是历史。只有任务本身就是读历史时（总结 git log、修 CI、给 issue 分类），这些示例才拉全量。

## 结论：浅克隆

按规则，用浅克隆，深度 1。

浅克隆有一个坑，要写进 agent 的提示词：浅克隆下 `git blame` **不报错**，而是把所有旧行都算到最新那个提交头上，只在前面标一个 `^`。实测（pallets/markupsafe，一个 389 行的文件）`--depth 1` 时 389 行全部显示为最新提交的作者和日期。所以提示词里要说明"仓库没有历史，不要用 `git log` / `git blame` 判断代码的来历"。

不用 `--filter=blob:none`（先只下载提交记录、文件内容用到时再下）：实测克隆时间只比完整克隆省一点，跑 blame 时却要一个个联网下载旧版本文件，同一条 blame 从 0.013 秒变成 1 分 47 秒。

## 已定：两个工具现在都不做

**"查提交"的工具：现在不做，留作以后的选项。** 等在真实仓库上测试时，如果看到 agent 确实因为缺历史而做错，再加。 上面三项数据说明的是"专门的查提交工具"在某些条件下有用，尤其是提交说明规范、历史丰富的仓库。如果要做，形式是：仍然浅克隆，agent 调用这个工具时，由外层程序替它补历史（`git fetch --deepen=N`，实测几秒钟）再搜索，结果截断后返回。这样 agent 不需要拿 GitHub 凭据。实测中要注意：`--shallow-since` 之后再加深会失败（原因待验证），用 `--deepen` 更稳。没有官方 agent 这样做。

**看其他分支的工具：不做。** issue 明确说问题只出在默认分支以外的分支上时，开工前的检查判为不处理，在 issue 里说明只处理默认分支（见 [什么样的 issue 适合交给 agent](什么样的issue适合交给agent.md) 第五节）。依据是：所有官方项目都只在默认分支上开工，PR 也合回默认分支；`issues` 事件触发的运行本身就指向默认分支。没有官方 agent 提供"看其他分支"的工具或提示词；需要往 release 分支回移的，是维护者自己写的技能文件，由人在本地交互着用。浅克隆默认只拿一个分支，要看别的分支得显式 `git fetch origin <分支>`。

## 以后做评测时

拿已经修好的旧 issue 做评测时，仓库里会留着"未来"的提交，agent 可能直接看到答案（SWE-bench issue #465）。浅克隆到修复前的那个提交天然没有这个问题；如果以后改成带历史，必须照 SWE-bench 的 `git_clone_timesafe()`（`swebench/image_builder/docker_utils.py`）删掉未来的提交和标签。
