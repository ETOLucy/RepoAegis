# 调研报告：agent 在哪里跑——部署方式与沙箱

> 调研于 2026-10-24（北京时间），分几次做：凌晨查官方项目的沙箱做法，以及 Docker 和 K8s 的区别、"企业级"指什么；晚上改用 GitHub Actions 之后，查自托管运行机和 Actions 计费。材料：当时主对话的回答、一个调研子 agent 交回的报告及其完整过程记录、另一个子 agent 对岗位描述的计数，均取自备份目录 `RepoAegis-backup-2026-10-25` 里的会话记录。2026-10-25 整理，未重新核对。网页内容是抓取工具转述给模型的，不是逐字原文；子 agent 标"只读到摘要"的，这里照样标出。

## 一、为什么查

最早的方案是自己写一个一直运行的服务，接收 GitHub 发来的通知再处理。这样一来，agent 改代码时要关在一个**沙箱**里（沙箱：一个和本机隔开的运行环境，agent 在里面执行命令、改文件，弄坏了也不影响外面）。沙箱用什么搭，是绕不过去的问题。用户当时的问题是："这个沙箱我们是怎么处理？就怎么做一个沙箱？用什么基础设施？"

接着用户追问了一层：企业常用 K8s，自己的电脑上没有这套环境，会不会因此做不出"企业级"的项目。用户自己的判断是"我想基础设施肯定不是最大的问题，最大的问题应该是一个代码负责度，或者说项目复杂度，或者说那个考虑的深度"（原话为语音输入，"负责度"应为"复杂度"），但不确定 Docker 和 K8s 除了能装多少东西之外还有什么区别，会不会让项目本身的复杂度不一样。这里先解释两个词：**Docker** 是把一个程序连同它需要的环境打成一个包（叫镜像），在一台机器上隔离着运行（运行起来的那个叫容器）；**K8s**（Kubernetes）是管一群机器的系统，决定每个容器放到哪台机器上跑、坏了谁来重新拉起。

后来触发方式改成 GitHub Actions（GitHub 自带的自动化功能：仓库里放一个配置文件，写明"什么事件发生时做哪些步骤"，事件一来，GitHub 就临时开一台虚拟机按步骤执行，执行完销毁，这台临时机器叫**运行机**）。用户问："难道不是只用它来通知一下吗？难道我们的 agent 也跑在 actions 里吗？"这就引出了最后一个问题：agent 到底跑在 GitHub 的机器上，还是跑在自己的机器上。

### 隔离强弱

几篇对比文章的共识是：Docker 容器和宿主机共用一个内核，最容易搭、启动最快，隔离最弱；gVisor 在用户态拦截系统调用，居中，有兼容性限制；Firecracker 微虚拟机每个任务一个独立内核，最强，但需要 KVM（硬件虚拟化支持）。【待验证】这些都来自厂商或厂商相关博客的搜索摘要，启动时间等数字各篇说法不一。文章也一致提醒：隔离技术只是一层，出网控制、密钥、权限要另外管。

### Docker 和 K8s 的区别

Docker 回答"怎么把一个程序和它的环境打成包，在一台机器上隔离着跑"；K8s 回答"有一群机器、很多包，谁来决定放哪台、坏了谁拉起、怎么升级"。【一手】K8s 官方概述页列出的能力是服务发现与负载均衡、存储编排、自动发布与回滚、按资源需求把容器放到合适的机器、自愈、密钥与配置管理、水平扩缩容。

放进"用沙箱跑 agent"的场景逐条看：同时来 20 个 issue 要决定每个沙箱放哪台机器，这是调度，单机 Docker 没有这个问题，满了就排队；一次性任务在 K8s 里叫 Job，失败会自动重试，【一手，只读到摘要】默认最多重试 6 次，间隔 10、20、40 秒指数增长，上限 10 分钟；限制单个沙箱的内存和 CPU，Docker 自己就有 `--memory`、`--cpus`（【一手】Docker 资源限制页），K8s 多出的是整个命名空间的总量上限（【待验证】ResourceQuota 一手页没读）；禁止沙箱访问内网，【一手】K8s 网络策略页写明要网络插件支持才生效，否则"创建了也无效"；滚动更新和扩缩容是给长期运行的服务用的，沙箱用完就销毁，几乎用不上。

更关键的一条是有些问题用了 K8s 也躲不掉。【一手，只读到摘要】K8s 的 Job 页说，即使把并行度和完成数都设成 1、失败不重启，同一个程序"有时仍会被启动两次"，应用要自己处理上一次遗留的临时文件、锁和不完整输出。【一手】Twelve-Factor 第 9 条要求进程经得住突然死亡、任务可重入。【一手，只读到摘要】SRE 书《Handling Overload》说重试要有预算，层层重试会组合爆炸。反过来，K8s 才会带来的问题集中在"沙箱后端"那一层：调度失败、镜像拉取、命名空间与权限、网络策略要插件、RuntimeClass 不存在时 Pod 直接失败（【一手】RuntimeClass 页）、取文件和执行命令要走接口。【推断】所以选 Docker 还是 K8s，改变的是沙箱后端那一层的实现和运维，去重、重试、失败恢复这些设计的复杂度基本不随它变；"完全不变"没有找到直接论述。

### GitHub 托管运行机和自托管运行机

**自托管运行机**是 GitHub 提供的另一种用法：在自己的电脑上装一个小程序并登记到仓库，触发、筛选、并发控制仍由 GitHub 管，轮到执行时，任务交给这个小程序在自己电脑上跑。

【一手】计费页原文："GitHub Actions usage is free for self-hosted runners and for public repositories that use standard GitHub-hosted runners."；私有仓库免费账号每月含 2000 分钟，Pro 账号 3000 分钟。【一手】自托管运行机参考页："Self-hosted runners connect to GitHub to receive job assignments"，并要求"The host machine must be able to make outbound HTTPS connections over port 443"，也就是只要能向外连 443 端口，不需要公网地址；页面没提长轮询，也没提入站端口。概念页说自托管运行机"Are free to use with GitHub Actions, but you are responsible for the cost of maintaining your runner machines"。参考页唯一的安全建议是用一次性运行机，"helps mitigate the risk of a compromised runner receiving new jobs"；关于公开仓库和 fork 的安全提醒，这两页都没写。

【推断】如果每处理一个 issue 要 10 到 30 分钟，2000 分钟一个月约能处理七十到两百个；这个"10 到 30 分钟"是假设，没有实测。按作业向上取整到整分钟、失败也计费等细节见 [Actions 平台事实](Actions平台事实_产物缓存重跑定时.md) 第 7 节。

### "企业级"指什么

没有一份官方的"企业级"清单。能找到的权威材料是：【一手】AWS Well-Architected 的六大支柱（运维卓越、安全、可靠性、性能效率、成本优化、可持续性），可靠性一项下面有故障隔离、容忍组件故障、测试可靠性、灾难恢复等；【一手】Twelve-Factor 十二条；【一手】Google SRE 书 34 章（服务目标、监控、处理过载、级联故障、数据完整性、事故复盘等）；CNCF 的云原生定义只读到搜索摘要，没找到它的"生产就绪清单"【待验证】。这几份的共同点是关心出了问题怎么办，而不是容量多大。

子 agent 按这些材料把条目分了两类（【推断】这是它的归类，不是出处原文）。主要靠应用代码和设计、个人电脑上能真实演示的：去重和可重入、重试预算与超时、任务状态、故障注入（杀掉进程看任务能否恢复）、日志与追踪、服务目标的定义与度量、沙箱接口抽象、权限与审计。和基础设施强相关、个人电脑上只能模拟或做不到的：多节点、多可用区的真实故障隔离（kind、k3d 的"多节点"其实是同一台机器上的几个容器）、真实多区域的灾难恢复、真实负载下的扩缩容、长期运行的达标数据；微虚拟机级隔离需要 KVM，在 WSL2 上能不能跑没查到资料【待验证】。

## 四、各项目借鉴什么、不借鉴什么及理由

**Copilot、Claude Code 的 GitHub 集成、OpenHands 解决器。** 借鉴它们共同的做法：agent 直接跑在 GitHub 托管运行机上，每次一台全新的、用完即毁的虚拟机，本身就是一个沙箱，不用自己装 Docker、搭沙箱，也不用让自己的电脑一直开着。我们的触发方式本来就是 Actions，这样最顺。不借鉴 Copilot 的防火墙，它只给 Copilot 自己用；托管运行机上怎么限制出网、怎么藏密钥，见 [Actions 里运行 agent 的安全做法](Actions里运行agent的安全做法.md)。

**Codex 云端。** 借鉴"装依赖时联网、agent 干活时断网、密钥从 agent 的环境里拿走"的思路，具体做法已在安全设计里定。不借鉴容器状态缓存 12 小时，我们每个 issue 只处理一次，没有可复用的状态。

**mini-swe-agent。** 借鉴"每条命令单独执行"，它让沙箱容易换、状态不会乱，工具清单里的 `bash` 工具已经照这个做。不借鉴它对 Docker 的依赖：运行机本身已经是隔离环境，现在不需要再套一层容器。

**OpenHands 主产品。** 不借鉴运行时镜像加"动作执行服务"、主程序通过 HTTP 把命令发进容器的结构。它是为常驻服务、多会话设计的，要先有 Docker，还要维护镜像，我们一次性跑完就销毁，用不着。

**SWE-ReX。** 借鉴"agent 代码不随运行位置改变"这个原则：以后如果换到自托管运行机，工作流里只改"在哪台机器上跑"那一行（`runs-on`），agent 代码不动。不借鉴它的多后端抽象层本身，我们只有一个运行位置，多写一层接口没有用处。

**K8s 和 kubernetes-sigs/agent-sandbox。** 不借鉴。agent-sandbox 面向常驻、可暂停恢复的 agent，我们每个 issue 跑一次就结束；本地跑 K8s 要先装 Docker，还要多处理一整层只有 K8s 才有的问题，而去重、重试、失败恢复这些设计问题并不会因此消失。岗位描述的计数也显示，K8s 的要求集中在基础设施团队。借鉴的是 K8s Job 文档里那句"同一程序有时会被启动两次"所代表的思路：程序要经得住重复执行和中途被杀，这已经落实为开 PR 前复查、交付步骤每一步先看再做（见 [触发与叫停](../触发与叫停.md)）。

**E2B、Modal、Daytona 等托管沙箱服务。** 不借鉴。要付费，还要把仓库代码交给第三方；托管运行机已经免费提供了一次性隔离环境。

**"Actions 只负责通知，agent 跑在自己的服务器上"。** 不采用。GitHub 的机器要能访问到这台服务器，就需要公网地址，又回到了 webhook 方案"GitHub 够不着本机"的老问题，绕 Actions 一圈没有好处。

**自托管运行机。** 现在不用，留作以后的升级：时长不够用，或者想完全掌控沙箱时再搬。好处是不占 2000 分钟、不需要公网地址；代价是电脑要一直开着，沙箱要自己搭（比如在 WSL 里装 Docker），agent 在自己机器上执行命令，安全要自己负责。

## 五、据此的决定

2026-10-24 晚上（北京时间），用户定下：agent 全部在 GitHub 托管运行机上跑，Actions 做完所有事；自托管运行机只是以后可能的升级。记录见项目记忆 `project-scope-one-shot.md`（"Decided 2026-10-24 (latest)"）。用户拍板那句原话【待验证】：现存记录里只找到引出这个问题的原话（见第一节），拍板的那句可能在已损坏的会话记录里。此前留给用户的"沙箱后端做 Docker 单后端，还是 Docker 加本地 K8s 双后端"这个问题，因为这个决定不再需要回答。

## 六、尚未查清

1. 托管运行机上 agent 的出网限制和密钥保管能做到什么程度，转到 [Actions 里运行 agent 的安全做法](Actions里运行agent的安全做法.md) 的待验证清单；GitHub 是否建议自托管运行机只用于私有仓库，当时没有重新核实。
