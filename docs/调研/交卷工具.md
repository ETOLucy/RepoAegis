# 调研报告：submit（交卷工具）的细节

> 调研日期：2026-10-27。源码和文档都是本次打开的原文，位置写在每条后面。标"推断"的是从源码推出来的，原文没有直说。

## 一、为什么查

2026-10-25 定了 `submit`：交一份固定格式的汇报，调用两次才算交上，补丁由程序用 `git diff` 生成（见 [agent工具清单](agent工具清单.md) 第八节）。2026-10-26 定了评论由程序按模板生成，agent 只交固定字段的 JSON（README"要做什么"）。2026-10-27 定了没有停止工具。现在要写 submit，需要定：两次调用各做什么、补丁包含什么、汇报有哪些字段、没改动能不能交、交完之后怎样。

已定、和本工具相关的其他规则：清晰度 1 分的 issue，agent 要把自己补上的假设写进 PR 描述和 issue 汇报（[接收哪些 issue](../接收哪些issue.md) 规则 2）；issue 里任务以外的要求，agent 跳过并在汇报里说明（[agent 读到的内容](../agent读到的内容.md) 第七节）；agent 读了代码才发现做不了的，"由 agent 在干活过程中结束、外层程序看到没有改动按事实留言"（[接收哪些 issue](../接收哪些issue.md) 第五节）；补丁和汇报在发布前由不拿密钥的产出检查作业检查，汇报文字清洗后再填进模板（[安全设计](../安全设计.md)"发布前检查产出"）。

## 三、各家做法

**SWE-agent（默认配置）。** 第一次调用 `submit`：程序执行 `git add -A && git diff --cached` 生成补丁，但不交，而是把补丁连同一份复查清单发给模型；清单四条：改代码后重跑复现脚本、删掉复现脚本、把改过的测试文件还原（SWE-bench 用隐藏测试评分，所以不许动测试）、再调用一次 submit 确认。第二次调用才把补丁交出去。它只数调用次数：两次之间又改了文件，第二次照样直接交（`SUBMIT_STAGE` 计数，推断）。`submit` 不带任何参数，没有文字汇报。

**mini-swe-agent。** 通用配置里，模型执行 `echo COMPLETE_TASK_AND_SUBMIT_FINAL_OUTPUT` 就结束，不能和别的命令合在一起。SWE-bench 配置里，模型先自己用 `git diff -- 文件1 文件2 > patch.txt` 只挑修复用的文件生成补丁，检查无误后再用另一条命令提交；说明里列出不该进补丁的东西：测试和复现文件、自己写的辅助脚本、构建和配置文件、二进制文件。

**OpenHands。** `finish` 只有一个 `message` 字段（"发给用户的最后一段话"）。工具说明写明两种情况都用它：任务做完了，或者因为技术限制、信息不足做不下去；话里要写做了什么、结果如何、做不了的原因、要问的问题。

**gh-aw。** agent 作业只读，写操作由另一个作业按 agent 交的结构化结果去做，叫"安全输出"。开 PR 的工具 `create_pull_request` 要 agent 给 `title`（标题）和 `body`（描述，最长 65536 字符），工具说明要求"写的是真要开的 PR，不许用占位内容试探"；补丁由程序从 agent 的提交生成。配置项里：默认开草稿 PR；没有改动时默认"警告"（还可设为报错或忽略）；补丁默认最大 4096 KB、最多 100 个文件；可以限定允许改的文件、剔除的文件；依赖清单、CI 配置、agent 指令文件算受保护文件，默认开 PR 但要求人工审批；默认在 PR 描述里加 `Fixes #N`，在末尾加固定的"由某某工作流生成"。另有两个结束工具：`noop`（没什么要改的，写一句说明，保证人能看到结果）和 `report_incomplete`（因为工具或环境故障做不了，框架按失败处理）。

**Codex CLI。** `codex exec --output-schema 文件` 让模型的最后一条回复符合给定的 JSON 格式。也就是"最终结果是固定格式的 JSON"，但它是约束最后一条回复，不是一个工具。

## 四、借鉴什么，不借鉴什么

- **借鉴 SWE-agent 的两次调用和复查清单，但清单换成我们的。** 不照搬"还原测试文件"：那是 SWE-bench 隐藏测试的需要，真实仓库里 agent 补的测试是好事。也不照搬"只数次数"：两次之间改了文件，就当作重新开始复查（推断：否则复查后再改的内容没人看过）。
- **借鉴 gh-aw 的"agent 写标题和描述、程序开 PR、程序加固定内容"。** `Closes #N`、AI 生成的说明、按哪个时间的版本处理等固定内容由程序加，不交给 agent。不照搬它那一大堆配置项，我们的规则已经写在产出检查里。
- **借鉴 OpenHands"做不了也用同一个结束工具说明原因"。** 这和我们文档里"agent 发现做不了就结束，程序看到没有改动按事实留言"一致；而且我们没有停止工具，这是唯一的出口。
- **不借鉴 mini 的"agent 自己挑文件生成补丁"。** 补丁由程序把所有改动一起生成，agent 只能改自己的工作区，不能决定交哪些（文档已定）；临时文件靠复查清单提醒删除，并在提示词里给一个仓库外的临时目录。
- **不借鉴 Codex 的"约束最后一条回复"。** 我们已经定了用工具交卷，而且 DeepSeek 的思考模式不支持强制调用工具（[agent工具清单](agent工具清单.md) 第六节），没法保证最后一条回复一定是 JSON。

## 五、建议（2026-10-30 已确认，答复见下）

2026-10-30 用户的答复：第 1 条去掉"改动超过 100 行"这项检查，100 行只是人挑 issue 时的软限制，submit 不管；第 5 条一度改为没有改动也开 PR，讨论了"GitHub 不让开没有提交的 PR、要空提交（待验证）"和"空 PR 被合并会用 `Closes #N` 误关 issue"两个问题后，用户决定维持原建议：没有改动只在 issue 里留言，不开 PR。其余几条同日确认按建议做，代码见 `src/repoaegis/tools/submit.py`。

写代码时补定（2026-10-30）：补丁和开工时的提交比，所以 agent 自己用 git 提交过的改动也算在内；生成补丁用一份临时暂存区，不动 agent 自己的暂存区（照 SWE-agent 直接 `git add -A` 的话，agent 之后跑 `git diff` 会看不到改动）；汇报字段不合格时报错，但不算一次调用，已经复查过的补丁改好汇报再交就行；复查时发给模型的补丁超过 16000 字符就截断，交上去的补丁是完整的。"碰了哪些文件算违规、什么样的字符串像密钥"这套规则属于产出检查，submit 只调用它、把提醒转给模型；规则本身等写产出检查时再定（gh-aw 的受保护文件名单里有 `README.md`，照搬会挡住改文档的 issue，要用户拍板）。

1. 第一次调用：程序把仓库里的所有改动（含新文件，遵守 `.gitignore`）生成补丁，连同复查清单发回模型，不结束。顺带按产出检查的规则先查一遍（碰了 `.github/`、依赖清单、agent 指令文件，补丁里有像密钥的字符串），有问题就一并提醒，让它趁早改。
2. 第二次调用：补丁和第一次时完全一样，才算交卷；不一样就当作新的第一次，重新发补丁和清单。
3. 复查清单：改完代码后测试重跑过没有；临时脚本、调试输出删了没有；有没有和 issue 无关的改动（顺手格式化、改别的文件）；汇报里的假设和跳过的要求写全了没有。
4. 汇报五个字段，每次调用都要带，以第二次的为准：`title`（PR 标题，100 字符以内）、`summary`（改了什么、为什么；没改动时写为什么没改）、`testing`（怎么验证的，跑了什么、结果如何；没验证就写原因）、`assumptions`（自己补上的假设）、`skipped_requests`（issue 里没照做的要求和原因）。都是字符串，后两个可以为空，除标题外每个 3000 字符以内；用 issue 的语言写。`Closes #N`、AI 生成说明、按哪个时间的版本处理等固定内容由程序加。
5. 没有改动也能交卷，同样走两次确认；`summary` 写明为什么没改，程序按"没有改动"的模板在 issue 里留言，不开 PR（2026-10-30 确认）。
6. 交卷后，submit 把补丁和汇报写进仓库外的输出目录，返回结果里标明"已交卷"；主循环看到就结束，之后的工具调用一概不执行。
7. 字段不合规（缺字段、类型不对、超长）就报错交回模型改；产出检查作业不信 agent 那台机器，会再查一遍。

4. **两次调用这套做法要评测（2026-10-30 用户要求标注）。** 担心的情况：agent 每次复查后都再改一点，补丁永远对不上，一直交不了卷。submit 自己不设"复查几次"的上限，这种情况现在只能靠主循环的时间和 token 上限兜住（10-31 定不设步数上限）；撞上限时怎么办（按失败处理，还是把已有改动交上去）还没定。评测时要看：每次运行复查了几次（每次复查返回的 `details["restarted"]` 可以在 Langfuse 里数）、有多少次运行是撞上限才结束的、复查后改的是真问题还是来回折腾。也要和"只调用一次就交卷"对照，看复查到底有没有用。
