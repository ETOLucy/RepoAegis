## 为什么查

作者想要一个"简易的、类似 Langfuse 的监控"，要能看到两类东西：

- 每次运行的**过程**：每次调模型、每次调工具、花了多少 token 和钱、各用了多久。
- 每次运行的**结局**：完成、暂停、超时、出错、交付失败。出事时还要能提醒到人。

约束：GitHub Actions 自带的临时机器（用完即毁）、一次最多 60 分钟、模型用 DeepSeek（走它兼容 OpenAI 的接口）、自己写 agent 循环、不自建服务器、不自建数据库、没有 Docker。

**OpenTelemetry（简称 OTel）** 是一套开源的、各厂商通用的"记录程序运行轨迹"的标准和工具库。它把一次操作记成一棵"span 树"：**span** 就是"一段有开始和结束时间的工作"，比如一次调模型、一次跑命令；span 可以嵌套。很多监控产品（Langfuse、Phoenix、Weave 等）都能直接接收 OTel 格式的数据。

## 一、Langfuse

### 1.1 它记录哪些东西

- **trace（一条轨迹）**：一次请求或一次操作里所有步骤的总称，所有步骤共用一个 `trace_id`。对 RepoAegis 来说，最自然的对应是"一次运行 = 一条 trace"。trace 上的属性会被复制到它下面每个步骤上。【原文：https://langfuse.com/docs/observability/data-model ，"Trace" 一节】
- **observation（观测，即步骤）**：trace 里的单个步骤，可以嵌套。类型共 10 种：`span`（通用的、有时长的一段工作）、`generation`（一次调模型，带提示词、token 用量和费用）、`event`（没有时长的一个瞬间事件）、`agent`、`tool`、`chain`、`retriever`、`evaluator`、`embedding`、`guardrail`。Python SDK 用 `as_type="tool"` 之类的参数指定，需要 SDK ≥ 3.3.1。【原文：https://langfuse.com/docs/observability/features/observation-types】
- **session（会话）**：把多条 trace 归成一组，页面上可以"回放"整组。限制：US-ASCII 字符串、少于 200 字符，超长会被丢弃。【原文：https://langfuse.com/docs/observability/features/sessions】
- **tags（标签）**：给 trace 打的字符串标签，用来筛选；每个最多 200 字符，超长被丢弃；创建后不能在页面上改。页面支持 `tags:(billing AND urgent)` 这种筛选。【原文：https://langfuse.com/docs/observability/features/tags】
- **metadata（元数据）**：任意键值对。用 SDK 的 `propagate_attributes()` 往下传时：键必须是 US-ASCII；值会被 JSON 编码，编码后必须 ≤200 字符。【原文：`langfuse-python/langfuse/_client/propagation.py` `propagate_attributes` 的文档字符串，约第 120–172 行】
- **score（评分）**：对 trace 或步骤打的分（数值、分类、布尔），按条计费。【原文：https://langfuse.com/pricing ，"billable unit" 定义】data-model 页本身没讲 score。
- 其他可挂在 trace 上的：user_id、environment（如 production/staging）、release/version。【原文：data-model 页】

**能不能把 issue 编号、运行编号挂上去**：能。`propagate_attributes(session_id=..., user_id=..., tags=[...], metadata={...}, trace_name=...)` 都接受字符串。【原文：propagation.py 第 120–172 行】一种可行的挂法【推断】：

- trace = 一次运行，`trace_name` 写 `agent-fix`；
- `session_id` 写 `仓库名#issue编号`，这样同一个 issue 的历次运行（比如撤标签后重打）归到一组；
- `metadata` 放 `run_id`（`GITHUB_RUN_ID`）、`run_attempt`、运行页链接；
- `tags` 放结局（`完成`/`超时`/`出错`…）。注意标签不能事后在页面上改，所以结局标签要在运行结束前由程序打上。

### 1.2 能不能在页面上看单次运行的完整过程

能。trace 详情页显示整棵步骤树；如果 trace 里有 `agent`、`tool` 这类类型的步骤（不是 span/event/generation），还会自动画出"agent 图"。【原文：https://langfuse.com/docs/observability/features/agent-graphs】session 页能回放同一组的多条 trace。【原文：sessions 页】详情页里的树形视图、时间线视图具体长什么样，本次没找到专门的文档页【待验证】。

### 1.3 云服务免费档（Hobby）

读取日期 2026-10-27，来源都是 https://langfuse.com/pricing 【原文】：

- **unit（计费单位）** 的定义："发到平台的任何一条追踪数据"，包括 trace、observation（span/event/generation）、score。
- 能看的历史：**30 天**。
- 用户：**2 个**；项目数不限。
- 速率：写入 1,000 次请求/分钟；通用接口 30 次/分钟；Metrics 接口 100 次/天。
- 告警：**2 个**；人工标注队列 1 个。

**30 天之后数据会删吗**：不会。30 天只限制"能看多久"，不删除数据；Hobby 和 Core 都**不能**设置自动删除，只有 Pro 和 Enterprise 能设保留期（最少 3 天）。自建版要用保留期功能需要企业版。【原文：https://langfuse.com/docs/administration/data-retention】也就是说，发到 Hobby 的数据会一直留在 Langfuse 那边，你没法让它自动过期。

### 1.4 告警（出事时提醒）

- 可监视的数据：observation、数值/分类/布尔评分；指标是"聚合方式 + 度量"，比如 `avg latency`、`count`、`p95 cost`；可以按模型名、标签、user_id、environment 筛选。文档没有一个现成叫"错误数"的指标，自定义错误信号要靠"写一条 score，再对这个 score 告警"。
- 统计窗口：比如 1 小时、1 天、1 周。多久评估一次，文档没写【待验证】。
- 发到哪：Slack、Webhook（带 HMAC 签名的 JSON）、或触发某个 GitHub 仓库的 `workflow_dispatch`（要填个人访问令牌）。
- 数量：Hobby 2 个，自建 v4 不限。
【原文：https://langfuse.com/docs/observability/features/alerts.md】

【推断】这类告警是"按时间窗统计后超阈值就报"，适合"最近一天出错数 > 0"这种，不是"某次运行一失败就立刻报"。对 RepoAegis，失败的即时提醒用 GitHub 自己的手段更直接（见第四节）。

### 1.5 自建需要什么

- 组件（文档当前版本标为 v4）：Web 容器 `langfuse/langfuse`（页面和接口）、Worker 容器 `langfuse/worker`（异步处理事件）、**PostgreSQL**（事务数据）、**Redis/Valkey**（缓存和任务队列）、**ClickHouse**（观测数据）、**S3 类对象存储**（原始事件和附件，Docker Compose 里用 MinIO）。【原文：https://langfuse.com/self-hosting】
- 部署方式：Docker Compose（单机，"没有高可用、扩展和备份"，适合本地和测试）；生产用 Kubernetes(Helm)、AWS、Azure、GCP。【原文：同上，以及 https://langfuse.com/self-hosting/deployment/docker-compose】
- 机器：单机部署建议至少 4 核 16 GiB 内存，硬盘示例 100 GiB。【原文：docker-compose 页】
- Python SDK v5 要求自建服务端 ≥ v4.59.0。【原文：sdk/overview 页】

**许可证**：仓库 LICENSE 写明，`ee/`、`web/src/ee/`、`worker/src/ee/`、`packages/shared/src/server/ee/` 这几个目录下的代码用 `ee/LICENSE`（企业版许可），其余部分是 MIT。【原文：`langfuse/langfuse` 仓库根目录 LICENSE 第 3–7 行】自建文档标 "(EE)" 的功能有：组织创建者、实例管理接口、界面定制；数据保留期也需要企业版。【原文：self-hosting 页、data-retention 页】

**对 RepoAegis 的影响**【推断】：自建 Langfuse 至少要一台常开、能被 GitHub 机器从公网访问到的服务器，跑 5–6 个服务。这直接违反"不自建服务器、不自建数据库"的原则，而且作者没有 Docker。

### 1.7 OpenAI 集成能不能配 DeepSeek 这类自定义 base_url

- 用法：把 `import openai` 换成 `from langfuse.openai import openai`（或 `OpenAI`）。【原文：https://langfuse.com/integrations/model-providers/openai-py】文档只写"支持 OpenAI 和 Azure OpenAI"，**没写**支持其他兼容接口。
- 但源码里它是用 `wrapt` 直接给 `openai` 库里的类方法打补丁（`openai.resources.chat.completions.Completions.create` 等），不管你的客户端 `base_url` 指向哪里。【原文：`langfuse/openai.py` 第 40、85–113 行】所以【推断】指向 DeepSeek 的 `base_url` 不影响记录，调用照样被记成一条 generation。实际跑通【待验证】。
- 记录失败的调用：调模型抛异常时，它把这条 generation 标成 `level="ERROR"`、写入错误信息，然后**原样把异常抛回给你的代码**，不吞掉。【原文：openai.py 第 1325–1335 行】
- **token 数**：从接口返回的 `usage` 里读。【原文：openai.py 第 704、710 行】流式调用要传 `stream_options={"include_usage": True}` 才有用量。【原文：openai-py 集成页】

### 1.8 短命进程：数据怎么确保发出去、失败会怎样、会不会拖慢 agent

这是读源码得到的，按发生顺序说：

1. **平时不阻塞**：Langfuse 的发送器继承自 OTel 的 `BatchSpanProcessor`（批量发送器）。每个步骤结束时只是放进内存队列，由后台线程攒批发送，agent 主线程不等网络。【原文：`langfuse/_client/span_processor.py` 第 128–227 行】
2. **默认参数**（OTel 默认值）：每 5 秒发一次、每批最多 512 条、队列最多 2048 条、导出超时 30 秒。【原文：`opentelemetry-python` 仓库 `opentelemetry-sdk/src/opentelemetry/sdk/environment_variables/__init__.py` 第 120–149 行】Langfuse 自己的 `LANGFUSE_TIMEOUT` 默认 **5 秒**，会作为导出超时传进去。【原文：environment_variables.py 第 165–171 行；span_processor.py 第 222 行】
3. **队列满了**：最老的数据被丢掉，打一条 "Queue full, dropping" 警告，不报错。【原文：`opentelemetry-sdk/.../_shared_internal/__init__.py` 第 204–208 行】
4. **服务端连不上或报错**：OTel 的 HTTP 发送器对可重试的状态码和连接错误最多重试 6 次，指数退避，但总时长不超过超时；不可重试或重试用尽，就记一条 error 日志、这批数据**丢弃**，返回失败，**不向你的代码抛异常**。【原文：`opentelemetry-python` 仓库 `exporter/opentelemetry-exporter-otlp-common/src/opentelemetry/exporter/otlp/common/http.py` 第 30、45–47、185–225 行】单批超过 64 MiB 也会直接丢弃并记日志。【原文：environment_variables.py 第 65–73 行】
5. **进程结束时**：客户端初始化时注册了 `atexit`（Python 正常退出时自动执行的钩子）去调 `shutdown()`，`shutdown()` 会先 `flush()` 再停后台线程。【原文：`langfuse/_client/resource_manager.py` 第 278、596–620 行】文档要求短命程序**手动调用** `flush()` 或 `shutdown()`。【原文：data-model 页；https://langfuse.com/docs/observability/sdk/troubleshooting-and-faq】
6. **flush 会不会卡住**：`flush()` 内部调 `tracer_provider.force_flush()`，但**不检查返回值**。【原文：resource_manager.py 第 596–601 行】所以【推断】发送失败时 `flush()` 也照常返回，不会抛异常，最多等到超时。注意：`flush()` 的文档字符串说它"保证数据已送达接口"【原文：`langfuse/_client/client.py` 第 2194–2221 行】，和上面源码行为对不上；以源码为准【推断】。它还提醒：送达后要 15–30 秒才能在接口里查到。
7. **GitHub 取消或超时会怎样**：GitHub 取消一个步骤时，先发 SIGINT（相当于 Ctrl-C），7.5 秒不退出就发 SIGTERM，再等 2.5 秒，然后杀掉整个进程树。【原文：https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-cancellation】Python 收到 SIGINT 会抛 `KeyboardInterrupt`，正常退出时 `atexit` 会执行【推断】；但被强杀时 `atexit` 不会执行，队列里没发出去的数据就丢了【推断】。`timeout-minutes` 超时是不是走同一套流程，该文档没写【待验证】。

**结论**【推断】：接 Langfuse 不会拖垮 agent（失败只记日志、丢数据），平时也不拖慢；只在结束时 `flush()` 可能多等几秒。代价是：**监控数据可能丢**，尤其是被强杀时。所以"运行结局"不能只靠 Langfuse 记，必须另有一份不依赖网络的记录（见第四节）。另一个容易踩的坑：如果你用自己的 OTel 配置，Langfuse 的发送器只发"Langfuse 自己的和 GenAI 相关的 span"（`should_export_span` 默认过滤）。【原文：sdk/overview 页】

### 1.9 隐私相关的 SDK 功能

- `mask`：在 SDK 生成属性时同步调用你的函数做脱敏，只对通过 Langfuse SDK 接口写入的数据生效。

## 四、GitHub 自带的手段

### 4.1 作业摘要 `$GITHUB_STEP_SUMMARY`

往这个环境变量指向的文件里写 Markdown，就会显示在**运行的摘要页**上。支持 GitHub 风格的 Markdown（表格、折叠块等）。每个步骤最多 **1 MiB**，超了这个步骤的摘要上传失败并产生一条错误注解；每个作业最多显示 **20 个**步骤的摘要。摘要里意外写入的密钥会被自动打码。步骤之间互相隔离，一个步骤的 Markdown 写坏不影响后面。【原文：https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-commands ，"Adding a job summary" 一节】

### 4.2 注解 `::error` / `::warning` / `::notice`

格式：`::error file={name},line={line},endLine={endLine},title={title}::{message}`，三种只差命令名；`file` 默认 `.github`。【原文：workflow-commands 页，"Setting a notice/warning/error message" 各节】**数量上限**：Actions 每个步骤最多 10 条 warning 注解和 10 条 error 注解。【原文：https://docs.github.com/en/rest/checks/runs ，"Create a check run" 的 `output.annotations` 参数说明】notice 的上限、每个作业的总上限，没找到一手说明【未找到】。显示位置：运行摘要页的注解区和日志里对应的行【推断，workflow-commands 页只说"会创建一条注解"】。

### 4.3 运行失败默认通知谁

- 你**触发的**运行结束时，你会收到通知；可以选"只在失败时通知"；渠道是邮件或网页，在个人通知设置里开。定时触发的工作流，通知发给最初创建它的人（改过 cron 的人或重新启用的人会接替）。【原文：https://docs.github.com/en/actions/concepts/workflows-and-actions/notifications-for-workflow-runs】
- 【推断】对 RepoAegis 来说，`issues: labeled` 触发的运行，"触发者"就是打标签的那个人，所以默认只有打标签的人（且他开了 Actions 通知）会收到失败通知；仓库主人不一定收到。设置里没有"把失败通知发给别人"的选项【推断：上述文档没提】。想通知固定的人，可以在工作流里加一个 `if: failure()` 的步骤，在 issue 里发评论并 @ 某人，借 GitHub 普通的 @ 通知送达【推断】。

### 4.4 用 REST 接口做汇总

- 列某个工作流的所有运行：`GET /repos/{owner}/{repo}/actions/workflows/{workflow_id}/runs`（`workflow_id` 可以直接写文件名），可按 `status`（含 `failure` 这种结局）、`event`、`created` 筛选，每页最多 100 条；带筛选条件时最多返回 1,000 条。返回字段有 `conclusion`（结局）、`status`、`run_started_at`、`html_url`、`display_title`。"对仓库有读权限的人都能调用"。【原文：https://docs.github.com/en/rest/actions/workflow-runs】
- 单次运行的计时接口 `GET .../runs/{run_id}/timing`，文档标注"正在关停"。【原文：同页】
- 列产物：`GET /repos/{owner}/{repo}/actions/artifacts`（整个仓库）、`GET .../runs/{run_id}/artifacts`（某次运行）；下载接口返回一个 **1 分钟后过期**的跳转地址；经典个人令牌需要 `repo` 权限。【原文：https://docs.github.com/en/rest/actions/artifacts】
- 日志和产物默认保存 **90 天**。【原文：https://docs.github.com/en/actions/how-tos/manage-workflow-runs/download-workflow-artifacts】

注意：GitHub 自带的 `conclusion` 只有 success/failure/cancelled/timed_out 这一类，分不出"暂停""交付失败"这种业务结局【推断】。所以要把我们自己的结局写进产物（比如一个 `result.json`）或写进运行标题/摘要，汇总时再读。

**汇总页的两种做法**【推断，均未实测】：

- **GitHub Pages 静态页**：一个定时或每次运行后触发的工作流，调上面的接口、下载各次的 `result.json`，生成一张 HTML 表格发布到 Pages。限制：免费账号的仓库必须是**公开**的才能开 Pages；"Pages 站点在互联网上公开可见，即使仓库是私有的"（视套餐而定）。【原文：https://docs.github.com/en/pages/getting-started-with-github-pages/creating-a-github-pages-site】站点最大 1 GB，带宽软上限 100 GB/月，构建软上限每小时 10 次，部署超过 10 分钟超时。【原文：https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits】
- **固定 issue 当看板**：每次运行结束时，用接口改一个置顶 issue 的正文（一张表：时间、issue、结局、token、费用、运行链接）。不需要 Pages，但每次运行都要写同一个 issue，两个运行同时结束会有"后写覆盖先写"的竞争。issue 正文的长度上限【待验证】。

## 五、安全与隐私

**把 trace 发到第三方的风险**【推断，依据见括号】：

- trace 里会有 issue 正文、仓库代码片段、模型的完整输入输出、工具输出（`@observe` 默认记录参数和返回值，见 1.6）。私有仓库的代码会因此出境，存进 Langfuse 在 AWS 的某个区（见 1.3）。
- 免费档**不能**设自动删除，数据会一直留着（见 1.3 data-retention）。
- 最危险的是密钥：agent 跑在装着各种令牌的 Actions 机器上，如果它执行了 `env`、`cat .env` 一类命令，工具输出里就带着密钥。GitHub 的自动打码**只作用于 Actions 日志**，不作用于你自己发往第三方的数据；而且 GitHub 自己也说打码"不保证"（值被变形后就认不出来）。【原文：https://docs.github.com/en/actions/concepts/security/secrets ，"Automatically redacted secrets"】所以发出去之前必须自己脱敏（Langfuse 的 `mask_otel_spans`，见 1.9）。
- 公开仓库的 issue 谁都能写，issue 内容可能是故意构造的提示注入；这类内容进 trace 本身问题不大，但会经过模型、影响工具输出。

**Langfuse 密钥放在哪**：
- 放进仓库的 Actions secrets，用环境变量传给 agent 进程。【推断】
- Langfuse 的公钥+私钥不只能写，还能**读**整个项目的数据（SDK 用同一对密钥查询，例如 `api.observations.get_many`）。【原文：client.py 第 2216–2220 行 flush 文档字符串里提到用 `api` 查询】【推断】所以私钥泄露 = 所有历史 trace 泄露。
- 可以用"环境密钥 + 必须有人批准"来限制哪些作业能拿到密钥。【原文：secrets 页，"Environment secrets"】但 RepoAegis 的流程是"打标签就自动跑"，加人工批准会和设计冲突【推断】。
- 只给需要的那一步传密钥，不要放在整个作业的 `env` 里，避免 agent 跑的命令也能读到【推断】。

**公开仓库下，作业摘要和产物谁能看**：
- 看工作流运行信息**必须登录 GitHub**，即使是公开仓库；查看、搜索、下载日志需要读权限。【原文：https://docs.github.com/en/actions/how-tos/monitor-workflows/use-workflow-run-logs】公开仓库任何登录用户都有读权限，所以【推断】任何登录用户都能看日志、作业摘要和下载产物。
- 下载产物需要读权限。【原文：download-workflow-artifacts 页】
- claude-code-action 自己也在 `show_full_output`、`display_report` 两个选项上警告：内容会公开可见、可能带密钥。【原文：`action.yml` 第 152–158 行】

## 六、三条路对比

下面"要做的事""成本"等都是【推断】，基于上面各节的原文事实。

### 路一：只用 GitHub 自带的（作业摘要 + 注解 + 产物 + 汇总页）

**要做的事**：agent 循环里每次调模型、调工具时，往本地写一行 JSON（时间、类型、耗时、token、费用、简要内容）；结束时（放在 `if: always()` 的步骤里，取消时也会跑，见 4.3 引的取消文档）做三件事：把轨迹文件作为产物上传；把一张摘要表写进 `$GITHUB_STEP_SUMMARY`；失败时打一条 `::error` 注解，并在 issue 里发评论 @ 人。汇总页另写一个小工作流：调 REST 接口，生成 Pages 页面或更新一个固定 issue。费用要自己按 DeepSeek 单价算。这正是 SWE-agent / mini-swe-agent 的做法（轨迹文件 + 查看器），见第三节。

**成本**：0 元。只占 Actions 分钟数和产物存储。

**能看到什么**：每次运行的结局和摘要表（运行页上）；完整过程要下载产物，用 `jless` 或自己写的简单查看器看；跨运行的统计看汇总页。没有现成的步骤树网页、没有筛选搜索。

**数据去哪**：只在 GitHub。保留 90 天（见 4.4）。公开仓库下登录用户都能看（见第五节）。

**出事怎么提醒**：打标签的人默认收到失败通知（见 4.3）；自己在 issue 里 @ 人。即时、不依赖第三方。

**风险**：摘要每步 1 MiB、注解每步 10 条的上限（见 4.1、4.2）；公开仓库里过程数据对所有登录用户可见，要先脱敏。

### 路二：接 Langfuse 云服务（Hobby 免费档）

**要做的事**（2026-10-30 改为收尾作业在运行结束后一次性上传、只用标准库直接发，不装 langfuse 库，见 [暂停存档与监控](../暂停存档与监控.md)）：在路一的基础上（结局和提醒仍然建议用 GitHub 做，原因见 1.8 的"数据可能丢"和 1.4 的"告警是按时间窗统计"），再加：`pip install langfuse`；用 `langfuse.openai` 替换 openai 导入或手动建 observation；用 `propagate_attributes` 挂 issue 编号、运行编号；在 Langfuse 里为 DeepSeek 加模型单价（或自己上报费用）；写 `mask_otel_spans` 脱敏；结束前 `flush()`；三个 `LANGFUSE_*` 放进 Actions secrets。

**成本**：免费档 0 元，每月 5 万单位、超出不能加量（约几百次运行，见 1.3 的估算）；2 个用户、30 天可见、2 个告警。超出要升 Core（29 美元/月）。

**能看到什么**：现成的网页：每次运行的步骤树、agent 图、每步耗时/token/费用；按标签、session 筛选；按 issue 归组回放。这是三条路里最接近"类似 Langfuse 的监控"的。

**数据去哪**：Langfuse 在 AWS 上的某个区（欧盟/美国/日本），免费档不能设自动删除；私钥泄露会泄露全部历史。

**出事怎么提醒**：Langfuse 告警可以按窗口统计发 Slack/Webhook/触发 GitHub 工作流，但适合趋势类；单次失败的即时提醒仍靠 GitHub。

**风险**：监控数据可能丢（被强杀、网络失败时只记日志）；不会拖垮 agent（见 1.8）。依赖一家第三方服务和它的免费政策。

### 路三：自建 Langfuse 或 Phoenix

**要做的事**：
- 自建 Langfuse：一台常开、公网可达的机器（建议 4 核 16 GiB），跑 Web、Worker、Postgres、ClickHouse、Redis、对象存储 6 个服务，通常靠 Docker（见 1.5）；还要管 HTTPS、密码、备份、升级。
- 自建 Phoenix：轻很多，一个 Python 进程 + 一个 SQLite 文件就能跑（见第二节）。但 GitHub 的临时机器要能把数据发到它那里，它就必须是一台公网可达的常开机器。
- 一个折中【推断，未验证】：运行时把 OTel 数据写成文件当产物上传，作者需要时再下载下来，导入 WSL 里本地跑的 Phoenix 去看。这样不需要常开服务器，但 Phoenix 是否支持从文件导入、怎么导入，本次没查【待验证】。

**成本**：一台云主机的钱（16 GiB 级别不便宜）加上维护时间；Phoenix 本地查看方案只花时间。

**能看到什么**：和路二差不多（Phoenix 的界面与 Langfuse 不同，但都有步骤树）；自建 Langfuse v4 告警不限数量。

**数据去哪**：自己的机器。

**出事怎么提醒**：自建 Langfuse 有告警；Phoenix 的告警能力本次没查【待验证】；单次失败提醒仍靠 GitHub。

**风险**：直接违反"不自建服务器、不自建数据库"；作者没有 Docker。Phoenix 是 Elastic License 2.0，不是 OSI 开源许可，自己用没问题，但若将来把它打包进 RepoAegis 对外提供要留意。

### 三条路共同的一点

无论选哪条，**"运行结局 + 出事提醒"都应该放在 GitHub 一侧做**：它不依赖网络、不会因进程被强杀而丢、通知直接到人。差别只在"过程"看哪里：GitHub 产物文件、Langfuse 云网页、还是自建的网页。具体选哪条由你定。

## 借鉴什么、不借鉴什么

- **SWE-agent、mini-swe-agent：借鉴。** 每次运行写一个完整的轨迹文件，每步一条，带时间、费用、结局，不依赖任何服务。这和我们"agent 每步把进度写到本机磁盘"的存档做法是同一份数据，可以合用。
- **claude-code-action：借鉴摘要，不借鉴默认把全部输出打进日志。** 它把报告写进作业摘要；完整输出默认关，因为可能带密钥。
- **Claude Code、Codex：借鉴"监控默认关、配了才开"。** 内容默认打码这一点不照搬：用户已确认试验项目内容公开问题不大，但密钥仍要脱敏。
- **OpenHands：不借鉴 Laminar。** 多一个第三方服务，和 Langfuse 二选一即可。
- **自建 Langfuse：不做。** 要 6 个服务和一台 4 核 16G 的常开机器，违反"不自建服务器、不自建数据库"。

## 建议（2026-10-27，用户已确认：不自建，用 Langfuse）

1. **结局和出事提醒放在 GitHub**：agent 每步往运行日志打一行（Actions 页面实时滚动，延迟几秒），结束时写作业摘要表、上传轨迹文件，失败或暂停时由收尾作业在 issue 里留言。这一层一定要有，因为它不依赖网络，进程被强杀也不丢。
2. **过程的网页查看接 Langfuse 云服务免费档，作为可选项**：配了密钥才开，没配就照常跑；发送前脱敏密钥；它每 5 秒批量发送一次，网页上接近实时（2026-10-30 改为运行结束后一次性上传）。限额是每月 5 万单位，30 天内可查。
3. **不用 GitHub Pages 做实时监控**：它只能放静态页面，不能接收数据。以后需要跨运行的汇总时，再考虑用定时工作流生成汇总页。
