# 调研报告：issue 和 PR 里的图片与附件有多常见

> 调研于 2026-10-24 前后，由当时的调研子 agent 用 `gh api graphql` 抓取 22 个公开仓库的数据并统计。材料：子 agent 交回的报告、抓取的原始数据和统计脚本、主对话里用户的原话。2026-10-25 从当时子 agent 交回的结果整理，未重新抓取。其中三项补充统计（漏检核对、前后对比字样、外部链接）在整理时用当时的脚本对当时保存的数据重跑过一遍，结果与报告一致，标为【实测】。
>
> 标记：【一手】写明文件和行号；【实测】是对保存下来的数据跑脚本得到的数字；【推断】是从数据或代码推出来的，原文没有直说；【待验证】是没查到的。下文"备份"指 `RepoAegis-backup-2026-10-25` 文件夹，"数据目录"指其中的 `调研数据_07cdd5fe/freq/`。

## 一、为什么查

2026-10-24 讨论 agent 收到的输入时，用户问了两次图片和附件的事。第一次是问 GitHub 支持哪些格式：

> "除了图片，还有没有比如说语音什么之类的东西？这是它支持的格式的关系。我想问的是，它支持的格式有哪些？"（主对话 `0501da8f….jsonl` 第 2285 行，2026-10-24）

第二次是问频率：

> "那比如说图片的使用频率一般是多少，以及除了图片之外其他格式的文件使用频率大概又是多少。我们可能需要一个频率比较高的常见的场景就可以。"（同上第 2338 行）

背后的问题是：要不要让 RepoAegis 支持看图。看图要用"多模态"模型，也就是除了文字还能接收图片的模型，会多出下载图片、选模型、评估效果这一整块工作。值不值得做，取决于真实仓库里带图的 issue 到底有多少、图里装的是什么。

## 二、方法和出处

**选了哪些仓库。** 子 agent 人工挑了 22 个活跃的公开仓库，分 5 类【一手】（数据目录 `repos.txt`）：

- 通用库和框架：pydantic、tokio、gin、axios、vuejs/core
- 前端界面组件库：mui、shadcn-ui、ant-design
- 桌面、终端、网页应用：zed、logseq、localsend、excalidraw、lazygit
- 开发工具：uv、prettier、vite、fzf
- 数据和机器学习：transformers、pandas、polars、scikit-learn、ollama

挑选理由是覆盖 Python、JS/TS、Go、Rust、Dart 几种语言，既有 zed、transformers 这样的超大项目，也有 gin、localsend、lazygit、fzf 这样的中等项目。

**时间范围和抽样。** 2026-04-24 到 2026-10-17，切成 6 个月度窗口，每个窗口里 issue 和 PR 各取最新创建的 10 个；最后一周不取，给讨论留时间【一手】（数据目录 `fetch.sh` 第 5 行、第 13 行）。所以每个仓库最多 60 个 issue、60 个 PR。实际拿到 1266 个 issue、1309 个 PR；gin 的 issue 只有 21 个，fzf 的 PR 只有 49 个【实测】（数据目录 `summary.txt`"样本规模"一节）。搜索条件是 `repo:… is:issue created:… sort:created-desc`，**没有限定开着还是关了**，所以样本里两种都有【一手】（`fetch.sh` 第 13 行）。

**抓了哪些文字。** 每个 issue 抓正文和全部评论（上限 100 条）；每个 PR 另外抓评审总评和每条评审下的行内意见。每条都取原始 Markdown 和 GitHub 渲染后的 HTML 两份【一手】（数据目录 `q_issue.graphql`）。子 agent 报告说没有一条触到上限。原始数据是 `raw/` 下 264 个 JSON 文件。

**怎么判定"含图"。** 规则写在数据目录 `analyze.py` 里【一手】：

- 先去掉代码块、行内代码和 HTML 注释，issue 模板里被注释掉的示例图不算（第 16–25 行）。
- 图片：Markdown 写法 `![…](…)`、HTML 写法 `<img src=…>`、旧式 `user-images.githubusercontent.com` 链接、直接贴出的外链图片地址（第 28–35 行、第 101–110 行）。GIF 算图片。
- 视频：GitHub 上传视频时，正文里插入的是一条不带图片语法的裸链接 `github.com/user-attachments/assets/<编号>`，光看 Markdown 分不出是图还是视频。脚本拿同一个编号去渲染后的 HTML 里找：出现在 `<video>` 里算视频，在 `<img>` 里算图片，都找不到记为"无法判定"（第 88–100 行）。扩展名是 mp4、mov、webm 等的链接也算视频。
- 其他附件：`github.com/user-attachments/files/<编号>/<文件名>` 这种链接，按扩展名归类（第 34 行、第 84–87 行）。
- 排除的噪声：徽章、状态图标、头像，以及 Cursor、cubic、Devin、CodeSandbox 等工具自动插进 PR 描述的按钮图（第 40–46 行），一共 142 张【实测】。
- 机器人：账号类型是 Bot，或者名字以 `[bot]`、`-bot` 结尾，就算机器人（第 115–118 行）。主口径只算人写的、非空的文字。

**统计口径。** 一是"条目"口径：一条正文或一条评论算一个条目，看含至少一张图（或一个视频、一个其他附件）的条目占多少。二是"整串"口径：一个 issue 只要正文或任何一条人写的评论里有，就算这个 issue 含图。

**一个离群值。** lazygit#6051 是维护者用来存 54 段演示录屏的 issue，主口径把它排除了。保留它的版本存在 `summary_keep_outlier.txt`：issue 评论的含视频比例会从 0.3% 跳到 2.5%，其他数字基本不变【实测】。

**怎么校验。** 漏检方面，拿渲染后的 HTML 反查：HTML 里带 GitHub 上传图片或视频的人写条目共 348 条，规则全部识别到了，没有漏检【实测】（整理时重跑数据目录 `crosscheck.py`，输出"未识别: {}"、"html-with-media human items 348"）。误检方面，子 agent 随机抽 30 条含图条目，只看图片前后的文字、没有打开图片，发现 1 条是 Weblate 翻译进度小图，属于误算（子 agent 自报，【待验证】，抽样过程没有留下记录）。

**样本偏向。** 这几点会影响数字能不能直接套到 RepoAegis 上：

- 仓库是人工挑的，每类只有 3 到 5 个，类别之间的差距很大程度上由个别仓库带动，比如 zed。不能当成整个 GitHub 的比例。
- 每月只取最新的 10 个，样本偏向每月月底；最后一个窗口的条目讨论时间短，评论可能偏少。
- 样本里开着的和关了的 issue 都有，而 RepoAegis 只处理开着的；也不是"被打上处理标签的 issue"。两者的含图率是否不同，【待验证】。
- 机器人只按账号判断，挂在普通用户账号下的 AI 工具发的截图算作人。
- 只统计了 GitHub 上传的附件和显式图片语法；不带扩展名的图床页面、外部视频网站、直接贴成文字的日志，不在主口径里。
- GitHub 搜索结果不包括已删除、被隐藏或转成讨论帖的 issue。

### 图片以外的附件

人上传的其他文件在整个样本里只有 40 个，按扩展名数：zip 14 个，log 10 个，md 5 个，sh 4 个，txt 3 个，pdf、py、js、gz 各 1 个。**一个音频文件都没有。**这些附件几乎都在 issue 里（issue 正文 14 条、issue 评论 16 条），PR 里只有 2 条【实测】。

另有一些不是附件、但作用相近的链接，不算在主口径里：gist 或 pastebin 这类粘贴站 19 条，YouTube、Loom 等外部视频 4 条，asciinema 终端录屏 1 条（分母是 7326 条人写的非空条目）【实测】（整理时重跑 `extlinks.py`）。也就是说，有人不传日志文件，而是贴一个粘贴站链接。

### 机器人发的图

把机器人算进去，PR 普通评论的含图率从 1.6% 升到 10.3%【实测】。发图最多的是 github-actions、coderabbitai、codspeed、netlify、greptile、vercel 等，内容多是状态徽章、性能图表、预览链接【实测】（重跑 `crosscheck.py` 的"发图最多的机器人"一行）。这些图对修代码没有用。

### 图片通常用来做什么

子 agent 抽 30 条含图条目，只看图片前后的文字粗略归类：报错或异常现象截图约 12 条，改动前后对比约 8 条，功能设想示意约 3 条，文档截图约 2 条（子 agent 自报，【待验证】，没有逐张打开图片）。

有两个数字可以从数据里核对。48 个含图的 PR 描述里，22 个出现了 before 或 after 字样，说明 PR 里的图多是改动前后对比【实测】（重跑 `beforeafter.py`）。人写条目里一共 414 处图片说明文字（`![这里](…)` 或 `alt="…"`），其中 310 处是空的、默认的 "Image"，或者只是截图文件名，约占四分之三；这个数也包含少量徽章【实测】（同一脚本）。所以靠图片的说明文字猜图里是什么，基本行不通。

还有一类值得注意：有人把终端输出或测试结果截成图贴上来，而不是贴文字。这时关键信息只在图里，只读文字的 agent 看不到。子 agent 给的例子：

- 报错和对照截图：https://github.com/excalidraw/excalidraw/issues/11515
- 界面显示问题，截图里用红框标出：https://github.com/shadcn-ui/ui/issues/11927
- PR 前后对比表：https://github.com/zed-industries/zed/pull/64684
- 用截图代替文字贴测试或终端输出：https://github.com/pola-rs/polars/pull/28061#issuecomment-4780131000 、https://github.com/vitejs/vite/issues/22750#issuecomment-4827605728
- 维护者用截图回复"复现不出来"：https://github.com/junegunn/fzf/issues/4836#issuecomment-4701730302

这些链接是子 agent 当时给的，整理时没有重新打开【待验证】。

### GitHub 允许上传哪些格式

这部分回答用户第一个问题，来自另一个子 agent 读的 GitHub 官方文档源文件 `github/docs` 仓库 `content/get-started/writing-on-github/working-with-advanced-formatting/attaching-files.md`（对应网页 docs.github.com 的 "Attaching files" 页）【一手】（子 agent 读取记录：备份 `会话记录/0501da8f…/subagents/agent-a395b4dfc47ba755a.jsonl` 第 301 行；本地没有保存该文件，整理时未重新打开）。

大小上限：图片和 gif 10MB；视频在免费计划的仓库里 10MB，付费计划 100MB；其他文件 25MB。哪里都能传的格式是 png、gif、jpg、svg 图片和 mp4、mov、webm 视频。在 issue、PR、讨论的评论里还能传：pdf 和 Office 文档、txt、md、csv、log、json 等文本，常见代码文件，zip、gz、tgz 压缩包，eml 等邮件文件，bmp、tiff 图片，以及 **mp3、wav 音频**。所以 GitHub 支持上传音频，只是抽样里一次也没出现。文档里音频等几项写在一个版本条件里（`ifversion fpt or ghec or ghes > 3.18`），github.com 上可用【一手】（同一行记录）。

上传后正文里出现的是一条 `github.com/user-attachments/…` 链接。公开仓库的附件不登录就能下，私有仓库的附件只有有权限的人能看（子 agent 转述同一文档）。用接口取正文时，图片会变成带时效签名的 `private-user-images.githubusercontent.com` 链接；claude-code-action 就是靠这种签名链接下载私有仓库图片的，细节见 [官方项目如何组织issue上下文](官方项目如何组织issue上下文.md)。

## 四、各项目对附件的做法：借鉴什么、不借鉴什么

各官方项目怎么处理图片，另一篇 [官方项目如何组织issue上下文](官方项目如何组织issue上下文.md) 有完整对比，这里只说和本篇数字直接相关的一点：**图片以外的附件，没有一家去读。**claude-code-action 只匹配 `user-attachments/assets` 形式的图片，`user-attachments/files/` 下的 pdf、日志等匹配不上，不下载【一手】（备份 `调研数据_07cdd5fe/cca/image-downloader.ts` 第 7–14 行）；OpenHands 旧版解决器只抽 `![…](http…)` 形式的图片地址；SWE-agent 只处理数据集里列出的图片。

借鉴：图片以外的附件一律跳过。抽样里这类附件只占约 1.8% 的 issue，以 zip 和 log 为主，没有音频，官方项目也都不处理，投入不划算【推断】。

不借鉴：本篇不涉及各家的看图方案，原因见第五节，用户决定暂不看图。

## 五、据此的决定

**图片以外的附件一律跳过。**用户 2026-10-24 原话："除了图片之外的东西，你说那个其他项目都是没有，就直接跳过 OK， 我们也这么做。"（主对话第 2338 行）已写进 [项目边界](../项目边界.md) 第 23 行。

**带图片的 issue 暂不处理。**用户 2026-10-24 原话："图片的话，需要引入多模态，然后这个多模态我目前都没有学过，以及它找到图片可能这个大模型发挥，最后文字加一块之后大模型发挥不一定好，所以我们先略过这个模块，之后再看看，把那个项目做完之后要不要加图片呢？就是我们先不处理带图的 PR……"（主对话第 2706 行）。原话说的是"带图的 PR"，上下文指的是交给 agent 处理的 issue，项目文档按"带图片的 issue"记录（[项目边界](../项目边界.md) 第 21 行、`CLAUDE.md`）。主体流程做完后再评估要不要加。

**待定**：遇到带图片的 issue 具体怎么回应（[项目边界](../项目边界.md) 第 21 行写明尚未确定）；被引用的 issue 里有图片时，是删图照收还是整个不收（[issue里引用的其他issue](issue引用与打标签前后的修改.md) 第 9 条，待拍板）。
