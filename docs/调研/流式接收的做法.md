# 调研报告：各项目怎么处理流式接收的难点

> 日期：2026-11-03。源码由调研子 agent 浅克隆后阅读，版本：codex `9630fcf`、openai-python `f6e8480`、anthropic-sdk-python `5752c13`、litellm `ff182c19`、OpenHands software-agent-sdk `77e7ce7`、aider `5dc9490`、gemini-cli `0ac57c0`（WSL `~/scratch/stream-research/`）。我抽查了其中三处原文：litellm 覆盖 id 和名字、Gemini CLI 的"无效流"检查、OpenHands 的 Retry-After 上限，与报告一致；其余出处没有逐条复核。标【推断】的是子 agent 从代码结构或库的文档语义推出来、没有打开原文核对的。

## 一、为什么查

[调用DeepSeek.md](调用DeepSeek.md) 定了用流式接收 DeepSeek 的回答，[model.py](../../src/repoaegis/model.py) 已经写好。流式有五个难点：工具调用的参数碎片怎么拼、怎么发现卡死、半路断开怎么办、怎么确认收完、中途报错怎么办。想知道别的项目怎么处理，对照我们的做法，找遗漏。

## 二、谁用流式

- 一直流式：Codex CLI（`core/src/client.rs:1168`）、aider（默认，`args.py:325`）、Gemini CLI。都是给人看的终端工具。
- 默认不流式：OpenAI 接口本身（官方文档 "By default ... we generate the model's entire output before sending it back"）、OpenHands SDK（`llm.py:510`，开了流式却没给逐字回调时自动退回非流式）、mini-swe-agent、SWE-agent。
- Anthropic SDK 对预计超过 10 分钟的非流式请求直接拒绝，要求改用流式（`_base_client.py:857–866`）。
- ChatGPT、Claude.ai 网页默认流式与否，官方文档没有明说【待验证】。Claude Code 内部是否流式，源码不公开【待验证】。

## 三、五个难点各家怎么做

**1. 拼工具调用碎片。**
- openai-python 按 `index` 拼，除 `index`、`type` 外所有字符串字段都接起来（`lib/streaming/_deltas.py:29–34`），只有 strict 工具最后检查 JSON。
- litellm 按"候选回答序号 + index"拼；`id`、名字、类型取新收到的非空值**覆盖**，只有参数接起来；不检查 JSON（`streaming_chunk_builder_utils.py:636–661`、`:718`）。
- Anthropic SDK 每来一段就按"部分 JSON"解析一次，失败直接抛错（`lib/streaming/_messages.py:501–515`）。
- Codex（Responses 接口）、Gemini 接口直接给完整工具调用，不用拼。

**2. 发现卡死。** Codex、OpenHands（只在异步路径，`llm.py:1211–1225`）、Gemini CLI 都是"两段之间最多 300 秒"；openai-python、aider 是 600 秒的读超时。Anthropic SDK 收到 `ping` 跳过但字节到了，计时会重置【推断】。

**3. 半路断开。**
- 整条重问、丢掉半截：OpenHands（5 次，8 秒起到 64 秒）、Gemini CLI（4 次，1 秒起翻倍）、aider（0.25 秒起，超过 60 秒停）。
- Codex 也整条重问，但每个已经完整收到的条目当场写进历史、工具当场执行，重试时只丢"正在收的那半截"（`core/src/stream_events_utils.rs:358`、`core/src/session/turn.rs:1842`）。
- 续写：litellm 有个默认关闭的开关，断流前只收到纯文字时把它当前缀接着写，收到过工具调用或思考内容就不续（`router_python_core.py:4298、4329–4353`）；Anthropic 官方文档也说 "Tool use and thinking blocks cannot be partially recovered"。
- openai-python、Anthropic SDK 流开始后不自动重试，异常交给调用方。
- 已经显示给人的字，各家都不撤回【推断】。

**4. 确认收完。**
- 检查的：Codex 必须收到 `response.completed`，否则报错并重试（`codex-api/src/sse/responses.rs:618`）；litellm 没收到 finish_reason 就报 "Stream ended before a finish_reason was received"（`streaming_handler.py:2199–2211`）；Gemini CLI 没有工具调用时，缺结束原因、工具调用格式错、正文为空、只有思考没正文都算"无效流"并重试（`geminiChat.ts:1729–1784`）。
- 不检查的：openai-python 断流时循环正常结束，注释写明不保证收完（`_completions.py:331`）；Anthropic SDK 不看有没有 `message_stop`（`_messages.py:96–102`）；aider 不检查。

**5. 中途报错。**
- Codex 先分类：上下文超长、额度用完、内容策略拦截不重试；限流、过载、未知错误重试（`sse/responses_error.rs:26–103`、`protocol/src/error.rs:426–475`）。
- litellm 统一包成"服务不可用"类错误交给上层重试；openai-python、Anthropic SDK 直接抛错不重试。
- Retry-After：OpenHands 服务端要求等的时间超过 64 秒上限，就放弃不等（`llm.py` 配置项 `retry_max_wait` 的说明）。

## 四、和我们的对照

**已经一样或更严：** 按 index 拼；两段之间 300 秒；断了整条重问、丢掉半截；5 次、8 秒起到 64 秒；没收到结束原因当没收完。openai-python、Anthropic SDK 都不检查收没收完，我们检查。

**其实已经处理、不用改的：**
- 保活注释算不算动静：`model.py` 每读到一行（包括 `: keep-alive`）都会重新开始计时，所以排队时不会被我们自己判卡死，最多等到 DeepSeek 排队 10 分钟主动断开，那时按"连接关了"重问。
- 参数不是合法 JSON：`call_tool` 会把"参数不是合法 JSON"交回模型让它重发（`tools/__init__.py`），不用整条重问。收完才执行，半截参数到不了这一步。
- 既没正文也没工具调用：主循环会打回去提醒，连续 3 次按出错结束（`loop.py` 模块说明）。

**值得借鉴（2026-11-03 用户确认，三条都已改进 `model.py`，补了 4 个测试）：**
1. **`id`、名字取第一次出现的非空值，不拼接**（照 litellm）。现在名字是拼接的，DeepSeek 实测只在第一段给名字所以没出问题，换成覆盖更稳。
2. **流中途的报错分类**（照 Codex）：余额不足、内容被拦截这类重试也没用，应直接失败；现在流中途的 `error` 一律重问。DeepSeek 中途报错长什么样没查到【待验证】，先按错误信息里的关键词分。
3. **Retry-After 超过 64 秒就不等**（照 OpenHands）。现在只要剩余时间够就照等。

**不借鉴：**
- Codex 保留已完成条目：靠 Responses 接口逐条的结束事件，chat completions 没有这种边界。
- 续写：官方明说工具调用和思考内容不能续，我们几乎每一步都有工具调用；后台运行也没有"已经显示给人的字"要保住。
- aider 的长度上限续写：我们靠工具调用推进，不适用。
