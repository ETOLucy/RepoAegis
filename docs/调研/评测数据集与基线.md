# 调研报告：评测数据集与基线

> 调研于 2026-10-24 前后。材料是当时几路调研子 agent 交回的报告和过程记录、主对话里用户的原话，以及当时下载到本地的 SWE-bench 榜单数据文件、两条 DeepSeek 记录的逐题明细和 20 条轨迹。2026-10-25 整理成文，网页上的数字**没有重新抓取**；本地数据文件在整理时用只读脚本重算过一遍，结果标【实测】。标【一手】的写了出处，指当时子 agent 读到了原文、源码或数据文件；标【推断】的是从数据推出来、原文没有直说的；标【待验证】的是只读到转述或摘要，或者几个出处互相矛盾。

## 一、为什么查

RepoAegis 最后要拿出一份评测结果，说明 agent 修 issue 的能力。2026-10-23 用户就评测提了三类问题。

第一类是**用什么数据**。用户当时的理解是：SWE-bench Verified 只当最终评测集，开发和实验阶段用 SWE-bench 全集扣掉 Verified 的部分，这样可以避免"数据污染"。用户想知道官方项目是不是这么做的，还是另有内部仓库；如果大仓库在本机跑不动，能不能找小型开源仓库代替，代价是什么。用户还问了几件事：test、dev、Verified 之间是什么关系，"污染"具体指什么，Verified 被质疑之后该怎么办，SWE-Gym、SWE-smith、SWE-rebench、SWE-bench-Live 这些数据集为什么没出现在选项里。

这里先解释两个词。**SWE-bench** 是从 12 个 Python 开源仓库的真实 issue 和对应的修复 PR 做成的评测集：每道题给 agent 一段 issue 文字和出问题时的代码，agent 交出补丁后，用修复 PR 里带的测试来判定修没修好。修好的题占总题数的比例叫**解决率**。**数据污染**指模型训练时已经见过评测题，或者见过题目的答案，分数因此虚高。

第二类是**跟谁比、凭什么比**。用户担心：个人项目和 OpenHands、mini-swe-agent 这类团队项目比没有优势，自己写的模块可能更差；模型、预算、提示词一不同，对比对象（**基线**，就是拿来做参照的那组成绩）就对不上；比不过的比较也没必要拿出来。那么个人项目该以什么为参照，优势在哪里？

第三类是**记录什么**。用户的看法是，成本、耗时不应该不加区分地全部记录，每项指标都要说清楚"记它是为了回答什么问题、支撑什么决定"；比如要比较哪个模型更划算，记成本才有意义。

约束条件：模型主要用 DeepSeek，通过 OpenAI 兼容接口调用；代码跑在个人电脑的 WSL2 上，8 核，内存约 7.8GB（可以调到约 12GB），当时没装 Docker；私有仓库只能做本地实验。

### 2. Verified 的质量问题和污染证据

调研子 agent 把"污染"整理成三层【推断：这是子 agent 的归纳，不是某篇论文的分法】。第一层是题目泄漏：训练数据里有 issue 文字和讨论。第二层是仓库泄漏：模型读过整个仓库，包括修复之后的版本。第三层是答案泄漏：训练数据里有正确补丁或测试，模型能直接背出来。SWE-bench 起初的防线是"训练集仓库和测试集仓库互不相交"，它只防住了"用同仓库的训练集训练"，防不住模型在预训练时抓取了整个 GitHub【推断】。

公开研究检测污染主要有三种办法。

第一种是记忆测试：只给 issue 文字，问模型要改哪个文件。SWE-Bench Illusion 发现，模型在 Verified 上最多 76% 答对，换成 SWE-bench 以外仓库的题只有 53%；复现的函数逐字重合（5-gram，即连续 5 个词相同）最高 35%，其他编码基准最高 18%【一手摘要：arXiv 2506.12286】。作者认为这可能是记忆，但这只是相关性，不能证明因果。

第二种是日期切分：只用模型发布日期之后才创建的题。SWE-rebench 报告，同一个 DeepSeek-V3-0324 在 Verified 上是 39.7%，在它 2025 年 3 至 4 月的新题上只有 21.3%【一手：arXiv 2505.20411】。

第三种是让训练集和测试集的仓库互不相交，也就是上一节说的 SWE-bench 自己的做法。

关于 Verified 本身的问题，有下面几份证据。

OpenAI《Why we no longer evaluate SWE-bench Verified》【一手，是经代理读到的转录件，页面不显示日期；日期 2026-02-23 来自搜索索引和二手报道，【待验证】】。审计对象是 138 题，挑选标准是"o3 在 64 次独立运行中没能稳定解出"。每题至少 6 名工程师审查，59.4% 有实质问题：测试过窄 35.5%，过宽 18.8%，其他 5.1%。OpenAI 还用 GPT-5 做自动红队测试，发现 GPT-5.2-Chat、Claude Opus 4.5、Gemini 3 Flash 都能复现部分题的标准补丁或原文细节。OpenAI 据此停报 Verified，建议改报 SWE-bench Pro 公开集，并自建私有基准。

这里要注意两点。一是 59.4% 只是"反复失败的那 138 题"里的比例，**不是整个 Verified 的比例**。二是多家二手报道把挑题用的模型写成了 GPT-5.2，原文写的是 o3。

OpenAI《Separating signal from noise in coding evaluations》【一手，同样是经代理读到的转录件；日期 7 月 8 日来自二手报道，【待验证】】审计了 SWE-bench Pro 公开集的 731 题：自动流程标出 200 题坏（27.4%），人工标出 249 题坏（34.1%），综合估计约 30% 是坏题。坏的类型包括测试过严、题面欠规定、测试覆盖太低、题面有误导。OpenAI 因此撤回了"改用 Pro"的建议。原文对 Pro **没有提污染**，问题出在任务本身。

Epoch AI 统计，Verified 近一半是 Django，5 个仓库占 80% 以上；他们人工分析了 40 题，估计约 5% 到 10% 的题有错、无法解出；所有题都来自 2023 年或更早【一手：Epoch AI substack】。另据子 agent 报告，Epoch AI 在 2026-09-03 把 Verified 评为 "Flawed"，推算至少 16.4% 的题是坏的。子 agent 没有注明这条是否读了原文【待验证】。

SWE-bench 官方仓库没有发声明，但有一个社区 issue（#669）指出 9 道 Verified 题的答案能从题面推出来【一手：子 agent 读到的 issue 页】。本地留存的榜单文件里，Verified 榜最后一条记录的日期是 2026-02-26【实测】。

更早的批评还有两项。SWE-Bench+ 核对了 SWE-agent 加 GPT-4 的成功补丁：32.67% 的题答案直接写在 issue 或评论里，31.08% 的测试太弱，过滤掉之后解决率从 12.47% 降到 3.97%【一手摘要：arXiv 2410.06992】。PatchDiff 发现 29.6% 的"通过"补丁行为和标准答案不同，解决率被高估 6.2 个点【一手：arXiv 2503.15223】。

### 4. 官方评分环境要多大的机器

官方 Docker 评分流程的要求是：至少 120GB 空闲磁盘，推荐 16GB 内存、8 核；并发数要小于 min(0.75×核数, 24)，8 核机器建议开 6 个；推荐 x86_64，arm64 还是实验性支持。镜像缓存分三级：base 约 120GB，默认的 env 约 100GB，instance 约 2,000GB。在 8 核、6 并发下跑完 Lite，env 缓存约 50 分钟，instance 缓存约 15 分钟【一手：swebench.com 的 docker_setup 与 harness 文档】。

Epoch 做了去重后的镜像仓库：全集 2,290 个镜像共约 67GiB，Verified 的 500 个约 30GiB；matplotlib 的镜像常见约 9GB，django 的 850 题只依赖 12 个环境镜像【一手：epoch.ai/blog/swebench-docker】。evalscope 文档说 Verified 全量镜像约 130GB，和 Epoch 的数字对不上【待验证】。

想省机器还有两条路。一是 Verified Mini：随机抽 50 题，约 5GB，HAL 和 evalscope 用它来调试【二手，【待验证】】。二是官方的云端评分工具 sb-cli，免费，约 20 分钟出结果【一手：mini-swe-agent 文档】。各仓库单题的测试耗时和镜像体积分布，官方没有公布，没查到。

### 5. bash-only 榜单：同一个最简脚手架、换不同模型

先解释两个词。**脚手架**（harness）指包在模型外面的那层程序，包括主循环、工具、提示词、停止条件。**mini-swe-agent** 是 SWE-bench 团队维护的极简脚手架，只给模型一个 bash 工具。SWE-bench 官网 Verified 榜里，有一组"bash-only"条目：所有模型都用 mini-swe-agent 跑，专门用于同一脚手架下的模型对比。

这组条目的设置如下。mini 的 1.x 版本从输出文本里解析动作，温度设为 0；2.x 版本改用工具调用。官方明确说 1.x 和 2.x 不一定可比，也"不为提高分数而调配置"。每条记录只跑 1 次，没有误差条【一手：verified.html 模板说明】。仓库里的 SWE-bench 配置是：最多 250 步，费用上限 3 美元，单条命令超时 60 秒【一手：`config/benchmarks/swebench.yaml`】。从 v1.17.1 到 v2.3.1，这份配置都把温度设为 0.0；2026-06-10 的 PR #861 去掉了这个默认值，随 v2.4.0 发布【一手：mini-swe-agent 仓库】。从 2025-11-18 起，向官方 Verified 榜提交新成绩要附 arXiv 报告，并且至少一位作者属于学术或研究机构【一手：SWE-bench/experiments README】。

榜上 Verified 的全部系统里最高是 79.2%，有两条：Live-SWE-agent 加 Claude Opus 4.5，以及另一个系统加同一模型【实测】。DeepSeek 在 Multilingual 榜上还有一条：mini 2.0.0a0 加 V3.2，59.0%，每题 $0.38【实测】。

表中最后两行是同一个 GPT-5 mini 模型，换了 mini 的大版本，解决率差了 3.6 个点。这和"1.x 与 2.x 不可比"的说法一致，但每条只跑了一次，分不清是版本的影响还是随机波动【实测 + 推断】。

### 6. DeepSeek V3.2 两条记录成本差 16 倍，原因是什么

| 项目 | v1.17.1 那条 | v2.0.0 (high) 那条 | 倍数 |
|---|---|---|---|
| 请求的模型与参数 | `deepseek/deepseek-reasoner`，温度 0.0，文本格式动作 | `deepseek/deepseek-v3.2`，`reasoning.effort=high`，温度 null，工具调用格式 | — |

| 输入 token 的缓存命中率（抽样） | 96.3% | 71.7% | — |
| 每百万 token 实付（抽样） | $0.044 | $0.183 | 4.1 |
| 抽样 10 题的成本比 | — | — | 18.5 |

出处：模型、参数、调用次数来自 experiments 仓库里两条记录的 metadata、逐题明细和轨迹【一手】，整理时用本地留存的文件重算过【实测】。v2.0.0 那条的 usage 字段里有 `is_byok`、`upstream_inference_cost`，这是 OpenRouter 的字段，所以判断它走的是 OpenRouter【推断】。

拆开来看：总输入量约 4.8 倍，乘以单价约 4.1 倍，约 20 倍；抽样实测是 18.5 倍，全量是 16 倍。所以这 16 倍来自 mini 版本和动作格式不同、走第三方供应商、缓存条件不同，**不是模型本身的成本差**【推断】。

两条记录逐题对比：两边都解出的有 275 题，只有旧版解出的 25 题，只有新版解出的 75 题【实测】。也就是说，总分差 10 个点，背后有 100 题的结果互相翻转。

另外，DeepSeek 官方价目页现在只列 V4.1-Flash 和 V4-Pro，V3.2 已经没法通过官方接口复现【一手：api-docs.deepseek.com 价目页，页面不显示日期】。

### 7. 改脚手架能带来多少提升，噪声有多大

先看固定模型、只改脚手架的公开记录。

SWE-agent 论文用 GPT-4 Turbo 在 SWE-bench Lite 上做了消融（消融指去掉或换掉某个部件再测一次，看它贡献多少）：完整设计 18.0%，只给 shell 11.0%，去掉编辑命令 10.3%【一手：arXiv 2405.15793】。

Agentless 不让模型自己决定步骤，而是走固定的"定位、修复、验证"流程：Lite 上 32.00%，每题 $0.70；同表里 SWE-agent 是 18.33%、每题 $2.53【一手：arXiv 2407.01489 表 1】。

Complexity Trap 只保留最近 10 轮的工具输出，更早的换成占位符：成本约降一半，例如 Qwen3-Coder 从 1.29 美元降到 0.61 美元；解决率从 53.4 到 54.8，落在置信区间内；每个配置只跑 1 次【一手：arXiv 2508.21433】。

Live-SWE-agent 在 mini 之上加了"让 agent 自己写工具"和"每步反思一句"：Claude Sonnet 4.5 从 70.6% 到 75.4%，Gemini 3 Pro 从 74.2% 到 77.4%；但小模型 GPT-5-Nano 从 44% 跌到 14%。全部是单次运行【一手：arXiv 2511.13646】。

SAGE 在 mini 之上加计划模块，提升 0.4 到 4.8 个点，单次运行【一手：arXiv 2511.05931】。

R2E-Gym 用验证器从 26 个候选补丁里挑一个，从 34.4% 提到 51.0%；26 个候选里至少有一个对的比例是 64.4%。不过多数题里只有不到 20% 的生成测试能区分补丁对错，而且它的模型是专门训练过的【一手：arXiv 2504.07164】。

再看噪声。On Randomness in Agentic Evals 在 Verified 上让 6 个配置各跑 10 次。单次解决率随运行不同，最多相差 2.2 到 6.0 个点（这是 10 次里的极差，标准差最多约 1.8 点）。温度设为 0 也不能消除波动，标准差约 1.0 到 1.8。轨迹在最初约 1% 的 token 内就会分叉【一手：arXiv 2602.07150 表 1】。

它的表 2 算了"要分辨某个差距，每组需要跑几次"，条件是标准差 1.5 点、显著性 p<0.05、检验功效 80%（**检验功效**指差距真实存在时，实验能检测出来的概率）。这个算法不是按题配对的算法：

| 要分辨的差距 | 每组需要的运行次数 |
|---|---|
| 1 个点 | 36 |
| 2 个点 | 9 |
| 5 个点 | 2 |

其他重复运行的数据如下。SWE-agent 同一配置跑 6 次，解决率 17.94±0.49，pass@6 为 32.67【一手：arXiv 2405.15793 附录 B.5】（**pass@k** 指跑 k 次里至少一次解出的比例）。《AI Agents That Matter》每个 agent 跑 5 次，用 t 分布给 95% 置信区间【一手：arXiv 2407.01502】。Complexity Trap 对 500 题做配对自助法（**配对自助法**是按题配对、反复重抽样来估计差距的置信区间），重抽 10,000 次【一手】。2609.33812 每个"agent、模型、接口"组合跑 52 次【一手】。

基础设施本身也会带来差异。Anthropic 实测，在 Terminal-Bench 2.0 上放宽容器资源限制，分数差 6 个点（p<0.01）；在 SWE-bench 上把内存放宽到 5 倍，只差 1.54 个点。他们建议，配置不一致时，3 个点以内的榜单差距要保持怀疑【一手：anthropic.com/engineering/infrastructure-noise】。HAL 提醒，供应商可能在同名接口背后悄悄换量化方式或权重【一手：arXiv 2510.11977】。

### 8. 成本、耗时在论文和榜单里怎么记，拿来干什么

SWE-agent 论文表 1 的"平均费用"只算**成功实例**：GPT-4 Turbo $1.59，Claude 3 Opus $2.59。论文给每题设了 4 美元上限；成功实例里 93.0% 在预算耗尽前结束，全部实例是 69.0%，以此论证"再加预算意义不大"。成功实例的步数中位数是 12 步，失败的平均 21 步。失败原因用 GPT-4o 分成九类，和人工标注一致率 87%，但只验证了 15 个实例【一手：arXiv 2405.15793 附录 B.3、B.4】。

Agentless 按阶段拆费用（定位 $0.02 到 $0.06，修复约 $0.22 到 $0.29，挑补丁 $0 到 $0.25），用来说明哪一步值得花钱；它没报方差【一手：arXiv 2407.01489 表 2 至 4】。

OpenHands 估算全量 2,294 题按每题 3 美元约 6.9k 美元，因此改用 Lite【一手：arXiv 2407.16741 第 4.2 节脚注】。

《AI Agents That Matter》主张成本和准确率一起报，画**帕累托前沿**（"没有别的方案在两项上都更好"的那条边界）；相近准确率下成本能差近两个数量级；成本要用美元和 token 计，不用参数量这类代理指标；它还指出很多基准没有留出集，也就是不参与调参的测试集【一手：arXiv 2407.01502 第 2、4、5 节】。

HAL 跑了 9 个基准、2.17 万次运行，约 4 万美元。它自动记录美元和 token，并按某一天的价格换算。最贵的模型只在 1 个基准上处于前沿；36 个组合里有 21 个"多推理没换来更高准确率"；同一基准的两种脚手架花费 171 美元对 1,577 美元，准确率只差约 2 个点。墙钟时间（实际经过的时间）不作为核心指标，因为并行运行时会被限流扭曲【一手：arXiv 2510.11977 第 3 至 5 节】。

SWE-Effi 发现"昂贵的失败"：SWE-agent 加 GPT-4o-mini 失败时约耗 880 万 token，成功时约 180 万。它还发现对话历史累积会让输入 token 随调用次数线性增长【一手：arXiv 2509.09853 第 5 节】。

另一篇论文发现，同一题不同次运行的 token 用量最多差 30 倍【只读到摘要：arXiv 2604.22750，【待验证】】。

SWE-bench 官方提交不要求报成本、token 或耗时，只要求预测结果、逐题日志和完整轨迹【一手：swebench.com/submit.html，experiments README】。

归纳起来，常被忽略的有三样：重复运行的方差、失败实例的花费、同一题多次运行的稳定性。这是子 agent 读完上述材料后的归纳，不是某篇原文的结论【推断】。

### 9. 多轮交互和系统属性的基准

**按评审意见修改。** 最接近的现成基准是 c-CRAB【一手：arXiv 2603.23448，github.com/c-CRAB-Benchmark】。它的构造过程是：从 671 个 PR、1,313 条评审评论出发，先用 LLM 筛出具体、可测的评论，再为每个 PR 建 Docker 环境，然后用 GPT-5.2 把评论转成"改之前失败、改之后通过"的测试，最后只保留 Claude Code（Sonnet 4.6）只看评论就能改对的题，得到 184 个 PR、234 个测试。它有三个问题：82.1% 的测试检查的是源码文本，而不是运行行为；人工抽检 50 题，一致率 84%；只保留 Claude Code 能做出的题，存在选择偏差。

2026 年还有几个多轮交互基准。SWE-Together 从 11,260 个真实会话里得到 109 题，用模型模拟用户来回放纠正【一手：arXiv 2606.29957】。UserSWE 有 72 题，发现轮次预算不同时模型排名会变，数据写的是"将发布"【一手：arXiv 2610.29822】。EvoCode-Bench 有 26 题、227 轮，多轮成绩比单轮低 22 到 40 个点【一手：arXiv 2605.24110】。

用历史 PR 评论构造评测有几个坑。评论噪声大：有研究抽查 270 条，36% 是噪声【一手：arXiv 2502.02757 第 IV-A 节】。人类评审本身会漏问题，所以召回率只是下界【一手：SWE-PRBench 局限一节】。产出率低：c-CRAB 最终保留不到 20%，SWE-Together 只有 0.97%。

**系统属性。**

可靠性：τ-bench 定义了 pass^k，即同一题跑 k 次**全部**成功的概率，每题至少跑 3 次。gpt-4o 在零售场景 pass^1 是 61.2%，pass^8 低于 25%【一手：arXiv 2406.12045 第 3 节】。

成本前沿：HAL 用成本和准确率的凸包表示，同时给 token 口径【一手】。

故障注入：ReliabilityBench 让每次工具调用按一定概率出故障（超时、断连、限流、部分响应等），但规模只有 20 个任务、k=2、2 个模型，结论很薄【一手：arXiv 2601.06112】。ToolMisuseBench 有 6,800 题，可确定地回放故障【只读到摘要，【待验证】】。

提示注入：AgentDojo 定义了三个指标，分别是无攻击时的效用、受攻击时的效用、定向攻击成功率【一手：arXiv 2406.13352 第 3.4 节】。IssueTrojanBench 把恶意指令藏进 issue 正文、评论、代码注释。它以 sympy 和 requests 各 3 个 issue 为种子，生成 696 个变体，跑了 4,176 次，总体 66.5% 的恶意指令被执行；实验机器是 16GB 内存的 Mac mini，数据在 Zenodo【一手：arXiv 2607.20759 表 III】。

沙箱逃逸：SandboxEscapeBench 有 18 个夺旗任务，每个"模型、任务"组合采样 5 次，用 Wilson 置信区间，需要虚拟机里再套容器【一手：arXiv 2603.02277】。

**小团队和个人的先例。** 以下作者规模和贡献类型都来自各论文署名与正文【一手】。

- Agentless：4 人，UIUC，卖点是更简单、更便宜。
- Complexity Trap：5 人，JetBrains Research 与 TUM，做受控分析，自己承认结论"可能不能推广"。
- Live-SWE-agent：5 人，UIUC，在 mini 上加了一个模块。
- PatchDiff：3 人，做测量批判。
- On Randomness：3 人，KTH，做方差研究。
- SWE-PRBench：1 名独立研究者，350 个 PR 的评审质量基准，已开源。
- ReliabilityBench：1 人，规模太小，是反例。
- mini-swe-agent 背后是 Princeton 和 Stanford 的 SWE-bench 团队，不算个人先例。

这些工作**没有一个靠"总分超过 OpenHands"立足**。它们比的都是对照组：自己重跑的 mini、去掉某个模块的自己、同一脚手架里的另一种策略【推断】。子 agent 没找到"个人项目靠可靠性、成本这类系统属性获得认可"的已核实案例【待验证】。

### 10. 成本估算（全部是推断）

估算用到的价格来自 DeepSeek 官方价目页（页面不显示日期）：deepseek-flash 缓存命中 $0.003、未命中 $0.15、输出 $0.60，单位是每百万 token，这是低峰价，高峰价翻倍；deepseek-v4-pro 对应为 $0.022、$0.66、$1.98【一手】。

第一轮子 agent 假设每题 89 次调用、每次约 2 万输入 token、150 输出 token，算出单题约 $0.03 到 $0.45（区间两端分别对应缓存命中 90% 和不命中）。按这个区间，50 题跑 3 次约 $4 到 $68，100 题跑 5 次约 $14 到 $225；基线和自己的系统两组要翻倍【推断】。

第二轮子 agent 改用 v1.17.1 抽样轨迹的实际 token 量（每题输入约 53 万、96% 命中缓存，输出约 4.8 万），按高峰价算：V4.1-Flash 约 $0.07/题，V4-Pro 约 $0.24/题，低峰减半【推断】。它也提醒，工具调用格式下 token 量实测是文本格式的 4.8 倍，新模型的 token 行为未知，所以估算误差可能达到几倍。

"一题约 15 分钟、4 并发跑 500 次约 30 小时"和"7.8GB 内存下并发 3 到 4"这两条，都是子 agent 自己的估计，没有任何出处【待验证】。

## 四、各数据集、各基准：借鉴什么，不借鉴什么

**SWE-bench Verified。** 可以借鉴的是它的可比性：它是现在公开成绩最多的集合，官方评分器成熟，也有 bash-only 榜可以对照。它的问题也很明确：仓库全来自 2023 年或更早，有证据表明前沿模型能背出部分补丁，测试也有缺陷。所以它的绝对分数不能当"真实能力"来讲，只适合比较"同一模型下 A 方案和 B 方案的差距"，而且要自己重跑、多次运行、报区间【推断，依据见第三节第 2、7 小节】。它还能不能当最终评测集，由用户决定（见第五节）。

**"test 扣掉 Verified"。** 它可以作为开发数据用，因为题号不重叠，符合用户的规则。需要知道它的局限：它和 Verified 是同一批仓库，只防住了题目层面的污染，防不住仓库层面的污染；而且它是"挑剩下"的题，坏题比例可能更高【推断】。官方项目里没找到把它当开发集的公开做法。

**SWE-bench 自己的 dev 划分（225 题、6 个其他仓库）。** 它在仓库层面比"test 扣掉 Verified"更干净；SWE-agent 论文在设计界面时就是从 dev 里手选例子做定性分析，文档里批量运行的示例也用 Lite 的 dev【一手：arXiv 2405.15793，swe-agent.com 批量模式文档】。缺点是题少，噪声大。建议把它列为开发阶段的候选，最终由用户定。

**Verified Mini 和 Lite。** 题少、镜像小，适合调试。但不能用它来在方案之间做选择，因为 50 题的噪声太大；也不能先拿它调参、再拿它出最终报告【推断】。另外，Verified Mini 是从 Verified 里抽的，按用户的规则，开发阶段**不能用**。

**SWE-bench Pro。** 它的结构值得借鉴：公开集、保留集、商业集三层，私有仓库只公布结果、不公开数据，这和用户"私有仓库只做实验、不公开数字"的规则是同一个思路。但它本身不建议当首选：OpenAI 审计认为公开集约 30% 是坏题，已经撤回推荐；它对资源的要求也没写清楚。

**SWE-rebench 和 SWE-bench-Live。** 借鉴的是"按日期切分防污染"：只用模型发布之后才创建的题。SWE-rebench 排行榜的评测方法（统一脚手架、每个模型跑 5 次、报标准误和 pass@5、标注潜在污染）是个人项目最该参照的模板。它们的局限是：SWE-rebench 的题窗口会滚动，不好做长期固定的比较；SWE-bench-Live 有 8 个仓库和 SWE-bench 重叠；两者都要自己处理镜像。这两个是"时间切分评测集"的候选，用不用由用户定。

**SWE-Gym、SWE-smith。** 不借鉴。它们是训练数据，不是干净的评测集；RepoAegis 不训练模型，用不上。SWE-smith"人造 bug 加模型写 issue"的造题方法，可以留作以后自建回归任务时的参考【推断】。

**Multilingual。** 暂不借鉴。它没有预构建镜像，官方只测过一个模型，环境要自己搭，成本高。

**用小型开源仓库自建测试集。** SWE-rebench、SWE-bench-Live 都是从 GitHub 自动挖仓库，它们的筛选条件可以照搬：许可宽松、PR 只关联一个 issue、PR 同时改了测试和非测试代码、改动 1 到 15 个文件等。但三者都没有"小仓库"标准，也没找到专门以小仓库为目标的数据集【一手：两篇论文的数据构造章节】。自建的代价也已经有数据：SWE-rebench 只有 31% 的仓库能生成可用的安装脚本，测试不稳定（依赖外部 API、浮点数要求精确相等）。

**bash-only 榜单和 mini-swe-agent。** 借鉴的是"同模型、同最简脚手架"的对照思路：在同一台机器上，用同一个 DeepSeek 模型重跑 mini，作为基线。不借鉴的是榜上的现成数字：mini 的版本、动作格式、供应商、缓存都会让成本和分数差很多（第三节第 5、6 小节），而且 V3.2 已经无法通过官方接口复现。重跑时要对齐这些条件：模型名和实际生效的版本、供应商、mini 的大版本、步数和费用上限、命令超时、采样参数、数据集版本、容器资源。

**成本和耗时的记法。** 借鉴 HAL 和《AI Agents That Matter》：token 分输入、缓存命中、输出三类记录，因为价格会变，只有 token 能拿来重算费用；美元成本只在比较性价比时换算，并注明价格日期。借鉴 SWE-Effi 和 SWE-agent：失败实例的花费也要算，不能只算成功的。不借鉴把墙钟时间当核心指标的做法，因为并行运行时会被限流扭曲（HAL）。

**统计方法。** 借鉴 On Randomness 的功效分析和"报方差，而不是单个数"；借鉴 Complexity Trap 的按题配对、配对自助法求置信区间。不借鉴论文里普遍的单次运行，比如 Live-SWE-agent、SAGE 的正收益都是单次运行，可能有发表偏差。

**c-CRAB 和多轮交互基准。** 它们针对的是"按评论继续修改"。RepoAegis 现在的定位是"每个 issue 只处理一次，PR 之后的事交给人"，这一步已经不在产品范围里，所以暂不借鉴。如果以后范围变了，c-CRAB 的 184 题规模在个人预算内，但要先处理它偏向 Claude Code 能解的题这一选择偏差【推断】。

**系统属性类基准。** 可以借鉴它们的度量定义：τ-bench 的 pass^k、AgentDojo 的三个指标、IssueTrojanBench 的注入方式（把指令藏进 issue 和评论，正好对应 RepoAegis 的输入来源）。有两处要注意。一是 IssueTrojanBench 的种子来自 sympy 和 requests，这两个仓库都在 SWE-bench 的 test 里；它的种子 issue 和 Verified 的题号是否重叠，没查过，用之前要按用户规则核对。二是 ReliabilityBench 规模太小，只借定义，不借它的结论。沙箱逃逸评测需要嵌套虚拟化，WSL2 能不能跑没查。

**三条评测路线（第二轮子 agent 整理，用户还没选）。**

- 路线 A：同模型受控对照。数据用时间切分集里晚于模型发布的题；和同模型、同预算的 mini 以及去掉某个模块的自己比；指标是解决率的均值与标准误、pass^k、每题成本；每个配置至少跑 3 次，想分辨 2 个点要约 9 次；按 Flash 估约 $130（300 题 × 3 次 × 2 组）【推断】。
- 路线 B：按评论修改，用 c-CRAB。在现在的范围下已经不适用。
- 路线 C：平台层的系统属性。比较同一个 agent"带平台层"和"裸跑"在故障注入、提示注入下的差别。风险是没有大项目的同口径数字可以对照，故障和攻击怎么设计由自己决定，容易被质疑挑了对自己有利的条件。

三条路线都需要先在 WSL 里装 Docker。

## 五、据此的决定

**数据集规则（用户 2026-10-14 定下，10-16 澄清）。** Verified 只用于最终评测。其他 SWE 数据都可以用于开发和实验，包括 test 扣掉 Verified、dev、train、Multilingual 等，前提是实例编号和 Verified 不重叠。用任何 SWE 数据之前，先拿 Verified 的编号清单核对并排除重叠；Verified 的题号和题目内容不进提示词、测试或调参依据。

**产品做完之前不跑基线。** 基线是成品的成绩，什么时候算做完由用户决定。验证某个环节能不能跑通，可以跑几道题，但不叫基线（见 [项目边界](../项目边界.md) 第八节）。

**不和大团队的产品比总分。** 要比，就和同一模型、同一预算下自己重跑的基线比，并多次重复（同上）。

**指标要有用途才记录（用户 2026-10-23 的原话归纳）。** 每项指标写明它支撑哪个决定。要比较性价比时，才记具体模型的系列、版本、当日价格；同时要关注不同运行之间的方差，以及各家模型不同的采样参数。

**待用户决定。** Verified 是否还适合当最终评测集，要考虑 OpenAI 的审计和 Epoch 的评级。开发阶段用哪套数据：dev、test 扣掉 Verified，还是时间切分集。走哪条评测路线。是否在 WSL 里装 Docker。
