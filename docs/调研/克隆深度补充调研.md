先解释三个词：
- 浅克隆：`git clone --depth 1`，只下载最新的一个提交。
- 浅克隆边界：浅克隆里"最老的那个提交"。git 假装它没有父提交，历史到它为止。
- 部分克隆：`git clone --filter=blob:none`，提交记录全下载，但文件内容（git 里叫 blob）先不下载，用到哪个再临时去 GitHub 拉。

## 1. 有没有"能看历史 vs 不能看历史"的消融实验

消融实验的意思是：其他条件不变，只去掉某一样东西，看效果差多少。

### 1.1 找到的、能读到原文数字的三项

**Code Researcher（微软，arXiv 2506.11060）**——这是本次新找到的、最直接的一项。
- 【一手】它给 agent 一个专门的工具 `search_commits(regex)`：用正则表达式搜过去提交的说明文字和改动内容（第 3 节；附录 B 说底层就是 `git log -E --grep` 和 `git log -E -G`，每次最多返回 5 个提交、每个截断到 100 行）。
- 【一手】消融在第 5.4 节和附录 A 表 3：模型 GPT-4o，Pass@5（跑 5 次有一次成功就算成功），每次最多 15 步。去掉 `search_commits` 后，崩溃解决率从 48.00% 降到 38.00%，正确改到"应该改的文件"的比例也明显下降。原文结论："the search_commits action plays a crucial role in context gathering and localization"。
- 【一手】重要限制：这个消融**只在 96 个 bug 上做**，而这 96 个正是完整版本来就解出来的（原文："only on the 96 bugs resolved by Code Researcher"）。题目是 Linux 内核崩溃（kBenchSyz），不是普通 issue。所有工具在"修复提交的父提交"上运行（第 4 节）。论文没写是否删除了未来的提交。
- 【推断】在"本来就解出来的题"上做消融，挑题方式偏向有利于完整版；完整版在这 96 题上重跑也只有 48%，说明每次运行的波动很大。Linux 内核的提交说明非常规范（常带 "Fixes:" 标签），这种仓库历史最有用，结论不能直接推到一般仓库。
- 出处：https://arxiv.org/html/2506.11060 第 5.4 节、附录 A 表 3、附录 B

**RepoMem（arXiv 2510.01003）**——上一篇已写：框架整理好的提交检索工具，SWE-bench Verified 上 37.0% → 40.4%（GPT-4o），历史少的仓库反而下降。

**HAFixAgent（arXiv 2511.01047，v4，2026-10-08；作者 Yu Shi、Hao Li、Bram Adams、Ahmed E. Hassan）**——HAFix 的 agent 版本，本次新找到。
- 【一手】基于 mini-swe-agent。框架先对出错行跑 `git blame`，把找到的那个提交的信息整理好放进提示词；agent 自己的工具只有 grep、sed、find 等，没有 git（第 4.3 节）。**出错行是直接告诉 agent 的**（第 5.3 节）。
- 【一手】表 1a，模型 DeepSeek-V3.2-Exp：不带历史 Defects4J 522 / 854、BugsInPy 373 / 501；最好的单一历史方案 545 和 377，只多了 4.4% 和 1.1%。第 6.1.3 节明说**不显著**（McNemar 检验 p=0.12 和 p=0.79）。只有"三种方案任取一个成功就算"的组合（论文自己叫 oracle upper bound，即理想上限）才显著。
- 【一手】小模型提升大得多：Qwen3-Coder-Next 在 Defects4J 上 129 → 212，Devstral-Small-2 218 → 330（表 1b、1c）。
- 【一手】论文没在 SWE-bench 上测，第 8 节说那是以后的工作。
- 出处：https://arxiv.org/html/2511.01047 第 4.3、5.3、6.1.3 节，表 1

### 1.2 SWE-bench 修复 #465 前后的分数变化

- 【一手】#465 里，SWE-bench 维护者 klieret 2025-09-15 说：Claude Opus 有 6 条"可疑的成功轨迹"，相当于 1.2 个百分点，前 4 名排名不变。这说的是**偷看未来提交**带来的分数，不是"看过去的历史有没有用"。
  出处：https://github.com/SWE-bench/SWE-bench/issues/465 （klieret 2025-09-11 评论中 9/15 的更新）
- 【一手】修复后的 Verified 镜像**保留了全部过去的历史**，只删未来的。维护者 closji 的理由："This should reflect the most realistic setting for agents."（2025-09-11）
- 【推断】所以 SWE-bench 上各家的成绩，从来都是"有完整过去历史"条件下测的，没有"没历史"的对照组。修复前后的变化只能说明"未来提交"有多少作弊价值，回答不了我们的问题。
- 【找不到】没找到任何一家公布"修复前后自家分数变化"的正式说明。

### 1.3 其他找过但没有相关消融的

- 【一手】NVIDIA 的 "Shortcutting the Fix"（arXiv 2609.06780，2026-09-06）：研究 agent 在评测里抄答案。它把"查看 base commit 及其祖先"明确算作正当行为（第 2.2 节："Benign Git commands, such as inspecting the base commit and its ancestors, are permitted"）。它只比较了两种提示词，没有比较"有历史 vs 没历史"的解决率。
- 【一手】"Understanding Software Engineering Agents"（Bouzenia & Pradel，arXiv 2506.18824）：按"探索、定位、搜索、修复"等八类统计 agent 动作，没有单独统计 git 命令。
- 【一手】SWE-agent（2405.15793）、AutoCodeRover（2404.05427）、Agentless（2407.01489）、OpenHands（2407.16741）四篇论文：我把 PDF 转成文字后搜 "git log / git blame / commit history / shallow"，**都没有**（Agentless 只在参考文献里引了一篇 2014 年的老论文）。Aider、Moatless 没有论文。
- 【找不到】没找到任何一篇论文比较"同一个 agent，仓库有完整历史、可以自己随便跑 `git log` / `git blame`"和"浅克隆没历史"的解决率。

### 1.4 小结

现有的正面数据，全部是"**框架专门做了一个查提交的工具**（或者框架先查好塞进提示词）"带来的提升，而且条件都很特殊：内核崩溃、已知出错行、旧模型、只在解出的题上消融。没有一项是"只是换成完整克隆，让 agent 自己看着办"。反过来，#465 里维护者在约 10000 条轨迹里只找到 5 条用了 `git log`（上一篇已写），说明 agent 很少主动去查。

## 2. Copilot cloud agent 把 `fetch-depth` 覆盖成多少

- 【一手】官方文档原话：你设的 `fetch-depth` 会被覆盖，"to allow the agent to rollback commits upon request"，同时降低安全风险。具体数字文档没写。
  出处：github/docs 仓库 `content/copilot/how-tos/copilot-on-github/customize-copilot/customize-cloud-agent/customize-the-agent-environment.md` 第 97 行
- 【一手，社区用户贴的运行日志】GitHub 社区讨论 #163397（"Copilot Coding Agent session overwrites custom actions/checkout options silently"）：
  - 用户 pheu（2025-10-14）："silently being changed to `fetch-depth: 2`"。
  - 用户 AdamVig（2025-11-03）贴了 agent 运行日志，`actions/checkout@v5` 的实际参数是 `fetch-depth: 2`、`persist-credentials: false`；他还说即使自己写了 `persist-credentials: true` 也被改掉。
  - 发帖人 darcien（2025-06-19）的需求正是"需要在 agent 里看到其他分支"，他的绕法是在 setup 步骤里用 `GITHUB_TOKEN` 手动 `git fetch origin main:main`。
  - 用户 stevoland（2025-09-04）说：以前 agent 能帮忙解合并冲突，现在 agent 回复说它拿不到 master 分支、没法 fetch。
  出处：https://github.com/orgs/community/discussions/163397
- 【推断】`fetch-depth: 2` 就是"当前提交加它的父提交"。文档说的"能回滚提交"大概就是指这个：agent 至少能看到上一个提交。这说明 GitHub 自家产品**主动选了浅克隆**，而且是强制的，用户改不了。
- 【一手】旁证：同一文档库里，Copilot CLI 在 Actions 中的两个示例，深度跟着任务走——要 `git show HEAD` 看本次改动的设 `fetch-depth: 2`（`use-copilot-cli-in-actions.md` 第 54、65 行）；任务本身就是"总结今天的 git log"的设 `fetch-depth: 0`（`automate-with-actions.md` 第 58 行附近）。claude-code-action 的示例也一样：修 issue 的 `examples/claude.yml` 用 1，做 issue 分类的 `examples/issue-triage.yml` 和修 CI 失败的 `examples/ci-failure-auto-fix.yml` 用 0。
  【推断】官方的习惯是：任务本身就要读历史时才拉全量；修代码默认浅。

## 3. 浅克隆之后按需补历史

### 3.1 git 官方文档怎么说（git-scm.com，页面标注 2.56.0 版）

- 【一手】`git fetch --depth=<n>`：从每个远程分支的最新提交往回数 n 个；对已有的浅克隆，用它来加深或缩短。加深出来的那些提交上的 tag 不会一起拉下来。
- 【一手】`git fetch --deepen=<n>`：和 `--depth` 类似，但是"number of commits from the current shallow boundary"，即从现在的边界再往回补 n 个。
- 【一手】`git fetch --shallow-since=<date>`：把浅克隆加深或缩短到"include all reachable commits after <date>"。
- 【一手】`git fetch --unshallow`：如果远程仓库是完整的，就把浅克隆变成完整克隆。
  出处：https://git-scm.com/docs/git-fetch （OPTIONS 一节）
- 【一手】`git clone --depth=<n>`："Implies --single-branch unless --no-single-branch is given"，也就是浅克隆默认**只拿一个分支**。`--filter=blob:none` 会先不下载所有文件内容，"until needed by Git"。
  出处：https://git-scm.com/docs/git-clone
- 【一手】git 术语表对浅克隆的定义：有些提交的父提交被"砍掉"了，"Git is told to pretend that these commits do not have the parents"。可以之后用 git fetch 加深。
  出处：https://git-scm.com/docs/gitglossary 的 "shallow repository" 条目
- 【一手】`git blame` 的文档**没有提到浅克隆**。它只说：被当作"边界"的提交在输出里前面带 `^`；`-b` 选项会把边界提交的编号显示成空白；`--root` 是"Do not treat root commits as boundaries"。
  出处：https://git-scm.com/docs/git-blame （OPTIONS 里的 `-b`、`--root`、`--abbrev`）
- 【推断】把这两条拼起来：浅克隆边界在 git 眼里就是一个"没有父提交"的根提交，所以 blame 会把边界之前写的所有行都算到边界提交头上，并打上 `^`。文档没直接写这句，下面的实测证实了。

### 3.2 实测（WSL，git 2.53.0，仓库 pallets/markupsafe，共 869 个提交，有 `main` 和 `stable` 两个分支）

脚本放在 WSL 的 `~/scratch/clone-depth/exp.sh`，对文件 `src/markupsafe/__init__.py`（389 行）跑 `git blame`，数一下有多少行前面带 `^`。

【实测】结果如下（时间受本机到 GitHub 的网络影响，只看量级）：

```
A. git clone --depth 1                    耗时 2.0s  .git 296K  提交数 1
   blame: 389 行里 389 行带 ^（全部算到最新那个提交头上）
   ^4e11127 (David Lord 2026-10-02 ...   1) from __future__ import annotations
   git log 只有一条：4e11127 2026-10-02 update dependencies
B. git fetch --deepen=20                  耗时 3.9s  .git 672K  提交数 78
   blame: 360 行带 ^
C. git fetch --shallow-since=2023-01-01   耗时 3.9s  .git 1.1M  提交数 331
   blame: 153 行带 ^
D. 接着 git fetch --unshallow             失败：
   fatal: error in object: unshallow 7b72ed9d...
F. git clone --filter=blob:none           耗时 4.5s  .git 1008K 提交数 869
   git log -- <文件>：没有触发临时下载
   git blame <文件>：触发了 97 次临时下载，第一次跑耗时 1 分 47 秒
G. 完整克隆                               耗时 2.7s  .git 1.6M  提交数 869
   同一个 blame 耗时 0.013 秒
```

另外几次单独验证：
- 【实测】新的 `--depth 1` 克隆直接 `git fetch --unshallow`：成功，变成 869 个提交。此时 blame 仍有 37 行带 `^`，那是仓库真正的第一个提交（根提交）写的行，属于正常现象。
- 【实测】`--depth 1` 后先 `--deepen=20` 再 `--deepen=200`：已经补全到 869 个提交。这时再跑 `--unshallow` 会报错 "--unshallow on a complete repository does not make sense"，退出码 128。
- 【实测】D 步的失败能复现：新克隆 → `--shallow-since=2023-01-01` → `--unshallow`，同样报错；改用 `--depth=2147483647` 也报同样的错。检查发现 `.git/shallow` 里记了 8 个边界提交，其中 3 个本地根本没有。
  【待验证】原因没查清。网上搜到 2018 年 git 的一个相关补丁（`.git/shallow` 里记着本地已不存在的提交，下次加深就会报这个错），但没找到和 `--shallow-since` 直接相关的报告。结论只是：在这个版本上，`--shallow-since` 之后再加深可能会坏，用 `--deepen` 更稳。
- 【实测】`--depth 1` 克隆后，`remote.origin.fetch` 被设成只拿 `main`（`+refs/heads/main:refs/remotes/origin/main`），`git branch -r` 看不到 `stable`。手动 `git fetch --depth 1 origin stable:refs/remotes/origin/stable` 可以拿到；`git diff main origin/stable` 能比较文件差异；但 `git merge-base main origin/stable` **失败**，因为两边都只有一个提交，找不到共同祖先。

要点：
- 浅克隆下，blame 的结果不是"查不到"，而是**看起来正常但内容是错的**：所有旧行都显示成最新提交的作者和日期，只有一个 `^` 提示。agent 如果不知道这个规则，会被误导。
- 部分克隆在克隆时只比完整克隆多花一点，但 blame 时每个历史版本的文件都要单独联网下载，在这台机器上慢了几千倍。对 agent 来说，这是最差的组合。

### 3.3 有没有官方 agent 用"按需加深"

- 【一手】claude-code-action 的 `src/github/operations/fetch-depth.ts`（第 3–18 行注释）：拉基础分支时，如果当前是浅克隆，就继续用 `--depth`；如果已经是完整克隆，就**不加** `--depth`，因为对完整仓库加 `--depth` 会把已有历史截掉、丢掉和基础分支的共同祖先。它不会替 agent 加深。
- 【一手】OpenHands software-agent-sdk 的 `openhands-sdk/openhands/sdk/git/cached_repo.py` 第 587–591 行有 `--unshallow`，但这个文件开头说明它只用于缓存技能和插件仓库，不是 agent 干活的仓库。
- 【一手】OpenHands extensions 的 issue-to-pr 手动版 `scripts/main.py` 第 558–586 行：`--depth 1 --single-branch`，注释原文 "the agent needs the tree, not the history"；同时把 `core.pager` 设成 `cat`，注释说 agent 也会在这个克隆里跑 `git log`（防止翻页卡住）。也就是说 agent 能跑，但只有一条历史。
- 【一手】**更正上一篇**：OpenHands extensions 里推荐的新版 `scripts/worker.py` 第 14–34 行，不是框架替 agent 克隆，而是在提示词里让 agent 自己跑 `gh repo clone <仓库>`，没有加 `--depth`。`gh repo clone` 的手册说额外的 git 参数要写在 `--` 后面，示例是 `-- --depth=1`（https://cli.github.com/manual/gh_repo_clone ）。
  【推断】所以新版实际是**完整克隆**。上一篇把"OpenHands 新版 issue-to-pr"归为浅克隆，指的其实是手动版 `main.py`，这里纠正。（读的是 OpenHands/extensions 提交 2604706，2026-10-23。）
- 【一手】Codex cloud（旧版文档 "Codex Cloud (Legacy)"）：容器"checks out your repo at the selected branch or commit SHA"，没写深度；agent 运行阶段默认断网。
  出处：https://learn.chatgpt.com/docs/environments/cloud-environment
  【推断】断网时 agent 想加深也加深不了。按需加深要求 agent 运行时能连 GitHub、并且有读仓库的权限。
- 【找不到】没找到任何官方 agent 在提示词或工具里教 agent "历史不够时自己 `git fetch --deepen`"。

## 结论

**按你的规则（有"带历史效果更好"的数据才完整克隆，否则浅克隆），应选浅克隆。** 依据：

1. 没有找到"完整克隆、让 agent 自己用 git"比"浅克隆"解决率更高的数据。现有的三项正面数据（Code Researcher、RepoMem、HAFixAgent），测的都是"框架专门做的查提交工具"或"框架先查好塞给模型"，不是克隆深度本身；而且分别有"只在解出的题上做消融""历史少的仓库反而变差""强模型上不显著"的限制。
2. agent 很少主动查历史：SWE-bench 环境一直保留完整的过去历史，维护者在约 10000 条轨迹里只找到 5 条 `git log`（上一篇已写）。
3. 官方产品的选择一致偏浅：Copilot 强制 `fetch-depth: 2`（社区日志），claude-code-action 示例用 1，OpenHands 手动版用 1；只有"任务本身就是读历史"（总结 git log、修 CI、分类 issue）的示例才用 0。例外是 OpenHands 新版 worker，让 agent 自己 `gh repo clone`，默认是完整克隆，文档没解释原因。

需要你判断的一点：Code Researcher 和 RepoMem 证明的是"**专门的查提交工具**有用"（尤其在提交说明规范、历史丰富的仓库）。如果你认为这也算"带历史效果更好的数据"，那它支持的是"浅克隆 + 以后另做一个查提交工具"，而不是"直接完整克隆"。这由你拍板。

另外，`--filter=blob:none` 不建议用：实测克隆不省多少，blame 却慢了几千倍。

**"按需加深"技术上可行，但有坑**，目前没有官方 agent 这么做：
- 可行：实测 `--depth 1` 后 `git fetch --deepen=N` 或 `--unshallow` 都能补上历史，小仓库几秒钟。
- 前提：agent 运行时必须能连 GitHub、有读仓库的权限。GitHub Actions 里默认能做到，但这和"agent 在隔离环境里、不带凭据"的安全要求有冲突，需要你决定是否给 agent 只读凭据，或者由框架替它加深。
- 坑 1：浅克隆下 blame 不报错，只是把所有旧行算到边界提交头上，前面带 `^`。如果提示词里不讲清楚，agent 会被误导。
- 坑 2：实测 `--shallow-since` 之后再加深会失败（原因【待验证】），用 `--deepen` 更稳。
- 坑 3：对已经完整的仓库跑 `--unshallow` 会以退出码 128 报错，要先用 `git rev-parse --is-shallow-repository` 判断。
- 坑 4：浅克隆默认只拿一个分支。要看别的分支，必须显式 `git fetch origin <分支>:refs/remotes/origin/<分支>`；两边都浅时 `git merge-base` 找不到共同祖先。

**关于其他分支**：没有官方 agent 教 agent 自己去看别的分支。现有做法是"人事先指定基础分支"（Copilot 按 issue 选，其他按工作流固定）；回移到 release 分支，是维护者给自己仓库写技能文件、人在本地交互着用。
