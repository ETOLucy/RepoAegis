# 调研报告：产出检查的规则

> 调研日期：2026-10-30。三个子 agent 分头读源码和官方文档，主对话抽查了关键出处（下文标"已抽查"的）。每条事实标【一手】（附出处位置）、【推断】或【待验证】；子 agent 报告里没被抽查的一手条目，是它们读原文后的转述，主对话没有逐条复核。

## 一、为什么查

agent 交卷时交两样东西：一个补丁（`git diff --binary`，含新文件、删除、二进制）和一份五个字段的汇报（`title`、`summary`、`testing`、`assumptions`、`skipped_requests`），汇报由程序填进草稿 PR 描述或 issue 评论的模板（见 [交卷工具](交卷工具.md)）。[安全设计](../安全设计.md)"发布前检查产出"一节已定：发布前由一个不拿任何密钥的作业检查补丁和汇报，不合规就不发布；目标仓库可能是公开的，PR 一开出来所有人都能看见，所以不能指望人审兜底。

submit 已经写好，它在第一次调用时会用同一套规则先查一遍，把问题提醒给 agent；规则本身一直没定。要定六件事：哪些文件算受保护、碰了怎么办、补丁大小上限、补丁里还有哪些危险改动、什么算"像密钥"、汇报文字怎么清洗。

## 三、各家做法

### gh-aw：最完整的一套

**受保护文件。** 名单写在 Go 编译器里，编译时写进运行配置，运行时由 JS 判断【一手 `pkg/workflow/runtime_definitions.go:38-174, 209-217`；`actions/setup/js/manifest_file_helpers.cjs`】。由四部分组成：

- 依赖清单和锁文件，按文件名匹配、任意深度：JS/TS 的 `package.json`、各种 lock 文件、`deno.json`；.NET 的 `global.json`、`NuGet.Config`；Go 的 `go.mod`、`go.sum`；Java 的 `pom.xml`、`build.gradle` 系列；Python 的 `requirements.txt`、`Pipfile`、`Pipfile.lock`、`pyproject.toml`、`setup.py`、`setup.cfg`、`uv.lock`；Ruby 的 `Gemfile` 系列；还有 Elixir、Haskell 的几个。
- 仓库治理文件，同样按文件名：`CODEOWNERS`、`DESIGN.md`、`README.md`、`CONTRIBUTING.md`、`SECURITY.md`、`CODE_OF_CONDUCT.md`、`CHANGELOG.md`（已抽查）。源码注释给 README.md 的理由是"agent 常把它当上下文读"。CHANGELOG.md 在名单里，但开 PR 时默认被排除。
- agent 指令文件，看用哪个模型引擎：Claude 是 `CLAUDE.md`、`AGENTS.md`、`.claude/`；Codex 是 `AGENTS.md`、`.codex/`；Gemini 是 `GEMINI.md`、`AGENTS.md`、`.gemini/`。
- 顶层点目录：路径第一段以 `.` 开头、文件在这个目录里面，就受保护，`.github/`、`.husky/`、`.githooks/` 都靠这条；仓库根目录的单个点文件（`.env`、`.gitattributes`）不算（已抽查 `manifest_file_helpers.cjs:203-214`）。

匹配方式：文件名精确比较、区分大小写；目录按路径前缀；改名时新旧路径都查；`diff --git` 头解析不了就拒绝整个补丁；补丁应用后再用 `git diff --name-only --no-renames` 取实际改动的文件重查一遍。

碰了受保护文件的处理有四种，默认是 `request-review`：照样开 PR，在描述顶部插一段 CAUTION 提示列出这些文件，再提交一个"要求修改"的审查。另外三种是 `fallback-to-issue`（推分支但不开 PR，改开一个附"创建 PR"链接的 issue）、`blocked`（直接报错不发布，不认识的策略值也按它处理）、`allowed`（不限制）【一手 `safe_outputs_handler_registry_pull_requests.go:328-333`；`create_pull_request.cjs:1354, 1560-1566, 2663-2727`】。

**补丁大小。** 文件数默认最多 100，按 `diff --git` 头数不重复路径，解析不了的头各算一个，宁多不少；超了默认改开 issue。大小默认最多 4096 KB，超了直接报错【一手 `create_pull_request.cjs:467, 509-559, 716, 1221-1272, 1315-1340`】。

**符号链接、可执行位、子模块、二进制。** 补丁规则检查里都没有。只在"签名提交推送"这一步处理：符号链接（git 记作 120000）和子模块（160000）拒绝推送；可执行位（100755）只警告、权限丢掉；二进制没有专门检查【一手 `push_signed_commits.cjs:698-800`】。

**按格式找密钥：只打码，不拦。** 内置约 15 条正则：GitHub 各类令牌（新格式的 `ghs_` 已经允许带点）、Azure、Google、AWS `AKIA`、OpenAI、Anthropic、Linear、Grafana；命中就替换成 `***REDACTED***`，在上传工件前对补丁和输出文件执行（已抽查 `redact_secrets.cjs:162-197`）。另有一步按工作流里真实用到的密钥值精确替换（之前的调研）。

**威胁检测。** 只要配置了发布动作就默认开启：让模型读 agent 的输出和补丁，判断提示注入、密钥泄露、恶意补丁三类问题。默认是"警告"模式，查出问题也照样开 PR，只加 CAUTION 标注和"要求修改"的审查；只有设成严格模式才整个不发布【一手 `pkg/workflow/threat_detection_config.go:36-38`；`docs/.../safe-outputs-specification.md:5607-5650`】。默认用的外部程序 `gh-aw-threat-detection` 的提示词不在仓库里【待验证】。

**文字清洗。** 按执行顺序【一手 `sanitize_content_core.cjs:1646-1722`、`sanitize_content.cjs:79-180`】：

1. Unicode：NFC 规范化，解码 HTML 实体，删零宽字符、软连字符、BOM、Unicode 标签字符、文字方向控制符；**全角字符 U+FF01–FF5E 一律转成半角**（已抽查 `:1552-1558`）；NFKC 规范化；把长得像拉丁字母的西里尔、希腊字母换成拉丁字母；反复做到不再变化。
2. 删 ANSI 转义和控制字符，保留换行和制表。
3. 删 HTML 注释（代码块里的不动）。
4. HTML 标签按白名单保留，删 `on*`、`style`、`title`、`data-*` 属性；不在白名单的标签改写掉。
5. URL：去掉 `用户名:密码@`；非 https 的协议替换成 `(域名/redacted)`；`javascript:`、`data:` 等替换成 `(redacted)`；https 链接按域名白名单过滤，默认只有 GitHub 自己的几个域名，编译后的工作流再加上防火墙放行的域名；默认连代码块里的也处理。
6. `@提及` 包进反引号，渲染后不通知（已抽查 `:632-645`）。PR 标题里全部中和；PR 描述里默认保留触发事件相关的人（对 issue 事件就是作者和被指派人），最多 50 个，所以**描述里 @issue 作者会真的通知到**。
7. "fixes #N" 这类关闭关键字：前 10 个保留，之后的包进反引号；描述里没有关闭关键字时自动加 `- Fixes #N`。
8. 模板符号 `{{`、`${` 等加反斜杠；修补没闭合的代码围栏；长度上限：标题 128 字符，描述 65000 字符。

### claude-code-action：只清洗、只打码

清洗函数依次：删 HTML 注释，删零宽字符、控制字符、软连字符、文字方向控制符，清空图片的替代文字，删链接的悬停标题，删 HTML 标签上的 `alt`、`title`、`aria-label`、`data-*`、`placeholder` 属性，把字符编码 `&#...;` 中可见的还原、其余删掉，最后抹掉 GitHub 令牌【一手 `src/github/utils/sanitizer.ts:1-77, 161`】。`redactSecrets` 认五类格式：GitHub 令牌（前缀后 36 位，`github_pat_` 后 11–221 位）、`sk-ant-`、AWS `AKIA`/`ASIA`、Slack `xox?-`、JWT（已抽查 `:86-100`）。没有处理 `@提及`，没有任何按路径或内容检查推送的代码；只限制推送命令本身的参数，防止借推送参数执行命令。改不了工作流文件，是因为它的 GitHub App 没有这个权限【一手 `docs/faq.md`】。

### Copilot cloud agent：靠流程兜底，不限文件

官方文档没有任何文件或路径限制，`.github/workflows` 也能改。兜底靠：只能推到 `copilot/` 开头的分支、只开草稿 PR、受分支保护约束、推送后工作流默认要人点批准才跑【一手 `content/copilot/concepts/security-governance-and-network-settings/risks-and-mitigations.md:36-42`】。CodeQL、密钥扫描、新依赖的漏洞比对默认开启，原文说发现问题后它会"尝试修掉"【一手 同文件 21–30 行】；这说明是反馈给 agent 自己改，不是发布前的硬拦截【推断】。

### OpenHands、SWE-agent、mini-swe-agent、codex-action：没有产出检查

OpenHands 旧 resolver 直接 `git add .` 后开 PR，正文原样拼上 agent 写的说明，令牌还要求带 workflows 权限【一手 `openhands/resolver/send_pull_request.py:213, 229, 383-387`；`README.md:16`】。SWE-agent 补丁不检查，开 PR 前只查 issue 的状态，正文固定写 `Closes #N`【一手 `sweagent/run/hooks/open_pr.py:94-98, 149-186`】。mini-swe-agent 只有一个"执行前用正则拦危险命令"的示例。codex-action 没有检查代码，但文档建议把它放在作业最后一步，产出交给另一个新作业处理【一手 `docs/security.md:76` 起】，和我们拆出检查作业的思路一致。

### GitHub 平台

- `GITHUB_TOKEN` 能申请的权限里没有 workflows（已抽查 `data/reusables/actions/github-token-available-permissions.md`）；GitHub App 要改 `.github/workflows` 必须有 "Workflows" 权限（已抽查 `choosing-permissions-for-a-github-app.md:92`）。所以用它推送改了工作流文件的提交会被拒【推断】，报错原文文档里没有【待验证，要在测试仓库实测】。
- 推送保护（检出密钥就挡下推送）：仓库级要付费的 Secret Protection，默认关；用户级默认开、作用于推到公开仓库的内容，但以个人账号为单位。`GITHUB_TOKEN` 或机器人的推送受不受它管，文档没点名【待验证】【一手 `content/code-security/concepts/secret-security/push-protection.md:53-106`】。
- `@用户名`、`@组织/团队` 会通知对方，事后编辑加上也会；对方要对仓库有读权限【一手 `basic-writing-and-formatting-syntax.md` "Mentioning people and teams"】。github-actions[bot] 发出的是否一样、包进反引号是否就不通知，文档都没写【待验证】；gh-aw 用的就是反引号的办法。
- 关闭关键字共九个：close、closes、closed、fix、fixes、fixed、resolve、resolves、resolved，可带冒号、可大写，目标分支是默认分支时合并后关闭 issue（已抽查 `linking-a-pull-request-to-an-issue.md:28-61`）。

### 密钥扫描工具

- **gitleaks**：MIT，最新 v8.30.1（2026-03-21）；README 写明已"功能完结"、只出安全补丁，作者转去做 Betterleaks。222 条规则，130 条带熵阈值（"熵"衡量一串字符看起来有多随机）。有 `stdin` 模式；只有 `git` 模式只看新增行。完全离线【推断，来自源码搜索】。单个 Go 程序，发布页只有 sha256 校验和、没有签名。两处会削弱检查：行内写 `gitleaks:allow` 就忽略这一行，要加 `--ignore-gitleaks-allow` 才不认；stdin 模式会读当前目录的 `.gitleaks.toml` 和 `.gitleaksignore`（已抽查 `cmd/stdin.go:28`）。官方 gitleaks-action 从 v2 起扫组织仓库要许可证【一手 `LICENSE.txt`】。
- **TruffleHog**：AGPL-3.0，v3.99.7（2026-10-24），约 900 多个检测器。默认会拿找到的密钥去对应服务试，还会联网检查更新并自我替换，离线要加 `--no-verification --no-update`。行内 `trufflehog:ignore` 也能让一行被跳过。校验和有 cosign 签名。
- **detect-secrets**：Apache-2.0，纯 Python，pip 可装；最新发布 v1.5.0（2024-05-06），之后没有新版本，没有 Anthropic 的插件；扫补丁只能用 Python 接口；验证默认开着、会联网，"验证无效"的发现会被丢掉。Python 3.14 能否运行【待验证】。
- **GitHub 自己的密钥扫描**：531 种格式，只公开名称、不公开正则；没有能离线调用的方式。
- **误报**：ESEM 2023 论文在 SecretBench 上用当时的默认配置测，gitleaks 精确率 46%、召回率 88%，TruffleHog 召回率 52%，误报主要来自"通用正则"和熵判断【一手 摘要】。针对普通代码补丁的公开误报数据没找到。
- **新格式令牌**：2026-04-27 起 GitHub App 安装令牌（`ghs_`）分批换成"前缀加 JWT"、约 520 个字符、带点的格式，官方建议匹配写法 `ghs_[A-Za-z0-9\.\-_]{36,}`【一手 changelog 2026-05-15】。claude-code-action 和 gitleaks 写死"36 位、不含点"，按字面不会整体识别【推断，未实测】；gh-aw 已经改成允许带点（已抽查）。

## 四、借鉴什么，不借鉴什么

- **借鉴 gh-aw 的受保护名单结构和匹配方式**：按文件名匹配的依赖清单和 agent 指令文件、按前缀匹配的目录、改名两边都查、补丁头解析不了就整个拒绝、应用后按实际改动重查。这是唯一一家做了名单的，理由（供应链、毒化后来的 agent、CI 配置）和我们的威胁一样。
- **不借鉴把 README.md 等治理文件列为受保护。** gh-aw 的理由是"agent 会把它当上下文读"，但修文档本身就是很常见的 issue；我们只开草稿 PR，都要人审。
- **不借鉴 gh-aw 的默认处理"照开 PR + 要求修改"用在 `.github/` 和点目录上。** 我们已经定了改 CI 的 issue 不做，`GITHUB_TOKEN` 也推不上去，这类改动直接拦下更省事。依赖清单不一样：小版本升级、加一个依赖是正常任务（[接收哪些 issue](../接收哪些issue.md) 规则 5 只排除"大版本升级"），所以借鉴它的默认处理，照开 PR、醒目标出。
- **借鉴 gh-aw 的文件数和大小上限**（100 个文件、4096 KB）。它管的是"不正常的大补丁"，和挑 issue 时的 100 行软限制不是一回事。
- **符号链接和子模块直接拦，借鉴 gh-aw 推送时的做法；可执行位和二进制只标出。** 加个可执行脚本、加一张文档图片是正常改动。
- **借鉴 gh-aw 和 claude-code-action 的"带前缀的令牌格式"正则，但命中就拦，不只是打码。** 公开仓库里 PR 一开出来就看得见，打码后照发等于默认相信剩下的部分没问题。不借鉴"按真实值精确替换"：检查作业手里本来就没有密钥。
- **不引入 gitleaks、TruffleHog、detect-secrets（建议，待定）。** 理由：agent 那台机器上本来就没有真密钥（模型密钥在代理里），扫描是最后一道保险；带固定前缀的格式几乎不会误报，命中就可以放心地拦，而 gitleaks 的通用规则误报多（论文里精确率 46%），一误报就拦下正常 PR；gitleaks 已停止加新功能、stdin 模式会读被扫目录里的配置、行内注释能让一行被跳过；TruffleHog 默认联网、AGPL；detect-secrets 两年多没发布。代价是覆盖面窄：没有前缀的密钥（随便一串随机字符）查不到。
- **借鉴两家都有的清洗步骤**：删不可见字符、控制字符、HTML 注释；`@提及` 一律包进反引号。项目里已有的 `src/repoaegis/sanitize.py`（清洗 issue 输入用）可以复用删不可见字符和注释的部分。
- **不借鉴 gh-aw 的全角转半角和"形近字母替换"。** 汇报用 issue 的语言写，中文的"，：（）！"会被改成英文标点，俄文、希腊文会被改坏。它们是为了防"用怪字符绕过过滤"，我们的过滤只看带前缀的令牌，全角和形近字母拼不出能用的令牌。
- **不借鉴 gh-aw 在描述里保留 @issue 作者。** agent 写的文字一个人都不通知；要不要 @ 打标签的人，由程序的模板决定，不交给 agent。
- **关闭关键字比 gh-aw 更严。** agent 写的 "fixes #5" 能在合并时关掉别的 issue；`Closes #N` 只由程序加，agent 文字里的关闭关键字全部包进反引号。

## 五、建议（待用户确认）

规则写成一个模块，submit 和检查作业共用。每条规则给出两种级别之一："拦下"或"标出"。submit 第一次调用时，两种都作为提醒发给 agent；检查作业里，有"拦下"就不开 PR、在 issue 里留言说明（不复述命中的密钥原文），只有"标出"就照开草稿 PR、在描述顶部列出。

1. **拦下的文件**：`.github/` 及所有顶层点目录里的文件（`.husky/`、`.githooks/`、`.claude/` 等）；agent 指令文件 `AGENTS.md`、`CLAUDE.md`、`GEMINI.md`（任意深度）。匹配照 gh-aw：文件名精确、区分大小写，目录按前缀，改名新旧两边都查，补丁头解析不了就拦。
2. **标出的文件**：gh-aw 名单里的依赖清单和锁文件（任意深度）。`README.md` 等治理文件不算受保护；`CODEOWNERS` 例外，拦下（它决定谁来审 PR）。
3. **补丁大小**：超过 100 个文件或 4096 KB 就拦下。
4. **其他危险改动**：新增或改动符号链接、子模块，拦下；改了可执行位、新增或改动二进制文件，标出。
5. **像密钥的字符串**：只看补丁新增的行和汇报全文；用自写正则，覆盖 gh-aw 那约 15 条内置格式、claude-code-action 多出的 `ASIA` 和 Slack、JWT、私钥文件头（`-----BEGIN ... PRIVATE KEY-----`），`ghs_` 按官方新写法允许带点；命中就拦下。
7. **新增被 `.gitignore` 忽略的文件，拦下**（2026-10-30 用户提出）。submit 生成补丁时用的 `git add --all` 会跳过被忽略的文件，但有两个口子，主对话实测过（WSL 里一次性脚本，仓库开工时 `.gitignore` 写着 `.env`）：agent 用 `git add -f .env` 强行加进暂存区，或者把 `.gitignore` 里那一行删掉，`.env` 都会进补丁；只是新建 `.env` 则不会。所以检查要按**开工提交里的** `.gitignore` 判断补丁新增的文件（在开工提交的检出里跑 `git check-ignore --no-index`，文件不用真的存在），而不是按改过之后的。开工时就已被跟踪、碰巧也匹配忽略规则的文件，改它不算。被忽略的多是 `.env`、构建产物、日志，拦下的代价是偶尔误拦一个维护者本该强行加入的测试数据文件。这次三路调研都没提到别家有这条，没有专门去查【待查】。
8. **汇报文字清洗**：删不可见字符、控制字符、HTML 注释（复用 `sanitize.py`）；`<`、`>` 转义，不让 agent 写 HTML；`@提及` 全部包进反引号；关闭关键字全部包进反引号；图片全部去掉（图片地址能把数据带到外部服务器）；链接只有 https 且域名是 GitHub 自己的（照 gh-aw 的默认名单）才保留可点击，其他的改成代码样式：文字还在，人能看到 agent 引用了哪里，但点不了（我们自己的设计，gh-aw 是直接替换成 `(redacted)`）。标题再去掉换行，截到 100 字符（submit 已限制）。不做全角转半角和形近字母替换。

## 六、尚未查清

1. 用 `GITHUB_TOKEN` 推送改了工作流文件的提交，被拒时的报错原文，以及是整个推送失败还是只拒那一个文件。2026-10-30 补查：GitHub 文档里没有这句报错；社区讨论 [community#35410](https://github.com/orgs/community/discussions/35410)（2022-10-07，用户自报，检出时没传令牌、用的是默认的 `GITHUB_TOKEN`）贴出的原文是 `! [remote rejected] <分支> -> <分支> (refusing to allow a GitHub App to create or update workflow .github/workflows/deliver.yml without workflows permission)`。同日在测试仓库实测【实测】：加一个手动触发的工作流（`permissions: contents: write`，检出时不传令牌，即用 `GITHUB_TOKEN`），在运行机上建两个分支：`probe-normal` 只有一个改普通文件的提交；`probe-mixed` 在它之后再加一个新建 `.github/workflows/probe-target.yml` 的提交。推 `probe-mixed` 得到 `! [remote rejected] probe-mixed -> probe-mixed (refusing to allow a GitHub App to create or update workflow `.github/workflows/probe-target.yml` without `workflows` permission)`，退出码 1，远端没有出现这个分支，连前面那个普通提交也没推上去；推 `probe-normal` 成功。即**整个分支被拒，不是只拒那个文件**。运行记录：`ETOLucy/repoaegis-sandbox` Actions 运行 41053737983（运行机 git 2.56.0）；测完已删掉 `probe-normal` 分支和测试工作流。这说明 `.github/workflows/` 在推送这一层有平台兜底，但产出检查仍要先拦：否则推送失败，整个 PR 开不出来，issue 里只能看到一个推送错误。`.github/` 下工作流以外的文件（如 `.github/CODEOWNERS`、issue 模板）不受这个限制，只能靠我们的检查。
