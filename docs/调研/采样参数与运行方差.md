## 一、为什么查

RepoAegis 的 agent 要调用 DeepSeek 的模型改代码。以后无论是选模型、选推理设置，还是比较两种 agent 写法哪个好，都要跑评测，而评测结果会受两件事影响：一是请求里带的"采样参数"，二是同一设置多跑几次本身就会有的分数波动。

先解释两个词。**采样参数**是控制模型"抽词"随机程度的设置：**温度**（temperature）越低，越倾向于选概率最高的词；温度为 0 时每一步都取概率最高的词，这种做法叫**贪心解码**。**top_p** 是只在累计概率排前面的那部分词里抽，**top_k** 是只在概率最高的前 k 个词里抽。**seed** 是随机种子，用同一个种子希望得到同样的结果。

用户当时提出了几个看法，要求核实：不是所有模型都能设温度；新模型除了温度还有新参数，设置不同跑出来的结果就不同；评测要考虑方差；评测时要记录模型的系列、版本和当日价格，但只在需要比较性价比时才记，每一项记录都要有用途。用户还有一个旧认识：Sonnet、Haiku 5.5 这类新模型好像没有温度参数了，换成了一个作用类似温度的新参数，以前温度设为 0 输出更准，新参数调低也有类似效果。这次调研就是要检验这些看法，并弄清楚要跑几次才能分辨两个方案的真实差距。

### DeepSeek 的细节

模型名当前只有两个：`deepseek-flash`，文档里的版本串是 DeepSeek-V4.1-Flash-1017；`deepseek-v4-pro`，版本串 DeepSeek-V4-Pro-0813。上下文都是 1M，最大输出 384K。旧名 `deepseek-v4-flash` 和 `deepseek-v4-flash-vision-exp` 还能调用，但请求实际由 V4.1-Flash-1017 处理、按 Flash 价计费【一手】（价目页 https://api-docs.deepseek.com/quick_start/pricing ，转述）。也就是说，同一个模型名背后的模型可能被悄悄换掉；只记模型名，事后无法解释成绩为什么变了【推断】。

思考模式默认开启，默认强度 high。实际只有三档：请求 minimal、low 都按 low，medium、high、xhigh 都按 high，max、ultra 都按 max【一手】（思考模式页，本次复核过）。思考模式下 temperature、presence_penalty、frequency_penalty"will not trigger an error but will also have no effect"，就是传了不报错、也不起作用【一手】（同上）。top_p 两个模型规则不同：`deepseek-flash` 只在思考模式下生效，有效范围 0.95 到 1.0，低于 0.95 按 0.95 算，非思考模式固定为 1.0；`deepseek-v4-pro` 在思考模式下忽略你传的值，带工具时固定 0.95、否则 1.0，非思考模式下生效【一手】（同上）。接口参考页写温度默认值为 1，并注明"Has no effect in thinking mode"【一手】（本次复核过）。参数设置页对写代码、做数学推荐温度 0.0，但这只对非思考模式有意义【一手】（https://api-docs.deepseek.com/quick_start/parameter_settings ，转述）。

接口参考页里没有 seed 字段（本次在保存的原文里搜过，没有这个词）；回包里有 `system_fingerprint`，说明是"the backend configuration that the model runs with"【一手】。没写 seed 不等于一定不支持，是否支持【待验证】。

### "温度 0 更准"成立吗

先解释两个指标。**pass@1** 是"只试一次就做对"的比例；**pass@k** 是"每题试 k 次，只要有一次对就算对"的比例。

在单轮、非推理模型、只看 pass@1 的任务上，温度 0 大致不比别的温度差，但也谈不上更准。Renze 与 Guven（arXiv 2402.05201）让 9 个模型做 10 类选择题，温度从 0 扫到 1.0：GPT-3.5 加思维链在 1000 题的大考上，Kruskal-Wallis 检验 p=0.403（§3.1），即温度对准确率没有显著影响；温度超过 1.0 后准确率下降，约 1.6 时接近 0【一手】。作者建议用 0，理由是可复现且不损失准确率，但只测了选择题和单轮对话（§4）【一手】。代码任务上，"Hot or Cold?"（arXiv 2309.02772）表 3 里贪心解码和最佳温度采样互有胜负，差 1 到 2 个点（CodeGen-2B 23.8 对 22.2，InCoder-6B 14.0 对 15.3）【一手】。

看 pass@k 时，温度高反而好。Codex 论文（arXiv 2107.03374 §3.3）里，679M 模型 pass@1 的最优温度是 0.2，pass@100 的最优温度是 0.8，原因是采样多时答案更多样更有利【一手】。

推理模型上温度 0 明显有害。DeepSeek-R1 论文（arXiv 2501.12948v1 §3）评测用温度 0.6、top_p 0.95，说明不用贪心解码是因为长输出时重复率更高【一手】；R1 模型卡建议温度 0.5 到 0.7、推荐 0.6，"to prevent endless repetitions or incoherent outputs"【一手】。Qwen3 模型卡写明思考模式不要用贪心解码，会导致性能下降和无尽重复【一手】（https://huggingface.co/Qwen/Qwen3-8B）。Pipis 等（arXiv 2512.12895 附录 A 表 1）在 AIME 上测贪心解码的"循环率"（一段输出里同一个 30 词片段出现至少 20 次）：R1 蒸馏的 1.5B 模型 76%，7B 49%，32B 37%，QwQ-32B 4%；提高温度能大体消除循环【一手】。较新的模型卡推荐温度普遍是 1.0：DeepSeek-V4-Pro / V4.1-Flash 推荐温度 1.0、agent 场景 top_p 0.95；Kimi K2-Thinking、GLM-4.6 也推荐 1.0【一手】（各自模型卡，转述）。

agent 任务上差距可以很大。Bjarnason 等（"On Randomness in Agentic Evals"，arXiv 2602.07150 表 1）里，DeepSWE-preview 在 SWE-bench Verified 上温度 1.0 是 31.4%，温度 0 掉到 20.4%，差 11.0 个点且显著；Devstral-2 在温度 0.2 和 0 之间没有显著差别（63.5% 对 63.8%）【一手】。

### 推理强度调高调低会怎样

各家对推理强度的定义都是"想多少"，不是"随机程度"。OpenAI 写它"guides the model on how much to think"，调低换来更快、更少的推理 token【一手】（转述）。Anthropic 写调低是为了速度和成本、接受一定的能力下降；Haiku 5.5 的说明写低档位下模型"more likely to skip a search, stop early, or skip a check"【一手】（主对话读原文）。没有任何一家说调低会更准、更确定，也没有一家说它替代温度【一手】。Google 在去掉温度的同一段里，建议用系统提示词写明规则来提高确定性【一手】（转述）。所以用户假设的前半句"新模型没有温度"在 Anthropic、OpenAI（开推理时）、Gemini 3.6 以后成立，在 DeepSeek 只在思考模式下成立，在 xAI 不成立；后半句"有类似温度的新参数、调低更准"在五家都不成立。

调高也不一定更好。HAL（arXiv 2510.11977 §4.1）的 36 个"模型 × agent × 基准"组合里，有 21 个调高推理强度后准确率持平或下降；9 个基准里只有 1 个，最贵的那次运行落在"同等花费下准确率最高"的边界上【一手】。SWE-bench 的 bash-only 榜单数据里，同一模型、同一 agent 版本的唯一干净对照是 GPT-5.2（mini-swe-agent v1.17.2）：未标注推理强度 69.0%、每题 0.27 美元，high 档 71.8%、0.52 美元【一手】（榜单数据文件 data/leaderboards.json）；这是单次运行，按下文的方差看不能算显著【推断】。s1（arXiv 2501.19393 §6.2）用强制延长思考把 AIME24 从 50% 提到 57%，延长到约 6 倍后不再提升【一手】。

"调低推理强度能让多次运行更一致"，没有找到正式研究【待验证】。唯一相关的小样本研究 arXiv 2608.16956 比较 Claude Sonnet 5 在 AIME 2026 上 high 档和不传 effort，每题 5 次共 30 题，准确率差 +1.3 个点，95% 置信区间 [-2.7, +4.7]，不显著，没算运行间方差【一手】。

### 温度 0 也不等于结果确定

Thinking Machines 的文章（2025-09-10，https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/）指出根因是服务端的计算缺少"批不变性"：服务器把多个请求凑成一批算，同一个请求的结果会随这一批里有多少别的请求而变，而负载一直在变。他们让 Qwen3-235B 在温度 0 下生成 1000 次，得到 80 种不同输出，从第 103 个 token 开始分叉；换成批不变的计算后 1000 次完全一致，但更慢【一手】（转述）。这种改法只有自己部署模型的人能做，调用接口的人做不了，只能多跑几次【推断】。

Atil 等（arXiv 2408.04667）在温度 0、固定 seed 下每个条件跑 10 次，准确率在不同运行之间最多相差 15%（§7.1）；GPT-4o 做大学数学，10 次原始输出完全一致的比例是 0%（表 2）；作者建议报告多次运行的最大值减最小值（§8）【一手】。s1 附录 B 也写到，vLLM 上贪心解码加相同 seed，分数仍会随批大小等显著变化【一手】。2602.07150 发现温度 0 并没有让 agent 评测的方差变小，有时反而变大，例如 Qwen3-32B（nano-agent）标准差从 0.7 升到 1.2 个点；运行在很早就分叉，温度 0 时中位分叉点在第 32 到 56 个 token【一手】。

各家的确定性承诺：OpenAI 的 seed 是尽力而为，cookbook 原句"Determinism is not guaranteed"，另用 `system_fingerprint` 提示后端变化【一手】（转述）；xAI 写"best effort"【一手】；Anthropic 没有 seed，也没找到确定性承诺；DeepSeek 只有 `system_fingerprint`，承诺【待验证】。MoE 结构和服务端版本更新怎样造成不一致，没读到一手资料【待验证】。

### 多次运行的分数波动，要跑几次才看得出差别

几个统计词先说清楚。**标准差**衡量多次运行的分数离平均值有多散；**极差**是最高分减最低分。**显著**指差距大到不太可能只是偶然，通常用"p<0.05"，即如果两个方案其实一样好，看到这么大差距的概率小于 5%。**统计功效**指两个方案确实有差距时，实验能把它检测出来的概率，常取 80%。

主要数据来自 2602.07150【一手】：在 SWE-bench Verified 的 500 题上，3 个模型 × 2 个 agent 框架 × 2 种温度共 12 种配置，每种独立跑 10 次，合计约 6 万条运行轨迹。同一配置 10 次之间，pass@1 的极差为 2.2 到 6.0 个点，标准差 0.7 到 1.8 个点（表 1）。例如 DeepSWE-preview 温度 1.0 是 31.4%±1.0，10 次落在 28.8% 到 32.4%。注意这里"2.2 到 6.0"是极差，不是标准差；当时主对话一度说"温度 0 时标准差仍超过 1.5 点"，不准确，原文温度 0 时的标准差是 1.0 到 1.8。

论文用功效分析算"要跑几次"（§3.2、表 2）。前提是：两组独立比较（两样本 t 检验），分数近似正态分布，显著性 p<0.05，功效 80%。公式为 n ≥ 2·((z_{α/2}+z_β)/(Δ/σ))²，n 是每个方案各跑几次，Δ 是想测出的差距，σ 是标准差。在 σ=1.5 个点时，测出 1 个点要 36 次，2 个点要 9 次，5 个点只要 2 次；σ=0.7 时测出 2 个点只要 2 次；把功效提到 95%，测出 2 个点约要 15 次（附录 A）【一手】。本次按公式复算，这几个数字一致。作者也说明他们的 10 次只够可靠测出 2 个点以上的差距。结论是 2 到 3 个点的提升在单次运行下可能只是噪声【推断】。

作者还建议同时报告 pass@1、pass@k 和 **pass^k**（k 次全部做对的比例，衡量稳定性）。例如 Devstral-2（nano-agent）pass@1 63.5%、pass@5 76.2%、pass^5 49.1%【一手】。

其他工作报告方差的方式【一手】：SWE-agent 同一配置跑 6 次，解决率 17.94±0.49（论文 B.5、表 10）；"AI Agents That Matter"（arXiv 2407.01502）每个 agent 跑 5 次，用 t 分布给 95% 置信区间；SWE-rebench 每个模型跑 5 次，报告平均值的标准误和 pass@5；Epoch 多数基准跑 8 到 16 次给误差棒；Artificial Analysis 多数基准重复 1 到 5 次。Anthropic 的基础设施噪声文章说，资源配置不同可在 Terminal-Bench 2.0 上造成 6 个点差距，榜单上 3 点以内的差距要谨慎看【一手】（转述）。

### 评测框架怎样设参数、记什么

参数不同的模型怎么公平比较，各家做法不一【一手】：SWE-rebench 用模型开发者推荐的默认生成参数；Epoch 用各接口的默认温度；Artificial Analysis 非推理模型温度 0、推理模型 0.6，厂商另有推荐时从其推荐；HAL 把同一模型的不同推理强度当成独立条目，按成本和准确率一起比较；arXiv 2608.16956 主张比较单位应是完整的一组条件：模型、推理强度或不传、输出上限、价格、日期。Anthropic 文档建议对新模型在自己的评测上"run an effort sweep"，把各档都跑一遍【一手】（主对话读原文）。Epoch 的博文还提到，同一模型换接口供应商是最大的方差来源，有供应商根本没把推理强度传下去，三档成绩一模一样【一手】（转述）。

两个参考项目的默认设置【一手】：SWE-agent 的 `GenericAPIModelConfig` 默认温度 0.0、top_p 1.0，没有推理强度字段，只能经 `completion_kwargs` 传。mini-swe-agent 的 SWE-bench 配置在 v1.17.1 到 v2.3.1 设了 `temperature: 0.0`，2026-06-10 的提交 06fabb88（PR #861，"Drop T=0 default in swe-bench"）去掉了它，随 v2.4.0 发布；现行配置只设 `drop_params` 和并行工具调用，温度和推理强度都由接口默认值决定。

SWE-bench 官方提交（https://github.com/SWE-bench/experiments）要求 `metadata.yaml`（模型、agent、可选的 `reasoning_effort` 等）、预测文件、每题日志和轨迹，没有价格字段，也没有温度字段【一手】（转述）。HAL 用 W&B Weave 记每次调用和 token 成本；一个子 agent 读到它按某日价格换算美元（§3），另一个没读到价格来源和日期，具体公式【待验证】。LiteLLM 的价格表是社区维护的"live list"，没见版本机制，用它算成本时结果取决于运行当天的表【一手】（https://docs.litellm.ai/docs/completion/token_usage ，转述）。

## 四、各家、各项目借鉴什么，不借鉴什么

**DeepSeek 官方文档。** 借鉴它的默认设置：思考模式开、强度 high，这是我们实际会用的状态；记录时以文档里的版本串为准。不借鉴参数设置页"写代码用温度 0.0"的建议：它只对非思考模式有效，而思考模式下温度根本不起作用；推理模型和 agent 任务上温度 0 还有循环和掉分的证据。

**Anthropic 文档。** 借鉴两点：对新模型把推理强度各档都跑一遍，而不是照搬旧设置；以及"没有设置能替代温度"这个提醒，即不再指望靠某个参数换来一致性。我们不用 Claude 的接口，它的具体参数规则只作对照。

**SWE-agent。** 不借鉴它默认温度 0.0 的做法：理由同上，而且对只接受默认温度的模型会报错（SWE-agent 怎么处理这种情况当时没查）。借鉴它报告多次运行的均值和标准差。

**mini-swe-agent。** 借鉴它现在的做法：不设温度，交给接口默认值。它自己在 2026-06 去掉了温度 0，和上面的证据方向一致。

**SWE-bench 提交规范。** 借鉴它记录推理强度、保存每题轨迹和日志。不照搬它"不记用量"的部分：token 用量是日后按新价格重算成本的唯一依据。

**HAL。** 借鉴它把不同推理强度当成独立条目、成本和准确率一起看的比较方式。

**SWE-rebench、Epoch。** 借鉴"主结果用厂商推荐或默认设置，同一设置多跑几次并给误差"的做法。不借鉴 Artificial Analysis 给非推理模型统一用温度 0：我们用的是推理模型，而且温度在思考模式下无效。

**On Randomness（2602.07150）。** 借鉴用功效分析定次数，以及同时报告 pass@1、pass@k、pass^k。它的数字来自开源模型和别的 agent 框架，DeepSeek 在我们任务上的标准差要自己测，不能直接套用 σ=1.5。

**Atil 等。** 借鉴报告多次运行的最高与最低分，而不是只报一个数。

**Thinking Machines。** 只借鉴它对原因的解释；批不变的计算只有自己部署模型才用得上，我们调接口做不到。

## 五、据此的决定

用户定下的记录规则，原话是：

> 而且还要记录具体的模型嘛，如果有需求的话，就是具体使用了什么模型，然后出了什么结果，模型的哪一个系列，哪一个版本，然后当日的价格等等。如果需要对比这个性价比这一块才会去记录这些东西……如果不需要记录的话，我觉得就没必要写。

以及更早关于成本和耗时的一句："需要记录的时候应该需要有原因……如果没有意义的话为什么要记录呢？"用户同时要求关注方差，并注意不是所有模型都能设温度、新模型有新参数、设置不同结果就不同。

当时根据调研对这条规则做了展开，按用户"之后要提醒我留意"的要求记进了提醒清单：每项记录写明用途；token 用量（输入、命中缓存的输入、输出）一直记，因为它是重算成本的唯一依据；价格和日期（DeepSeek 还要记是否高峰）只在比较性价比时记；墙钟耗时很少有意义，因为并发和限流会扭曲它；每次运行记请求的模型名和文档里的版本串、推理强度档位，以及请求里发送的采样参数值和实际生效的值。这些细则用户没有在材料里逐条表态，"token 一直记"和"分开记发送值与生效值"两条是调研后补充的，是否采纳待用户确认。

另外已经明确的结论：不靠温度 0 求可复现，靠多次运行，次数按功效分析算。

待定：评测时用 DeepSeek 哪一档推理强度、要不要扫多档；要不要比较非思考模式；每组比较跑几次（取决于自己测出的标准差和想分辨的差距）；用配对比较还是独立比较；何时开始正式评测（产品做完、由用户定）。
