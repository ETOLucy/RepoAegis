# 调研报告：issue 里看不见的内容，以及怎么清洗

> 调研日期：2026-10-26～27。这份报告合并了三部分：两个调研子 agent 的笔记（各自打开了源码、规范和官方文档，用 GitHub 的渲染接口和浏览器做了实测），以及我在 2,423 篇真实 issue 上的统计。子 agent 的结论我抽查了关键几条（第六节的解析器验证是我重跑的），其余没有逐条复核，下文按原标注写明【一手】【实测】【转述】【推断】。子 agent 的笔记、抓下来的源文件和测试文件保存在会话临时目录 `research-sanitize-A/`、`research-sanitize-B/`，我的统计脚本在 WSL 的 `~/scratch/sanitize/`。本文取代 2026-10-26 的初版（当时只列了八条规则，太简单）。

## 一、为什么查

维护者是看了 GitHub 网页上**渲染出来**的 issue 才打标签的，agent 读到的却是 Markdown **原文**。原文里有些内容网页上不显示，维护者看不到，模型却读得到，这就是藏指令的地方。清洗要做到两件事：一是把这些看不见的内容去掉或标出来，让 agent 读到的和维护者看到的一致；二是不能误伤正常内容，比如代码样例、非英文文字、表情。

初版建议照搬 claude-code-action 的七条规则再补几条。用户担心现实场景比这复杂得多，要求认真查。查下来，确实复杂得多。

## 二、方法和出处

1. **各家项目的清洗代码**（子 agent A）：gh-aw 的 `actions/setup/js/sanitize_content_core.cjs`（提交 `6c387d00`），claude-code-action 的 `src/github/utils/sanitizer.ts` 及其 issue 区，run-gemini-cli / gemini-cli 的工作流和安全公告，Cline 的修复 PR #9211，codex-action 的 `docs/security.md`，OpenHands/extensions，Copilot 文档，以及 Embrace The Red、Paul Butler、Trail of Bits 关于藏字手法的原文，微软 Spotlighting 论文（arXiv 2403.14720），OWASP LLM01。
2. **GitHub 渲染规则和 Unicode 事实**（子 agent B）：GFM 规范 0.29-gfm、CommonMark 0.31.2、html-pipeline 的清洗白名单、GitHub 官方 MCP 服务器的清洗代码（`github/github-mcp-server` `pkg/sanitize/sanitize.go`），Unicode 18.0 的 `DerivedCoreProperties.txt`、`emoji-sequences.txt` 等，Trojan Source 论文（arXiv 2111.00169）。用 GitHub 渲染接口（`POST /markdown`，只渲染、不改动任何东西）做了 20 多组实测，在 github.com 页面上用浏览器检查了几处样式。
3. **真实 issue 上的统计**（我）：上一份报告的 12 个仓库共 2,123 篇 issue 和 PR 正文，加上 ant-design、apache/echarts（中文多）和 rastikerdar/vazirmatn（波斯文多）各最近 100 篇，共 2,423 篇。把候选规则逐条跑一遍，数每条会动到多少篇、动的是什么。
4. **验证"以渲染结果为准"的做法**（我）：用 Python 3.14 自带的 `html.parser` 读子 agent B 的渲染结果，看它对注释等边角情况的判断是否和浏览器一致（第六节）。

## 三、藏东西的地方，比"删 HTML 注释"多得多

下面每一条，都是"原文里有、GitHub 页面上看不见"，除非另外注明，都经过渲染接口实测（子 agent B 笔记第一到六节）。

**HTML 注释本身就有好几个坑。**

- 行首的 `<!--` 会开启一个"HTML 块"，可以跨空行，没写结尾就吞掉后面全文。前一行是段落、中间不空行也照样生效。
- GitHub 用的是 CommonMark 0.31.2 的新注释规则：`<!-->`、`<!-- a -- b -->` 都是注释。按 GFM 规范文档里的旧规则写的正则会漏掉。
- 最危险的一处：GitHub 先把 Markdown 转成 HTML，再用 HTML5 规则清洗。两步对"注释到哪结束"看法不一致。比如列表项或引用块里没闭合的注释，Markdown 这一步认为它在容器结束时就结束了，HTML5 这一步却一路吞到容器外面。
- `--!>` 在页面上算注释结束，Markdown 规则却不认。所以按 Markdown 语法找注释的程序，会把维护者**看得见**的内容也删掉。
- 和注释同类、同样看不见的还有三种：处理指令 `<?…?>`、声明 `<!X…>`、`<![CDATA[…]]>`。没闭合的会吞到第一个 `>`。
- 写在原始 HTML 的 `<pre>`、`<code>` 里的注释，照样看不见。

**链接定义和脚注。**

- 单独一行的 `[//]: # (…)`、`[comment]: <> (…)` 整行不显示，列表项和引用块里也一样。
- 同名的链接定义只有第一条生效，后面几条整条消失。
- 没被引用的脚注整条消失。

**代码块相关。**

- 围栏开头 ```` ``` ```` 后面那串字（信息串）不显示。
- `mermaid`、`geojson`、`topojson`、`stl` 代码块和 `math` 块，页面上显示画出来的图或公式，原文本身看不见。
- 公式里的 `\color` 在 github.com 上确实生效（在真实页面上看过），所以 `$\color{white}{…}$` 在浅色主题下和背景同色。`\phantom{…}` 只占位不显示，待验证。

**HTML 属性和元素。**

- 鼠标悬停才出现：任何标签上的 `title`，以及链接地址本身。
- 完全看不见：`alt`、`cite`、`summary`、`abbr`、`itemtype`、`value`、`label` 等一长串属性的值；`<picture><source srcset/media>`，Trail of Bits 就是用它对 Copilot 藏指令的；空文字的链接；`<rp>`；宽高为 0 的图片。
- `<video>` 会连同里面的文字整段被 GitHub 删掉，页面上看不见，原文里却有。
- 不算看不见、但容易错过：折叠的 `<details>`，以及一长串 `<br>` 把后文推到很下面。

**HTML 实体解码成不可见字符。** `&#xE0041;`、`&#8203;`、`&#x202E;` 这类写法在页面上被解码成真正的不可见字符。只按字符扫描的清洗程序会放过它们，而模型自己能把实体解出来。真实样本里就有 `&#8203;`（ant-design #59636）。

**Unicode 不可见字符。** Unicode 标准把 4,174 个码位列为"默认可忽略"（`DerivedCoreProperties.txt` 中的 Default_Ignorable_Code_Point）：

- **标签字符** U+E0000–E007F 和 ASCII 一一对应，能拼出整句英文，完全看不见（"ASCII 走私"）。
- **变体选择符** U+FE00–FE0F、U+E0100–E01EF 共 256 个，每个能编码一个字节，挂在一个表情后面看起来什么都没有（Paul Butler 的做法）。
- **双向控制符**会让维护者看到的字的顺序和模型读到的不同（Trojan Source）。
- 另有韩文填充符、盲文空白 U+2800 等显示成空白的字符。
- Embrace The Red 的 "Sneaky Bits" 说明，**任意两个**不可见字符就能当 0 和 1 编码任意内容，所以"列一张删除清单"永远可能漏。

GitHub 只对**文件内容**显示双向字符和隐藏字符警告（changelog 2021-10-31、2025-05-01），没说 issue 正文；渲染接口对 issue 正文也不加任何标记。issue 页面上会不会提示，待验证。

**还有一类清洗管不了：看得见的注入。** 两次真实事故用的都是普通可见文字：

- PromptPwnd 攻击 Gemini 的工作流，把指令直接写在 issue 正文里；
- Clinejection 攻击 Cline，把指令写在 issue 标题里。

修复它们靠的是收紧权限和工具：Gemini 改成不给令牌、只给 `read_file`；Cline 干脆删掉了这些 AI 工作流（PR #9211）。都没有加文字清洗（子 agent A 笔记第三、四节）。同形字也属于这一类：用西里尔字母 `а` 冒充拉丁字母 `a`，人和模型都可能被骗，清洗不能删，删了就改变了原意。

## 四、清洗会误伤什么（实测 + 一手 issue）

**真实 issue 里，不可见字符多半是正当的。** 2,423 篇正文里，不可见字符出现的情况是：

- ZWNJ U+200C：34 篇，全部是波斯文，比如 `پیش‌ساخته`。删掉后字母被连写，拼写就错了。
- 变体选择符 FE0F：18 篇，全部紧跟在 ⚠️、✂️ 这类符号后面。
- ZWJ U+200D：5 篇，都在 👨‍👩‍👧‍👦、🤷‍♂️ 这类组合表情里。
- 从左到右标记 LRM：3 篇，在 RTL 文字和 Windows 系统信息里。
- BOM：2 篇，在行首，是复制粘贴带进来的。
- 零宽空格：2 篇，其中一处是 Dependabot 故意插在 `@` 后面，防止 @ 到人。
- 控制字符：2 篇，都在代码块里（换页符，以及 man 输出里的退格符）。

**没找到一处是用来藏东西的**，也没有一处是连续两个以上的零宽字符。所以初版"删掉所有格式字符"的建议，会损坏约 2.5% 的 issue，而且集中在非英文 issue 上。

**HTML 注释大量出现，而且删掉没问题。** 315 篇（13%）在代码外有注释，绝大多数是 issue 模板自带的提示语，比如 rich 的"WAIT! Is this a feature request?"。这些本来就是写给提交者看的，删掉正确。反过来说，"含注释就拒绝"会误拒大量正常 issue。

**链接定义行有正当用法。** 11 篇用了 `[1]: https://…` 这种脚注式链接，删掉整行就丢了网址；`[//]: #` 只出现在 Dependabot 的 PR 里，是它自己用的标记。所以链接定义只能删标题，不能删整行。

**粘贴进来的整页 HTML。** axios #11155、express #7422 把整个 Word 或 Excel 导出的 HTML 贴进了正文，带着条件注释、`<meta>`、本机文件路径。这种内容很长，但页面上只显示文字。

**两家现成清洗器都出过误伤 bug**（子 agent A 笔记第九节，读了 issue 原文）：

- claude-code-action #1366、#1897：删属性的正则不分是不是在 HTML 标签里，把代码 `plt.plot(x, y, title="…", alt="…")` 改成 `plt.plot(x,y,,)`，TOML 里的 `title = …` 整行消失。
- claude-code-action #1845：非 ASCII 的实体被整个删掉，`caf&#233;` 变成 `caf`，`&#20320;`（你）消失。
- claude-code-action #1779：一份没清洗的副本绕过清洗、直接进了模型。教训是清洗必须卡在唯一的出口。
- gh-aw：全角标点被改成半角，俄文、希腊文里的部分字母被换成拉丁字母，`x²` 变成 `x2`（子 agent 用 Python 按其规则复现）；网址过滤太严，有两个 issue（#17513、#33970）一直开着没解决；处理 60 万字符的输入卡了 816 秒（#50810）。

**删字符会毁掉复现材料。** issue 报的如果正是"零宽空格导致 split 出错""BOM 导致解析失败"这类 bug，那个字符本身就是复现条件，删掉就等于删掉了 bug（推断）。

## 五、各家怎么做，借鉴什么

- **只有两家对 issue 文字做了成套的清洗：gh-aw 和 claude-code-action。** Gemini、Cline、codex-action、OpenHands 都不清洗，靠的是限制谁能触发、不给令牌、少给工具、限定输出格式（子 agent A 笔记第一节）。gh-aw 自己的文档也说，这套清洗防的是"乱 @ 人、触发别的机器人"，不是提示词注入。
- **gh-aw**（规则最全）：先解码实体，再反复清洗不可见字符，直到结果不再变化；删除标签字符、注释（含 `--!>`）、引用式链接的标题；把行内链接的标题挪进可见文字；非白名单标签改成圆括号；网址只留 GitHub 域名；中和 @ 提及、斜杠命令和 `fixes #N`。
  - **借鉴**："先解码再清洗""反复做到不变""链接标题挪进可见文字"。
  - **不借鉴**：全角转半角、NFKC 规范化、同形字替换（伤中文、俄文）；网址过滤（会丢掉复现地址）。@ 提及这类中和属于产出发布前的检查，不在输入这一侧。
- **GitHub 官方 MCP 服务器**（GitHub 自己给模型读 issue 用的）：
  - **借鉴**：保留 ZWJ；变体选择符只留"紧跟在可见字符后面的第一个"，连续的、开头的都删，专门对付变体选择符藏数据；把围栏信息串里的长串内容删掉。
  - **不借鉴**：删 ZWNJ（伤波斯文）。
  - **更正（2026-10-27 我亲自核对主分支源码）**：它对 issue 的正文和标题用的不是同一套。正文只用 `sanitize.Content`，也就是只删不可见字符，HTML 注释、链接标题都原样保留；标题用 `sanitize.PlainText`，删不可见字符，再去掉 HTML 标签（`pkg/github/minimal_types.go` 第 817–818 行、`pkg/github/issues.go` 第 2140–2149 行；`pkg/sanitize/sanitize.go` 第 47–49 行，该文件最后一次修改是提交 `25f11e629c`，2026-09-03）。子 agent B 说的"对整篇正文做 HTML 清洗、把代码里的 `"` 变成 `&#34;`"，指的是同文件里的 `Sanitize` 函数，读 issue 的路径没有用它。所以 GitHub 自己给模型读 issue 正文时，只删不可见字符。
- **claude-code-action**：
  - **借鉴**：抹掉密钥；"以触发那一刻的内容为准"（这一条已经采纳）。
  - **不借鉴**：它的正则写法，因为误伤见第四节。
- **Copilot**：闭源，文档只说"过滤隐藏字符"，举了 HTML 注释一个例子。
- **Spotlighting 论文**（每个空格插标记、整段编码）：论文自己写明不适合代码类文本，不借鉴。

**通用 agent 读的都是原文。** 上面这些项目，无论清洗与否，交给模型的都是 Markdown 原文；OpenHands 的 issue-to-pr 干脆让 agent 自己用 `gh issue view` 读原文。调研中没有找到哪一家以渲染后的可见文字为准。模型本身读原始 Markdown 没有问题；"人看到的和模型读到的不一样"，只在"人先审、再交给 agent 去做"的流程里才是问题，而这正是 RepoAegis 的触发方式（codex-action `docs/security.md` 第 9 行专门提醒了这种情形）。

**GitHub 自带一种"纯文字"版本。** REST 接口用 `Accept: application/vnd.github.text+json` 请求时会返回 `body_text`，文档说是"正文的纯文字表示"【一手：docs.github.com `rest/issues/issues` 页】。2026-10-27 拿 rich #3931、black #4838、bat #1174 实测【实测】：注释被去掉了，但链接网址也全部丢了（`[docs](网址)` 只剩 `docs`），标题的 `#`、代码块的边界都没了，代码和正文混成一片。而且它只给当前版本，不是打标签那一刻的版本。所以不能直接拿来用，但它说明 GitHub 自己也认为"可见文字"是有用的一种视图。

## 六、两条路：照着规则改原文，还是以 GitHub 的渲染结果为准

**路线一：照着规则改原文**，也就是 claude-code-action 和 gh-aw 的路。要做对，就得判断"哪里是代码、哪里是注释"，而第三节说明：

- 必须用和 GitHub 完全相同的 Markdown 解析器（cmark-gfm），再模拟一步 HTML5 怎么吃注释；
- 光是"跳过代码块"就有十几种情况会判错（子 agent B 笔记第三节）。比如 ```` ```a`b ```` 不是围栏，判错一处，后半篇的"代码"和"非代码"就全部错位；
- GitHub 以后改规则，我们也得跟着改。

两家的 bug 记录说明，这条路很难写对。

**路线二：以 GitHub 的渲染结果为准。** 把打标签那一刻的标题和正文交给 GitHub 的渲染接口（`POST /markdown`，指定 issue 所在仓库，这和 issue 页面用的是同一套渲染）。从返回的网页里**只取页面上会显示的部分**：

- 文字照取；代码块保留原样；
- 链接写成"文字（网址）"；
- 属性一律不取；注释由解析器自动跳过；
- `<rp>` 和画图代码块不取。

注释、链接定义、信息串、属性、实体这些，渲染接口都已经按 GitHub 的真实规则处理好了，我们不用再判断哪里是代码。

**验证**（我重跑的）：用 Python 3.14 自带的 `html.parser` 读子 agent B 的四份渲染结果。

- 注释没闭合、吞掉列表外面的内容：取到的只有 `top item1`，和浏览器一致；
- 引用块里同类情况：只有 `top`；
- `--!>` 提前结束注释：`visible-after-bang line2 -->` 正确地被当成可见文字；
- 没闭合的处理指令吞到第一个 `>`：取到 `top x last`。

四组都和浏览器一致。

**代价：**

- 每篇多调一次接口。和其他接口一样，算在每小时 1,000 次的额度里。
- 要写一段把网页转回"带代码块、列表、标题的文字"的程序。
- 渲染接口和 issue 页面在前端可能还有细微差别（待验证）。
- 公式和画图是在浏览器里画的，接口看不出效果，要单独处理。
- 不可见的 Unicode 字符，渲染接口原样保留，仍然要自己处理。

## 七、决定和规则清单

**用户决定（2026-10-27）：按官方项目的做法，走路线一，在原文上按规则清洗。** 路线二（以渲染结果为准）没有采用：调研没有找到哪一家这样做，且要多写一段把网页转回文字的程序。路线一会漏掉第三节的部分边角情况，例如没闭合的注释吞掉后文、画图代码块里的注释；漏掉的由权限结构兜底：agent 没有令牌、没有 sudo、上网受限，发布前检查产出，PR 只能是草稿。

**规则（用户 2026-10-27 定）：以 GitHub 官方 MCP 服务器的做法为准，再加"删 HTML 注释"一条。** 代码按源码改写成 Python，保留原项目的 MIT 版权声明。

1. **正文：删不可见字符。** 照 MCP 服务器的 `FilterInvisibleCharacters`（`pkg/sanitize/sanitize.go`，提交 `25f11e629c`）：删标签字符、双向控制符、零宽空格、BOM、软连字符等；变体选择符只留"紧跟在可见字符后面的第一个"；保留 ZWJ。MCP 服务器读 issue 正文时只做这一步（`sanitize.Content`）。
2. **正文：删 HTML 注释。** 照 gh-aw 的 `removeXmlComments`（`actions/setup/js/sanitize_content_core.cjs` 第 839–870 行），能处理嵌套和以 `--!>` 结尾的注释，代码块里的不删。加这一条，是因为 Copilot 文档点名过滤 HTML 注释，codex-action 文档也点名注释是藏字的地方；样本里 13% 的 issue 带模板注释，删掉没有损失。
3. **标题：删不可见字符，再去掉 HTML 标签。** 照 MCP 服务器的 `sanitize.PlainText`。
4. **作用范围**：被引用的 issue 也照此处理。检查模型和 agent 都只读清洗后的那一份。
5. **ZWNJ（零宽不连接符）照源码删**（用户 2026-10-27 定："和 GitHub 官方完全一致，不做任何改动"）。代价已知：波斯文、印地文等靠它控制字母连不连写，删掉后个别词会连写变形；样本里 34 篇波斯文 issue 用到了它。
6. **不做的**：删链接标题、删 HTML 属性、解码实体、抹掉密钥（发布前检查产出时另做）、以渲染结果为准、全角转半角、NFKC、同形字替换、网址过滤。

**实现和实测（2026-10-27）。** 代码在 `src/repoaegis/sanitize.py`，测试 `tests/test_sanitize.py` 照搬两家原版测试用例，全部通过。在 2,423 篇真实正文上跑正式代码的结果：

- 348 篇（14.4%）删了 HTML 注释；
- 41 篇（1.7%）删了不可见字符，其中 34 篇是波斯文的 ZWNJ；
- 39 个标题有改动，几乎都是 `<`、`>` 被写成 `&lt;`、`&gt;`，比如 "versions >= v1.3.7" 变成 "versions &gt;= v1.3.7"，这是 MCP 服务器 `PlainText` 的原样行为；
- 出现了一处"删掉复现材料"：rich #3947 讨论表情处理，代码里的字面量 `'️'` 因为前面是引号，被当成孤立的变体选择符删掉了。

另外照搬了 gh-aw 的一个特性：它用 JavaScript 正则判断代码块围栏，`.` 不匹配 `\r`，所以用 `\r\n` 换行的正文认不出围栏代码块，里面的注释会被当成普通注释删掉。样本里实测没有一篇因此误删。

**明知漏掉的**（由权限结构兜底）：链接的悬停标题、`[//]: # (…)` 这类链接定义行、写成 `&#xE0041;` 的实体（MCP 服务器读正文时不解码实体，模型却能自己解出来）、没闭合的注释吞掉后文、画图代码块和公式里的藏字。
