标注约定：
- **出处**：仓库 + 文件路径 + 行号，或文档页面 + 行号/小节标题，都是本次亲自打开读过的。
- **实测**：本次在本机实际看过的。
- **推断**：根据源码或文档推出来的，原文没有直接这样写。
- **未找到**：找过但官方源码/文档里没有。

先解释三个后面反复出现的词：
- **会话记录**（transcript / trajectory / rollout / event log）：agent 和模型来回的每一条消息、每次调用工具和工具的输出，按顺序存下来的文件。各家叫法不同，指的是同一类东西。
- **续跑**（resume）：读回会话记录，让模型带着之前的全部对话接着往下做，而不是从头开始。
- **检查点**（checkpoint）：某个时刻的"存档"，出了问题能退回到这里。有的项目存的是代码文件，有的存的是对话。

## 1. GitHub Copilot 编码 agent（现在文档里叫 "Copilot cloud agent"）

来源：`github/docs` 仓库，提交 `02c25d16`（2026-10-23）。旧路径（如 `about-coding-agent`、`using-the-copilot-coding-agent-logs`）已经改名，在新文件的 `redirect_from` 里能看到旧地址（`content/copilot/how-tos/copilot-on-github/use-copilot-agents/manage-and-track-agents.md` 第 11–20 行）。

Copilot 是闭源的，下面全部来自官方文档，内部实现看不到。

### 1.1 边做边推送吗
- 打开任务后**马上**开一个草稿 PR，然后"边做边把改动推到这个 PR 上"，做完再把发起人加为审查人。出处：`content/copilot/how-tos/use-copilot-agents/cloud-agent/use-cloud-agent-on-github.md` 第 128 行；`.../cloud-agent/use-cloud-agent-with-mcp.md` 第 34 行（"As it works, it will push changes to the pull request"）。
- 推送前会先在临时环境里跑测试和代码检查（linter）。出处：`manage-and-track-agents.md` 第 33 行；`troubleshoot-cloud-agent.md` 第 92 行。
- 分支、提交说明、推送都由 Copilot 自己处理。出处：`content/copilot/concepts/copilot-surfaces/copilot-on-github.md` 第 64 行。
- 每个提交的作者是 Copilot，发起人列为共同作者；**每条提交说明里都带一个指向会话日志的链接**；提交有签名，显示 "Verified"。出处：`manage-and-track-agents.md` 第 37 行。
- **多久推一次、由什么触发推送**：未找到。文档只说"边做边推"。（推断：由 agent 自己在工作中决定推送时机，不是定时推。）
- 只能推到一个分支：新任务推到新建的 `copilot/` 分支；在已有 PR 里 @copilot 时推到那个 PR 的分支。出处：`content/copilot/concepts/security-governance-and-network-settings/risks-and-mitigations.md` 第 37 行。

### 1.2 时长上限、超时、被停止
- **每次会话最长 59 分钟，不能延长**；超时就停止。可以在 `copilot-setup-steps.yml` 里用 `timeout-minutes` 设得更短（最大 59）。出处：`copilot-on-github.md` 第 140–142 行；`.../customize-cloud-agent/customize-the-agent-environment.md` 第 93 行。
- 看起来卡住时："如果一直卡着，一小时后会超时"。出处：`troubleshoot-cloud-agent.md` 第 76–80 行。
- **点 "Stop session" 会结束对应的 GitHub Actions 运行，已经推送的提交保留**。出处：`manage-and-track-agents.md` 第 56 行。这说明 Copilot 本身就是跑在 GitHub Actions 上的（`troubleshoot-cloud-agent.md` 第 92 行也说"powered by GitHub Actions"）。
- 环境准备步骤（setup steps）失败时，跳过剩下的准备步骤，带着当前环境继续干活，而不是整个失败。出处：`customize-the-agent-environment.md` 第 105 行。
- 通过 API 查任务状态，状态有：`queued`、`in_progress`、`completed`、`failed`、`idle`、`waiting_for_user`、`timed_out`、`cancelled`。出处：`.../cloud-agent/use-cloud-agent-via-the-api.md` 第 89 行。也就是说官方把"失败"、"超时"、"被取消"分成了不同状态。

### 1.3 有没有自动重试
- **未找到任何自动重试的说法**。文档给的是手动办法：卡住超时后，"把 issue 取消指派再重新指派给 Copilot"来重试；回应评论时卡住，就"把同样的评论再发一次"。出处：`troubleshoot-cloud-agent.md` 第 80、82 行。

### 1.4 能否在同一个 PR 上继续
- 能。在任何 PR 的评论里 @copilot，它会开一个**新会话**，默认把新提交推到这个 PR 的分支。出处：`use-cloud-agent-on-github.md` 第 145–147 行。
- 新会话开始时，评论上出现 👀，PR 时间线出现 "Copilot started work"。出处：同文件第 168 行（"Tracking and continuing a session" 小节）。
- "Copilot 会记住同一个 PR 上之前会话的上下文，所以后续请求更快更可靠"。出处：同文件第 172 行。**它具体记住什么（是读回完整会话记录，还是一份摘要）未找到。**
- 会话进行中还可以在网页上追加指令（steering，"中途引导"），它在当前工具调用结束后执行。出处：`manage-and-track-agents.md` 第 39–50 行。

### 1.5 会话日志存在哪、谁能看、存多久
- 会话跑在 GitHub 托管的临时环境里，**会话结束环境就销毁，但会话日志留在 github.com 上**。出处：`content/copilot/concepts/security-governance-and-network-settings/session-data.md` 第 44 行。
- 日志内容：Copilot 的"内部推理"（internal reasoning）和它用过的工具。出处：`manage-and-track-agents.md` 第 33 行；`agent-management.md` 第 42 行说能实时看"思考过程"。
- 谁能看：**默认共享**，仓库里有访问权限的人都能在仓库的 "Agents" 标签页看到。出处：`manage-and-track-agents.md` 第 70 行；`session-data.md` 第 44 行。
- 删除：cloud agent 会话**只能归档，不能删除**。出处：`manage-and-track-agents.md` 第 66 行；`session-data.md` 第 98 行的表格。
- **保留多久：未找到**。
- 对日志有没有做脱敏：**未找到**。只知道 agent 拿不到仓库/组织的 Actions secrets，只能拿到放在 `copilot` 环境里的 secrets（`content/copilot/responsible-use/agents.md` 第 207 行）。

## 2. claude-code-action 与 Claude Code / Claude Agent SDK

### 2.1 claude-code-action（`anthropics/claude-code-action`，提交 `925afb53`，2026-10-24）

**它怎么调用 agent**：通过 Claude Agent SDK 的 `query()` 一次跑完。出处：`base-action/src/run-claude-sdk.ts` 第 4、190 行。

**会话记录**：
- 把 SDK 吐出的**所有消息**收集起来，跑完（或出错时）写成一个 JSON 文件 `$RUNNER_TEMP/claude-execution-output.json`（`RUNNER_TEMP` 是 Actions 机器上的临时目录）。出处：`base-action/src/execution-file.ts` 第 6–12、25 行；`run-claude-sdk.ts` 第 212–216 行（出错时也写）、第 222 行（正常结束时写）。
- 这个文件路径作为 action 的输出 `execution_file` 提供给后续步骤。出处：`action.yml` 第 173–175 行。
- 会话 ID 从第一条 `system/init` 消息里取出来，作为输出 `session_id`，说明文字是"可以配合 `--resume` 继续这次对话"。出处：`action.yml` 第 185–187 行；`run-claude-sdk.ts` 第 227–234 行。
- **action 自己没有把会话记录上传成 Actions 产物（artifact）**：整个仓库的 `action.yml`、`src`、`docs`、`examples` 里都搜不到 `upload-artifact`。（实测：grep）
- **action 自己没有用续跑**：`src`、`base-action/src`、`docs` 里搜不到 `resume`/`continue` 的调用，只是把 `session_id` 暴露出来。（实测：grep）机器跑完就销毁，`~/.claude/projects/` 下的原始记录也跟着没了（推断）。

**日志脱敏**：
- 默认在 Actions 日志里只打印两类消息：初始化（只显示模型名）和最终结果（只显示 `subtype`、是否出错、耗时、轮数、花费等），其他消息不打印。出处：`run-claude-sdk.ts` 第 114–160 行。
- 打印 SDK 选项时去掉了 `env` 和 `extraArgs`，"因为可能含敏感数据"。出处：同文件第 182–184 行。
- 开 `show_full_output: true` 才打印全部消息，文档明确警告"可能暴露密钥"。出处：`docs/security.md` 第 181–205 行。
- 注意：脱敏只针对**打印到 Actions 日志**的内容，写进 `claude-execution-output.json` 的是全部原始消息（出处：`execution-file.ts` 第 25 行直接 `JSON.stringify(messages)`）。

**超时与重试**：
- 旧版输入参数 `timeout_minutes` 已删除，改用 GitHub Actions 自带的作业级 `timeout-minutes`。出处：`docs/migration-guide.md` 第 29、209–219、341 行。
- 轮数上限通过 `claude_args: --max-turns N` 传。出处：`docs/migration-guide.md` 第 23 行。
- action 里的 `retryWithBackoff` 只用于 **GitHub API 调用**（拿令牌、建分支、更新引用），默认 3 次，首次等 5 秒，每次翻倍，最多 20 秒。出处：`base-action/src/retry.ts` 第 1–19 行；`src/github/token.ts` 第 168–174 行；`src/github/operations/branch.ts` 第 395 行。
- **模型接口的重试不在 action 里，而在 Claude Code 本体里**（见 2.2）。

**进度与提交**：
- 提示词要求 agent 在 issue/PR 评论里维护一个待办清单，每完成一项就更新评论（工具 `mcp__github_comment__update_claude_comment`）。出处：`src/create-prompt/index.ts` 第 596–597、714–757 行。
- 提交由 agent 自己用 `git commit` + 推送脚本完成（或开启签名时用 `commit_files` 工具）。出处：同文件第 397–457 行。**多久推一次由 agent 自己决定，action 不强制**（推断）。
- **收尾兜底**：跑完后（不论成功失败，在 `finally` 里）检查 agent 的分支：如果一个提交都没有，但工作区有没提交的改动，就自动 `git add -A`、提交（说明为 "Auto-commit: Save uncommitted changes from Claude"）、推送；如果既没提交也没改动，就删掉这个空分支。出处：`src/github/operations/branch-cleanup.ts` 第 74–130、143–146 行；`src/entrypoints/run.ts` 第 325–356 行。
- 一个小插曲：action 收到最终结果消息后主动 `break`，注释说某些 PR 触发的运行里 SDK 迭代器不关闭，会一直挂到作业超时、而且不写执行记录文件。出处：`run-claude-sdk.ts` 第 198–209 行。（官方 SDK 文档反而建议"不要在 result 上 break"，见 `agent-loop.md` 第 63 行；这是两边的已知分歧。）

### 2.2 Claude Code / Claude Agent SDK 的会话（官方文档 code.claude.com/docs，2026-10-24 抓取的 `.md` 原文）

**存在哪、存什么**：
- 会话记录在 `~/.claude/projects/<把工作目录路径编码后的名字>/<会话ID>.jsonl`，一行一条，内容是"完整对话：每条消息、每次工具调用和工具结果"。出处：`claude-directory.md` 第 112 行；`agent-sdk/sessions.md` 第 269 行。
- 子 agent 的记录、超大工具输出另存在 `<会话ID>/subagents/`、`<会话ID>/tool-results/`。出处：`claude-directory.md` 第 114–115 行。
- 默认 30 天后自动清理（`cleanupPeriodDays`）。出处：`claude-directory.md` 第 108 行。
- **明文存储、不加密**；"如果工具读了 `.env` 或命令打印了密钥，这个值就会写进 jsonl"——也就是**不做脱敏**。可以用 `-p --no-session-persistence` 或 `CLAUDE_CODE_SKIP_PROMPT_HISTORY` 完全不写记录。出处：`claude-directory.md` 第 193–199 行。
- 思考内容：**实测**本机一个会话文件里有 9 个 `"type":"thinking"` 块，每块都带 `signature`（模型返回的签名），其中 8 块的思考文字为空，1 块有文字。所以 jsonl 会保存思考块，但文字是否完整取决于模型返回了什么。官方文档里**未找到**对此的说明。

**怎么续跑**：
- 命令行：`claude --continue`（接着当前目录最近一次会话）；`claude --resume <ID或名字或jsonl路径>`（接指定会话）；加 `--fork-session` 则复制一份历史、用新 ID 往下走，原会话不变；`--session-id <UUID>` 指定新会话的 ID。出处：`cli-reference.md` 第 80、94、126、128 行。
- SDK：选项 `continue`（最近一次）、`resume=<会话ID>`、`fork_session`。会话 ID 在每条结果消息里都有，**成功或出错都有**。出处：`agent-sdk/sessions.md` 第 32–39、150 行。
- 官方明确列出的续跑场景之一："**从上限中恢复**：第一次运行以 `error_max_turns` 或 `error_max_budget_usd` 结束，用更高的上限续跑。" 出处：`agent-sdk/sessions.md` 第 218 行。
- 结束状态分类：`success`、`error_max_turns`（轮数到上限）、`error_max_budget_usd`（花费到上限）、`error_during_execution`（执行中被打断，例如请求被取消）。所有结果都带 `session_id`，"出错后也能续跑"。出处：`agent-sdk/agent-loop.md` 第 315–327 行。
- **跨机器续跑**（正好是我们"临时机器用完即毁"的情况），官方给了三条路（出处：`agent-sdk/sessions.md` 第 392–402 行）：
  1. 挂一个 `SessionStore` 适配器，把记录同步写到你自己的存储（对象存储、数据库等），另一台机器从同样的工作目录续跑。详见 `agent-sdk/session-storage.md` 开头："CI 运行器不共享文件系统……本地容器是临时的，外部存储能扛过重启"。
  2. 把 `~/.claude/projects/<编码后的目录>/<会话ID>.jsonl` 存下来，到新机器上放回 `~/.claude/projects/` 下任意目录，再 `resume`。
  3. **不依赖续跑**：把需要的结果（分析结论、决定、文件改动）当成应用自己的状态存起来，塞进**新会话**的提示词。原文说"这往往比搬运会话记录文件更稳"。
- 续跑只恢复对话，**不恢复工作目录里的文件**（推断：文档描述的续跑对象都是 transcript；文件回退是下面的检查点功能，且只回退 agent 用编辑工具改过的文件）。

**检查点（checkpointing）是什么**：
- 每当用户发一条开启新一轮的提示，Claude Code 自动存一份"改动前的文件快照"；保留最近 100 个检查点。出处：`checkpointing.md` 第 13–20 行。
- 快照存在 `~/.claude/file-history/<会话ID>/`，同样约 30 天后清理。出处：`claude-directory.md` 第 117 行；`checkpointing.md` 第 22 行。
- 检查点和会话一起保存，所以续跑后还能 `/rewind`（回退）。回退可以选"代码和对话一起回退"、"只回退对话"、"只回退代码"。出处：`checkpointing.md` 第 21、32–39 行。
- 局限：**只跟踪 Write/Edit/NotebookEdit 这些编辑工具改的文件；只被 bash 命令改过的文件不跟踪**；子 agent 的改动多数不跟踪；官方原话"不能代替版本控制（Git）"。出处：`checkpointing.md` 第 74–105 行。
- SDK 里对应 `enable_file_checkpointing=True` + `rewind_files(检查点ID)`；只回退磁盘上的文件，不回退对话。出处：`agent-sdk/file-checkpointing.md` 第 13–23、143 行。

**模型接口出错重试**：
- 临时性故障（服务端错误、过载、断线、429 限流等）**最多重试 10 次，指数退避**。出处：`errors.md` 第 444 行（"Automatic retries" 小节）。
- 不重试的情况里有一条很关键：如果模型**已经输出完一段文字或一个工具调用之后**才断，Claude Code 不会整个重发，因为"可能把同一个工具调用执行两次"；它保留已完成部分，接着往下走。出处：`errors.md` 第 466–468 行附近（"Claude Code doesn't retry these failures"）。
- 单次请求等响应头的超时 `API_TIMEOUT_MS` 默认 10 分钟。出处：`env-vars.md` 第 180 行。

## 3. OpenAI Codex CLI 与 openai/codex-action

### 3.1 Codex CLI（`openai/codex`，提交 `970111f6`，2026-10-23）

**会话记录（Codex 叫 rollout）**：
- 位置：`~/.codex/sessions/年/月/日/rollout-<时间>-<会话ID>.jsonl`（`CODEX_HOME` 可改根目录）；归档的放 `archived_sessions`。出处：`codex-rs/rollout/src/lib.rs` 第 86–87 行；`codex-rs/rollout/src/recorder.rs` 第 82 行（注释里的示例路径）、第 1770–1780 行（按年/月/日建目录）；文件名解析见 `codex-rs/rollout/src/rollout_file_name.rs` 第 39–58 行。
- 格式：JSONL，一行一个条目。写进去的东西由 `codex-rs/rollout/src/policy.rs` 决定：
  - 模型侧条目：消息、**推理（Reasoning）**、各种工具调用及其输出、网页搜索、压缩记录等都写；只有"压缩触发器"和未知类型不写。出处：`policy.rs` 第 80–99 行。
  - 会话元数据、每轮的上下文、token 用量、压缩结果等"执行标记"都写。出处：`policy.rs` 第 41–48 行。
  - 流式增量（一个字一个字的 delta）不写。出处：`policy.rs` 第 218–219 行附近。
  - 命令输出和 MCP 工具结果写入时截断到 64 KB。出处：`policy.rs` 第 16–19 行。
- 思考内容：`Reasoning` 条目包含 `summary`（推理摘要）和 `encrypted_content`（加密的推理内容）；如果模型返回了原始推理文本（`ReasoningText`），也会写进去。出处：`codex-rs/protocol/src/models.rs` 第 1095–1107、1773–1780 行。

**怎么记录哪些 issue 处理过**：
- 每个仓库一份 JSON 状态文档，存在自动化服务自带的键值存储里，键为 `state:{owner}__{repo}`；没有键值存储时退回本地 JSON 文件。出处：`state-schema.md` 第 17–42 行；`main.py` 第 254–354 行。

- 开工前**重新拉一次 issue**，如果标签已经被撤掉就跳过。出处：`main.py` 第 1184–1188 行。
- 每个任务记录：issue 号、标题、打标签事件 ID、基准分支和基准提交、工作分支、状态、对话 ID、本地克隆目录、最近活动时间、收尾尝试次数、PR 链接、完成时间、超时放弃时已跑秒数、最后错误。出处：`state-schema.md` 第 68–109 行。

**"超过 2 小时放弃"怎么实现**：
- 常量 `MAX_ACTIVE_AGE = 2 * 60 * 60`。每次轮询收尾检查时，如果对话还没进终止状态（`idle`/`finished`/`error`/`stuck` 之外）且距 `last_activity` 已超过 2 小时，就把任务标为 `expired`，在 issue 里评论"OpenHands 放弃了，没开 PR"，并释放克隆目录。出处：`main.py` 第 181–185、987–1004 行。
- 也就是说它**不是在 agent 里面计时**，而是外部轮询器看墙钟时间判断。

**失败后会不会重试**：
- 对话以 `error` 或 `stuck` 结束 → 标为 `failed`，在 issue 里评论并附对话链接，**不自动重试**。出处：`main.py` 第 1023–1036 行。
- 对话结束后，**推送和开 PR 这一步**失败（例如 GitHub 临时故障）→ 保留任务和克隆目录，**下次轮询再试，最多 3 次**；3 次都失败才标 `failed` 并评论原因。出处：`main.py` 第 192–195、1095–1121 行。注释原意："推送和开 PR 发生在 agent 停止之后，GitHub 一次临时故障不该把活扔掉"。
- 错误信息写进状态和公开评论之前，先把 GitHub 令牌替换成 `***`。出处：`main.py` 第 508–509、1101–1103 行。
- 唯一的"人工重试"方式是重新打标签（产生新事件 → 新任务）。出处：`state-schema.md` 第 62–64 行。
- 其他收尾细节：agent 被要求自己推送并开 PR；收尾时**向 GitHub 查证 PR 是否真的存在**（"报告不算证据"）；agent 没提交的改动由脚本代为 `git add -A` 并提交；一个提交都没有就标 `no-changes` 并把 agent 的回答贴到 issue。出处：`main.py` 第 1047–1093、595–612 行。
- issue 在 agent 工作期间被关闭 → 标 `issue-closed`，不开 PR。出处：`main.py` 第 1006–1015 行。

- **没有自动提交**：到上限时 `submission` 直接是空字符串。出处：`default.py` 第 137、145 行。
- 批量跳过：看输出目录下的 `preds.json`，里面有的实例 ID 就跳过；**出错的实例也会写进 `preds.json`（结果为空），所以默认也会被跳过**，要用 `--redo-existing` 才重跑。出处：`run/benchmarks/swebench.py` 第 155–176、212、229–232 行。
- 没有续跑、没有重放命令（`run/` 下搜不到 `resume`/`replay`）。
- 模型接口重试：默认 10 次（环境变量 `MSWEA_MODEL_RETRY_STOP_AFTER_ATTEMPT` 可改），指数退避 4–60 秒；鉴权失败、上下文超长、模型不存在、参数不支持等直接放弃。出处：`models/utils/retry.py` 第 19–25 行；`models/litellm_model.py` 第 50–57 行。
- 思考内容：因为存的是整个原始响应，模型返回的思考块会一起进轨迹（推断）；发给 Anthropic 模型前专门重排思考块（`models/utils/anthropic_utils.py` 第 4–8 行）。
- 脱敏：轨迹里写入模型和环境的完整配置（`model_dump`），**没有看到脱敏**；如果把 API key 写在模型参数里，会原样进轨迹（推断）。

## 7. 对比：存什么、存在哪、什么时候存、怎么恢复、失败怎么分类和重试

### 7.1 存什么

- **只把代码进度当存档**：Copilot（边做边推到 PR 分支，停了以后"已推送的提交保留"）、OpenHands issue-to-pr（工作分支 + 外部状态文档，对话记录留在 OpenHands 服务里只给链接）。
- **只存会话记录**：Codex（rollout）、OpenHands SDK（base_state + events）、SWE-agent / mini-swe-agent（.traj）。其中 SWE-agent 的"代码进度"是靠收尾时 `git diff` 生成补丁塞进轨迹，不是单独存。
- **两者都存**：Claude Code（会话 jsonl + `file-history` 文件快照）；claude-code-action（执行记录文件 + agent 自己推的提交 + 收尾时自动提交没提交的改动）。

### 7.2 存在哪

- 存在**运行机器本地**的：Claude Code（`~/.claude/projects/`、`~/.claude/file-history/`）、Codex（`~/.codex/sessions/年/月/日/`）、OpenHands SDK（`persistence_dir`）、SWE-agent / mini-swe-agent（输出目录）。机器一毁就没了。
- 存在**机器之外**的：Copilot 的会话日志（github.com，默认仓库内共享，只能归档不能删）、Copilot 的代码（PR 分支）、OpenHands issue-to-pr 的任务状态（自动化服务的键值存储）、Claude Agent SDK 可选的 `SessionStore`（你自己的存储）。
- 在 GitHub Actions 上跑的两个官方 action（claude-code-action、codex-action）**都没有上传会话记录**；只有 OpenHands 的 pr-review action 用 `if: always()` 上传日志 artifact（保留 7 天），Codex 文档示例上传的是补丁而不是会话记录。

### 7.3 什么时候存

- **每一步/每条消息就写**：Claude Code jsonl（推断：追加写）、Codex rollout（源码里是后台写入任务逐条写）、OpenHands SDK（每个事件一个文件、状态字段一变就存）、SWE-agent 和 mini-swe-agent（每步整个重写）。
- **跑完或出错时写一次**：claude-code-action 的执行记录文件（`finally`/`catch` 里写）。
- **每轮用户提示前存一次**：Claude Code 的文件检查点。
- **由 agent 自己决定何时推送**：Copilot、claude-code-action 的提交（推断）。

### 7.4 怎么恢复

- **原样续接（带着完整对话接着跑）**：Claude Code / SDK（`--resume`、`--continue`、`resume=`；官方点名可用于 `error_max_turns`/`error_max_budget_usd` 之后）、Codex（`codex exec resume`）、OpenHands SDK（同 ID + 同目录重建，`error`/`stuck` 状态下再 `run()` 就继续）、旧版 OpenHands（pickle 状态 + 事件流）。共同前提：**会话记录文件要在**；跨机器要自己搬文件或接外部存储（Claude 文档第 392–402 行专门讲了）。
- **只告诉 agent 进度（开新会话，把已有成果喂给它）**：Copilot 在 PR 上 @copilot 开的是**新会话**，"记住之前会话的上下文"（具体机制未公开），代码进度靠 PR 分支本身；Claude 官方文档把"不依赖续跑、把需要的结果作为状态塞进新会话"列为跨主机的第三种方案，并说"往往更稳"。
- **不恢复，只重做或重放**：SWE-agent（跳过已完成实例；`run-replay` 只是重新执行动作做示范/调试）、mini-swe-agent（跳过已完成实例）、OpenHands issue-to-pr（失败就结束，重新打标签才会再来一次，而且是全新任务、新分支）。
- **回退**（不是续跑，是退回去）：Claude Code 检查点（`/rewind`、`rewind_files`），只管编辑工具改的文件，官方说不能替代 Git；Codex 的 git 快照撤销功能已移除。

### 7.5 失败怎么分类、怎么重试

**分类**（越往后越细）：
- Copilot：`completed` / `failed` / `timed_out` / `cancelled` 等任务状态（API 文档）。
- Claude Agent SDK：`success` / `error_max_turns` / `error_max_budget_usd` / `error_during_execution`。
- OpenHands SDK：终止状态 `finished` / `error` / `stuck`，`error` 再用错误事件的 `code` 区分（`MaxIterationsReached`、`MaxBudgetReached`、`LLMAuthenticationError`、异常类名）。
- OpenHands issue-to-pr（任务层面）：`closed`（已开 PR）/ `no-changes` / `failed` / `expired`（超 2 小时）/ `issue-closed`。
- mini-swe-agent：`Submitted` / `LimitsExceeded` / `TimeExceeded` / `RepeatedFormatError` / 异常类名。
- SWE-agent：最细，9 种 `exit_*`，并且大多数会自动提交已有改动、变成 `submitted (exit_xxx)`。

**重试分三层，各家做法很一致**：
1. **模型接口这一层，全都自动重试，指数退避**：Claude Code 最多 10 次；Codex 请求 4 次 / 流式 5 次，从 0.2 秒翻倍；OpenHands 5 次，8–64 秒；SWE-agent 20 次，10–120 秒；mini-swe-agent 10 次，4–60 秒。**鉴权失败、上下文超长、额度用光、内容审核这类"重来也一样"的错误，各家都不重试**。Claude Code 还特意规定：模型已经输出完一个工具调用后才断的，不整个重发，以免同一个工具执行两次。
2. **模型输出格式不对这一层，重问几次**：SWE-agent 3 次、mini-swe-agent 连续 3 次、Claude Code 对"说要调工具却没给工具调用"重问 2 次；OpenHands 对连续报错先"提醒一次"。
3. **整个任务这一层，基本都不自动重试**：Copilot 无自动重试（手动重新指派或重发评论）；claude-code-action、codex-action 无；OpenHands issue-to-pr 对话失败不重试，只对"推送 + 开 PR"这个收尾步骤重试最多 3 次（理由是工作已经做完，别因 GitHub 临时故障丢掉）；SWE-agent 的 `RetryAgent` 是唯一的"整体重来"，但它的目的是"多试几次挑最好的"，每次重置环境、从零开始，而不是"失败了接着做"。

**和我们最相关的几个现成做法**（只列事实，不替你做决定）：
- 时间上限：Copilot 用 59 分钟硬上限 + Actions `timeout-minutes`；OpenHands issue-to-pr 用外部轮询器看墙钟（2 小时）。
- 已有改动不丢：Copilot "停止时已推送提交保留"；claude-code-action 收尾时自动提交未提交的改动；SWE-agent 出错时自动收成补丁；OpenHands issue-to-pr 收尾时代为提交。
- "只处理一次"的依据：OpenHands issue-to-pr 用"打标签事件 ID"做键，先认领再干活，认领 15 分钟无进展就释放。
- 会话记录留存：只有 Copilot 把日志留在机器之外（且默认仓库内公开）；GitHub Actions 上的官方 action 都不上传会话记录。
