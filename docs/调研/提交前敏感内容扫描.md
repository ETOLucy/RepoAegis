# 调研：提交前怎么拦住敏感内容

读取和实测日期：2026-10-30。版本号、规则数以后会变。

## 为什么查

RepoAegis 是公开仓库。本机的 `.env` 里有 DeepSeek 密钥和 GitHub 令牌，WSL 里有 Langfuse 密钥。要求是：**暂存区里只要出现敏感内容（密钥、令牌、私钥、环境变量文件等），就不许提交**——不是拿已知的密钥值去比对，而是按"长得像密钥"来认，没见过的密钥也要拦。

`.gitignore` 已经排除了 `.env`，但它只管 `git add .` 时不带上 `.env`；`git add -f` 强制添加、密钥被复制进别的文件、密钥写进提交说明，它都管不了。

## 方法和标注

- 用 `gh api` 读各工具仓库的信息、源码和发布页；用网页抓取读 GitHub 文档。
- 【原文】= 打开了一手来源；【实测】= 在本机跑过；【推断】= 根据前两者推出来的。

## 数据

### 三个现成工具

**gitleaks**【原文：`gh api repos/gitleaks/gitleaks`、`releases/latest`】
- MIT 许可，约 3 万星，2026-10-28 仍有提交；最新版 v8.30.1（2026-03-21），发布页有 Windows 和 Linux 的单文件程序，各约 8MB。
- 自带规则 222 条，包括 `github-pat`、`openai-api-key`、`private-key`，和一条"通用 API 密钥"规则 `generic-api-key`。【原文：`config/gitleaks.toml`，`[[rules]]` 计数；第 636–660 行】
- **没有 DeepSeek 规则**。通用规则只认"名字 + 等号/冒号 + 值"的写法（正则见上述第 638 行附近），单独出现的 `sk-...` 认不出。【原文】
- 能在规则文件里写 `[extend] useDefault = true` 沿用自带规则，再加自己的规则；规则可以只按文件路径匹配。【原文：README "Load Configuration" 一节】
- 自带的全局放行名单会跳过图片、字体、Office 文档、PDF 等文件（`gitleaks.toml` 第 22–50 行）。用 `useDefault` 时放行名单是"追加"的，我们关不掉。【原文：README 同一节 "Allowlist arrays are appended"】
- 行尾写 `gitleaks:allow` 可以放行这一行；加 `--ignore-gitleaks-allow` 可以关掉这个口子。`--redact` 让输出不显示密钥本身。【原文：README Usage 一节】
- 扫暂存区的命令是 `gitleaks git --pre-commit --staged`。【原文：`cmd/git.go` 第 17–18 行】

**trufflehog**【原文：`gh api repos/trufflesecurity/trufflehog`】
- AGPL-3.0 许可，约 2.9 万星，v3.99.7（2026-10-24）。
- 有 DeepSeek 和 Langfuse 识别器。DeepSeek 识别器的格式是 `sk-[a-z0-9]{32}`，但要求附近出现 "deepseek" 这个词才算。【原文：`pkg/detectors/deepseek/deepseek.go` 第 28 行】Langfuse 的格式是 `pk-lf-`/`sk-lf-` 加 UUID。【原文：`pkg/detectors/langfuse/langfuse.go` 第 25–26 行】
- 它的强项是把找到的密钥拿去调对应服务的接口，验证是否真能用。放在提交前，每次提交都要联网，还会把疑似密钥发给对方。【原文：README `--results=verified` 各例；推断：对提交前检查的影响】

**detect-secrets**（Yelp）【原文：`gh api repos/Yelp/detect-secrets`】
- Apache-2.0，最新版 v1.5.0 是 2024-05-06 发布的，只有 Python 版。Windows 这边没有 Python，Git Bash 里提交时跑不了。

### GitHub 自己的推送拦截

- RepoAegis 是公开仓库，已开启 secret scanning 和 push protection。【实测：`gh api repos/ETOLucy/RepoAegis` 的 `security_and_analysis`】
- GitHub 支持识别的密钥种类里有 "DeepSeek API Key"（`deepseek_api_key`），标为支持推送拦截。【原文：docs.github.com supported-secret-scanning-patterns 页，经网页抓取工具摘出这一行】实际能否拦住，未实测。
- 推送拦截能被推送的人在页面上手动放行。【推断，未查文档原文】

### 本机实测

- 用新规则扫真实的 `.env` 和 `langfuse.env`（只在本机，输出遮盖）：DeepSeek 密钥命中 `deepseek-api-key`，GitHub 令牌命中自带的 `github-pat`，`.env` 文件本身命中 `env-file`，两把 Langfuse 密钥都命中 `langfuse-api-key`；报告里真实值出现 0 次。【实测】
- **`gitleaks git --pre-commit --staged` 会漏掉二进制文件**：它扫的是 `git diff`，含空字节的文件在 diff 里只有一句 "Binary files differ"，整个被跳过，按文件名拦的规则也就失效了。同样暂存 `cert.p12`（二进制）、`id_rsa`（二进制）、`text.p12`（文本）三个文件，这个模式只报出 `text.p12`；先用 `git checkout-index` 把暂存内容导出到临时目录，再用 `gitleaks dir` 扫，三个都报出。【实测】
- 用假密钥在临时仓库里测钩子，Git Bash 和 WSL 各 13 项全部符合预期：干净文件、`.env.example` 通过；单独一行的 DeepSeek 密钥、带 `gitleaks:allow` 的行、中文 Markdown 里的 Langfuse 密钥、yml 里的 GitHub 令牌、txt 里的私钥、强制添加的 `.env`、子目录里的 `.env.local`、二进制 `cert.p12`、在已有文件里追加密钥、提交说明里的密钥、找不到 gitleaks，全部拒绝；输出里没有出现假密钥。【实测】
- 第一版钩子把退出码取晚了，取到的是后面一句赋值的结果，导致发现密钥也放行；测试发现后已改。【实测】
- 用新规则扫 RepoAegis 现有的 71 个文件（已跟踪和未跟踪），没有误报。【实测】

## 借鉴什么、不借鉴什么

- **gitleaks：采用。** 单文件程序、两边都能跑、离线、规则可扩展、能遮盖输出。不用它的 `--pre-commit` 模式（漏二进制），改为导出暂存内容后按目录扫。
- **trufflehog：只借鉴它的 DeepSeek 和 Langfuse 密钥格式**，写成我们自己的 gitleaks 规则，并去掉"附近要有 deepseek 这个词"的条件。不采用它本身：联网验证不适合提交前检查，AGPL 许可也比 MIT 重。
- **detect-secrets：不采用。** Windows 这边跑不了，且两年多没发新版。
- **原先的"拿真实值逐字比对"脚本：不再使用。** 它只能拦已知的密钥，不符合"按特征认"的要求。

## 结论（2026-10-30 用户确认用 gitleaks）

1. 仓库根目录的 `.gitleaks.toml`：沿用 gitleaks 自带规则，另加 DeepSeek 密钥、Langfuse 密钥两条内容规则，以及 `.env` 类文件、私钥和证书容器文件两条只看文件名的规则。
2. 本机 `.git/hooks/pre-commit` 和 `.git/hooks/commit-msg` 装同一个脚本：前者把这次新增或改动的文件导出后用 `gitleaks dir` 扫，后者用 `gitleaks stdin` 扫提交说明；都加 `--redact --ignore-gitleaks-allow`；找不到 gitleaks 或规则文件也拒绝提交。
3. gitleaks 8.30.1 装在 Windows 的 `~/bin/gitleaks.exe` 和 WSL 的 `~/.local/bin/gitleaks`，下载后按官方校验文件核对过哈希。

## 已知的漏洞

- `git commit --no-verify` 能跳过所有提交前检查，这是 git 的设计，本地没法禁止。
- gitleaks 自带的放行名单会跳过图片、PDF、Office 文档等，这些文件里的密钥拦不住。
- 钩子在 `.git/hooks/` 里，不随仓库走：换一台电脑或重新克隆，要重新装。
- 钩子读的是工作区里的 `.gitleaks.toml`，如果同一次提交里把规则改松，这次提交就按改松后的规则扫。

## 尚未查清的

- GitHub 推送拦截实际能否认出 DeepSeek 密钥（可用假密钥向临时分支推一次实测）。
- 是否要在 GitHub 上再加一道服务端扫描（比如推送后自动跑 gitleaks 的工作流），堵上 `--no-verify` 的口子。

## 不做的

- 不加"按公司名等关键词拦截"的规则（2026-10-30 用户决定）：用户的意思是公司项目放在另外的文件夹、别和这里混在一起即可，而关键词规则本身得在本地存一份词表。实测当天仓库文件和全部提交历史里都没有这类内容。
