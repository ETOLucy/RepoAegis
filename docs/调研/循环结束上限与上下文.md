标注约定：【一手】是读到了源码、官方文档或论文原文，写明文件和行号（子 agent 当时没记行号的写函数名或章节）；论文数字是子 agent 读 arXiv 网页版、经抓取工具摘出来的，本次没有逐页再对。【实测】是在本机数据上算出来的。【推断】是从源码或数据推出来的，原文没有直说。【待验证】是只读到摘要、二手转述，或者没找到出处。

## 一、为什么查

RepoAegis 的 agent 跑在 GitHub Actions 里：读 issue、改代码、交出补丁和汇报，然后由程序开草稿 PR。每个 issue 只处理一次，中途没人能跟它对话。工具已经定了四个（`bash`、`str_replace_editor`、`read_issue_ref`、`submit`，见 [agent 工具清单](agent工具清单.md)），循环照 mini-swe-agent 的结构自己写。剩下的问题是循环的"边"：什么时候算做完，要设哪些上限防止它一直跑下去，撞到上限或出错时怎么收场，对话记录越来越长怎么办。

这个问题最早是这样来的：之前提到过一个"固定 50 步硬上限"，你觉得太草率，会把没做完但正常推进的任务切断，上限应该只是防死循环的保险。那个 50 来自 OpenHands 旧版（V0）issue 解决器的示例配置，指的是"最多 50 个动作"，不是它现行产品的做法【一手】（`openhands/resolver/examples/openhands-resolver.yml`、`resolve_issue.py` 的 `--max-iterations` 默认 50，子 agent 读的是 0.59.0 标签，行号未记）。本文只用它说明来历，不拿它当依据。

还有两条已经定下的约束会影响结论。一是运行硬上限 60 分钟：到时间还没完成就停止，不开 PR，在 issue 里说明超时（见 [接收哪些 issue](../接收哪些issue.md) 规则 4）。二是 DeepSeek 在思考模式下不能强制模型"必须调用工具"，所以模型随时可能回一段不带工具调用的文字（见 [agent 工具清单](agent工具清单.md) 第六节）。

## 三、各家做法和数据

### 1. 循环什么时候算结束：几乎都是模型自己说了算

所有看过的项目，"做完了"都由模型自己宣布，系统只在外面加上限；没有一家把"测试通过"当成结束条件【一手】（结束判定那路子 agent 汇总的 Copilot、Codex、Claude Code、Devin、OpenHands、Jules、Cursor 文档）。宣布的方式分三种。

第一种是"不再调用工具就结束"。Claude Agent SDK 的循环是：回复里带工具调用就执行，再把结果喂回去，直到某次回复没有工具调用【一手】（agent loop 文档页）。Codex CLI 也是这样：`run_turn` 里是一个 `loop`，每圈问一次模型，模型这轮不需要继续（`needs_follow_up` 为假）时才收尾，收尾前还要过一道"停止钩子"，钩子可以要求继续【一手】（`codex-rs/core/src/session/turn.rs` 第 174、473、596、622、736 行起）。OpenHands 新版 SDK 里，模型回了一段纯文字也算结束，状态设为 FINISHED【一手】（`agent/response_dispatch.py` 第 270–281 行）；如果回复里既没有工具调用也没有文字，就插一条"请用工具继续"的提醒【一手】（同文件第 375–400 行）。

第二种是专门的结束工具。OpenHands 的 `finish` 工具就是这个用途，它的说明里写着做不到或缺信息时也要调用它，并说明原因【一手】（`tool/builtins/finish.py`，行号未记）。SWE-agent 的提交工具在默认配置里要调两次：第一次只返回改动和复查清单，第二次才真提交【一手】（`tools/review_on_submit_m/bin/submit`，见 [agent 工具清单](agent工具清单.md)）。

第三种是特殊命令。mini-swe-agent 让模型执行 `echo COMPLETE_TASK_AND_SUBMIT_FINAL_OUTPUT`，命令输出第一行是这个标记就算提交【一手】（`environments/local.py` 的 `_check_finished`）。模型没按格式调用工具时，mini 会把错误信息发回去让它重来，连续 3 次才退出【一手】（`agents/default.py` 的 `AgentConfig.max_consecutive_format_errors=3`）；它还专门处理了"模型输出太长、被截断在半路"的情况，提示它说短一点【一手】（`config/benchmarks/swebench.yaml` 第 159–161 行）。

我们的 `submit` 属于第二种。因为 DeepSeek 不能强制调用工具，"模型回了一段文字但没调 submit"一定会发生，这正是 mini 那套"打回重来、连续几次就放弃"要处理的情况【推断】。

### 2. 各家设了哪些上限

先解释两个词。"墙钟时间"就是真实流逝的时间，和模型调用了几次无关。"一步"在本文里指"问一次模型、执行一次它要的工具"。

| 项目 | 步数 | 费用 | 墙钟时间 | 原地打转检测 | 到上限后 |
|---|---|---|---|---|---|
| mini-swe-agent | 类默认 0（不限）；SWE-bench 配置 250 | 3 美元 | 类默认 0（不限） | 只有"连续 3 次格式错误" | 补丁记为空，等于没解决 |
| SWE-agent | 默认不限；只给 bash 的配置 250 | 3 美元 | 总执行时间 1800 秒；连续 3 次命令超时也退出 | 没有 | 把已有改动自动当补丁提交 |
| OpenHands 新版 SDK | 500 | 默认不限 | 没读到 | 默认开，四条规则 | 标为出错；打转则标为"卡住" |
| Codex CLI | 没有（循环里没有计数） | 没有 | 没读到 | 没读到 | 无从触发；上下文快满就压缩 |
| Claude Agent SDK | 默认不限，可设 | 默认不限，可设 | 没有 | 没读到 | 返回错误结果，保留会话可续跑 |
| Copilot | 未公开 | 未公开 | 单次最长 59 分钟，不能延长 | 未公开 | 超时停止 |
| DeepSWE 论文的评测 | 不设 | 不设 | 9000 秒 | 没有 | 按失败计分 |

出处逐行如下。mini：`agents/default.py` 的 `AgentConfig` 默认 `step_limit=0`、`cost_limit=3.0`、`wall_time_limit_seconds=0`，三项都在每次问模型之前检查【一手】（子 agent 记录里的源码原文，行号未记；退出状态见 [会话记录检查点](会话记录检查点与失败重来.md) 第 264–265 行）；SWE-bench 配置 `step_limit: 250`、`cost_limit: 3.`、单条命令超时 60 秒【一手】（`config/benchmarks/swebench.yaml` 第 112、113、117 行）。SWE-agent：`per_instance_cost_limit` 默认 3.0、`per_instance_call_limit` 默认 0、单条命令 30 秒超时【一手】（`models.py`、`tools/tools.py`，行号未记）；连续命令超时和总执行时间的判断【一手】（`sweagent/agent/agents.py` 第 970、1018 行）；`config/bash_only.yaml` 把调用上限设为 250【一手】。OpenHands：`max_iteration_per_run=500`、`stuck_detection=True`、`max_budget_per_run=None`【一手】（`conversation/impl/local_conversation.py` 第 231、232、249 行）；费用上限把 agent 和压缩用的模型调用都算在内【一手】（同文件第 743–757 行）；到了步数上限时，如果最后一步刚好完成，保留"完成"不改成出错【一手】（同文件第 2081–2108 行）；每次调用 `run()` 重新计数【一手】（见 [会话记录检查点](会话记录检查点与失败重来.md) 第 179 行）。Codex：`turn.rs` 里只有第 2831 行一处注释出现 iteration 一词，循环里没有步数计数【一手】；代码里还有一句注释，说只要压缩能把上下文压到上限以下，"就不必担心死循环"【一手】（第 693 行）。Claude Agent SDK：`max_turns` 只数带工具调用的轮，`max_budget_usd` 包含子 agent 的花费，两者默认都不限；费用在模型回复到达后才比较，所以可能超出一次回复的钱；文档示例写 `max_turns=30`，用途标注为"防止失控"【一手】（agent loop 文档页）。Copilot 的 59 分钟【一手】（见 [会话记录检查点](会话记录检查点与失败重来.md) 第 35 行）。DeepSWE【一手】（arXiv 2607.07946，节号未记）。

规律很清楚：产品类 agent（Codex、Claude Code）默认不限步数，靠模型自己停加上下文压缩；评测用的框架才设硬步数上限，目的是控制整套评测的总花费【推断】（两路子 agent 都这么总结，没有哪家原文这样说）。

### 3. 上限设多大：有哪些证据

先说结论：**没有找到"同一模型、同一框架、只改步数上限、看解决率怎么变"的对照实验。**下面都是侧面证据。

SWE-agent 论文用的不是步数而是费用：每题 4 美元，超了就把已有改动交出去，大约对应 30 到 40 轮；理由只写了"受预算限制"【一手】（2405.15793 附录 B.3.2、B.9）。它给了一组常被引用的数字：已解决的任务里 93.0% 在花光预算前就自己提交了，全部任务里这个比例是 69.0%；成功任务的步数中位数 12、费用 1.21 美元，失败任务的平均步数 21、费用 2.52 美元（一个是中位数一个是平均数，不能直接比）；作者据此猜测"提高预算不太可能明显提升表现"【一手】（同文 B.3.1）。这是推测不是实验，模型是 2024 年的 GPT-4 Turbo。

SWE-smith 给出了反面的情况：它的微调小模型（SWE-agent-LM-32B）用 75 步上限，超过一半没解决的任务是撞上步数或费用上限才停的，而且常常还没改源码【一手】（2504.21798 §4.2、附录 F.5）。它画过"步数上限和解决数"的曲线，但那是跑一次 75 步之后事后推算的，不是重跑【一手】。SWE-Lego 在它的微调模型上看到：轮数上限升高时，被截断的比例快速下降，约 140 轮后不再下降；解决率在中等轮数最高，太少（探索不够）或太多（多半卡住反复试）都偏低【一手】（2601.01426）。两篇都是微调小模型，不能直接推到我们用的模型。

最接近"上限只当保险"的公开做法是 DeepSWE 论文：用 mini-swe-agent，不设步数和费用上限，只设 9000 秒墙钟上限，7174 次评分运行里只有 67 次（0.9%）撞到它【一手】（2607.07946）。Anthropic 的 SWE-bench 文章也是"一直采样，直到模型认为完成，或超出 200k 上下文"，并提到有的任务超过 100 轮才提交【一手】（anthropic.com 的 SWE-bench Sonnet 文章）。

"失败的运行是不是更长、能不能用长度来判断该不该砍"，两篇论文结论相反：一篇说失败轨迹更长、波动更大，另一篇说控制任务难度后相关性反过来【待验证】（2511.00197、2604.02547，只读了摘要）。另一篇说准确率常在中等花费处见顶，同一题不同次运行 token 最多差 30 倍【待验证】（2604.22750，只读了摘要）。比较稳妥的理解是：步数长短主要反映题目难度，拿它来判断"该不该切"证据不足【推断】。

和我们最相关的是 DeepSeek 自己要走多少步。SWE-bench 榜单里有两条"mini-swe-agent + DeepSeek V3.2"的记录（各 500 题，Verified 集），数据文件里有每题的模型调用次数和是否解决。整理时我按成功、失败分开算了分布【实测】（`leaderboards.json` 里 `20260217_mini-v2.0.0_deepseek-3-2-high` 和 `20251201_mini-v1.17.1_deepseek-v3.2-reasoner` 两条的 `per_instance_details`；平均值和文件里的 `instance_calls` 88.506、46.404 一致）：

| 记录 | 解决率 | 成功的中位数 / 第 95 百分位 / 最大 | 失败的中位数 / 最大 | 成功运行里超过 50 步的 | 超过 100 步的 |
|---|---|---|---|---|---|
| mini 2.0.0 + V3.2（high） | 350/500 | 79 / 132 / 242 | 95 / 250 | 323 个（92%） | 78 个 |
| mini 1.17.1 + V3.2 Reasoner | 300/500 | 39 / 74 / 132 | 47 / 250 | 87 个（29%） | 3 个 |

这张表说明三件事。第一，同一个模型换了框架版本，步数就差将近一倍，所以别人的上限数字不能直接搬【实测】。第二，如果在 mini 2.0.0 那组上设 50 步上限，九成以上本来能成功的运行会被切断【推断】（假设撞上限之前的行为不变）。第三，两组分别只有 1 个和 2 个运行停在第 250 步【实测】，应是撞上了配置里的 250 步上限，说明宽上限只碰到极个别运行【推断】。要注意这是 V3.2 不是我们用的 `deepseek-flash`，任务是 SWE-bench 题不是真实 issue，每步耗时也不在数据里，所以 60 分钟够不够还得实测【待验证】。

### 4. 原地打转怎么办

"卡死检测"是指程序看最近几步，发现 agent 在重复同样的事就叫停。只有 OpenHands 做了，规则如下【一手】（`conversation/stuck_detector.py`）：只看上一条用户消息之后、最近 20 个事件（第 21、66–83 行）；同一动作得到同一结果连续 4 次；同一动作反复报同一个错，正好 3 次时先发一条"别再重复同样的调用，看看报错换个办法"的提醒，再多一次才判卡住（第 208–248 行）；agent 连续 3 条纯文字、没有动作（第 250–275 行）；两个动作交替出现 6 次（第 277–301 行）。第五条"反复撞上下文上限"目前是空函数，直接返回"没卡住"（第 146–149、314–323 行）。阈值 4、3、3、6 写在 `conversation/types.py` 的 `StuckDetectionThresholds` 里【一手】（子 agent 读的，行号未记）。主循环每步之前先检查：命中提醒就插入提醒继续跑，命中卡住就把状态设为"卡住"并停下【一手】（`local_conversation.py` 第 767–791、2034–2036 行）。这几个阈值为什么是 3、4、6，没找到依据；有人在 GitHub 上反映过误报【待验证】（子 agent 引用了 OpenHands 卡死检测文档页和 GitHub issue #762，本次没有再核对）。

有没有用？SWE-smith 的数据是：它的 32B 模型有 25% 以上的轨迹出现长度至少 10 的重复动作，Claude 3.7 Sonnet 不到 4%；出现这种重复的运行 89% 失败【一手】（2504.21798 §4.2、附录 F.5）。作者试了三种干预（重复时警告、重新采样、注入提示），重复是少了，解决数却降到 192 题（38.4%），他们的结论是重复是"题太难"的症状，不是病因【一手】（同上）。

另一个方向是"预测这次会失败就提前停"。FailFast 用一个 0.6B 的小模型看 issue 和最近 8 步，从第 20 步起判断；误报率控制在 5% 时省 14.6%–20.4% 的 token，而只按步数停的简单基线也能省 10%–12%；误报率放到 25% 并配合"带上旧改动重开"，Qwen3.6-27B 从 66.6% 升到 71.8%，但重开本身多花 20%–44% 的 token【一手】（2608.03222，只在 SWE-bench Verified 和 mini-swe-agent 上评测过）。没找到有产品在用【推断】。

### 5. 到上限或出错时怎么收场

各家分三种做法【一手】（各项目源码，见下）。

一是直接记失败。mini 撞上步数或费用上限时抛出 `LimitsExceeded`，提交内容是空字符串，评测脚本拿到空补丁就算没解决（`agents/default.py`、`run/benchmarks/swebench.py`；见 [会话记录检查点](会话记录检查点与失败重来.md) 第 264–265 行）。

二是把已有改动交出去。SWE-agent 几乎所有异常都走"自动提交"：在仓库里执行 `git add -A && git diff --cached`，把现有改动收成补丁（`sweagent/agent/agents.py` 第 823–868 行，命令在第 856 行）；如果运行环境已经死了，就用上一步记录下来的 diff（第 831–850 行）。触发它的有主动放弃、总时间超限、连续命令超时、上下文超长、费用超限、模型接口错误、环境错误、格式错误次数用尽（第 1150–1221 行）；唯一不走自动提交、直接抛出的是"整批任务的总费用超限"（第 1180 行附近）。OpenHands 旧版 issue 解决器撞上限后也会去取 git diff，再让模型判断成没成【一手】（`issue_resolver.py` 的 `complete_runtime`、`guess_success`）。

三是标成出错、保留状态，以后加大上限续跑。OpenHands 新版把状态设为 ERROR 并发出 `MaxIterationsReached` 或 `MaxBudgetReached` 事件（`local_conversation.py` 第 760–765、2075–2108 行）；Claude Agent SDK 返回 `error_max_turns` 或 `error_max_budget_usd`，没有结果文字，但保留了花费和会话编号，官方把"用更高上限续跑"列为续跑场景之一（见 [会话记录检查点](会话记录检查点与失败重来.md) 第 103–104 行）。

第三种依赖"之后还能接着跑"，我们每个 issue 只处理一次，用不上【推断】。我们已定的是"到 60 分钟不开 PR，在 issue 里说明超时"，这对应第一种。还要注意 Actions 的作业超时是直接取消：先给步骤进程发中断信号，7.5 秒后发终止信号，再过 2.5 秒强制结束（见 [Actions 平台事实](Actions平台事实_产物缓存重跑定时.md) 第 145–149 行）。也就是说，如果只靠 Actions 的 `timeout-minutes`，循环自己来不及做任何收尾，所以程序内部要有一个比它早的截止时间【推断】。

### 6. 上下文太长怎么办

"上下文"就是每次发给模型的全部对话记录：系统提示词、issue、模型每一步说的话和每个工具的输出。它只增不减，越长越贵，最后会超出模型能接受的长度。各家的应对分两层。

第一层是单条输出截断，各家都有，我们也已经定了"首尾保留、中间截掉"（各家具体长度见 [agent 工具清单](agent工具清单.md) 第三节）。

第二层是处理整段历史。做法有两种。一种叫"遮蔽"：把较早的工具输出换成一行占位文字，模型自己的话保留。SWE-agent 论文的消融里，只保留最近 5 条工具输出的解决率是 18.0%，全部保留是 15.0%【一手】（2405.15793，GPT-4 Turbo，SWE-bench Lite）；但 SWE-agent 现在的默认配置并没有开这个，只开了提示词缓存标记【一手】（`config/default.yaml`，子 agent 读）。另一种叫"摘要压缩"：让模型把前半段历史写成一段摘要替换掉。OpenHands 的做法是事件数超过 240 或 token 超限时触发，前 2 个事件永不压缩，把历史压到一半左右，压缩失败就把整段历史都总结掉，压缩的花费计入预算【一手】（`context/condenser/llm_summarizing_condenser.py` 的 `max_size=240`、`keep_first=2`，同目录 README；`local_conversation.py` 第 743–747 行）；模型接口报"上下文超长"时，有压缩器就请求压缩，没有就直接报错【一手】（`agent/agent.py` 第 855–868 行）。Codex 在上下文用到窗口的 90% 时压缩，分"一轮中途"和"一轮结束后"两个时机【一手】（`protocol/src/openai_models.rs` 第 534–545 行；`turn.rs` 第 677–733、797 行起）。Claude Code 接近上限时自动压缩，有压缩前的钩子，具体阈值文档没写【一手】（agent loop 文档页）。

效果证据不多。Complexity Trap 在 SWE-agent 上比较了两种做法：遮蔽（保留最近 10 条）和摘要的解决率相当，费用都约为不管理时的一半；摘要反而让轨迹变长（Gemini 2.5 Flash 平均 52 轮，遮蔽 44 轮），作者猜摘要像一个"继续干"的信号；换到 OpenHands 上要重新调窗口大小，否则遮蔽的效果明显下降【一手】（2508.21433）。OpenHands 博客说带压缩平均解决 54%、不带 53%，单轮费用最多降一半，但没写子集多大、跑了几次【一手，厂商自报】。

放到我们这里有三点。DeepSeek 当前模型的上下文长度是 100 万 token（见 [issue 里引用的其他 issue](issue引用与打标签前后的修改.md) 第 54 行），上面的 DeepSeek 运行平均 88 步，加上输出截断，60 分钟内撑满的可能性不大【推断】。DeepSeek 要求只要带工具，之前所有轮的思考内容都必须原样回传（见 [agent 工具清单](agent工具清单.md) 第六节），这意味着思考内容也在累积，而且任何改写历史的做法都得保住它【推断】。模型服务商普遍会对"和上次请求开头相同的部分"打折计费（前缀缓存），改写旧消息会让这部分折扣失效，遮蔽省下的钱可能被抵掉一部分【推断，没有核实 DeepSeek 的缓存规则】。

## 四、各项目借鉴什么、不借鉴什么

**mini-swe-agent。**借鉴它的两处：上限检查放在每次问模型之前，结构最简单；模型没按格式调用工具时打回重来、连续 3 次放弃，正好用来处理 DeepSeek 不能强制调用工具的问题。不借鉴它"到上限补丁记空"的处理，它是为评测打分设计的，我们需要的是给人一个说明。它 SWE-bench 配置里的 250 步、3 美元，没找到作者的理由，不当依据。

**SWE-agent。**借鉴它把退出原因分细的做法（时间、费用、上下文、格式错误、接口错误各有名字），收尾作业正好可以按原因选留言模板。不借鉴"出错就把改动自动当补丁交出去"：在评测里这能多拿分，但在我们这里，一份没经 agent 自查、也没有汇报的半成品进了 PR，人得自己判断它做到哪一步，和"到时间不开 PR"的既定决定冲突。

**OpenHands 新版 SDK。**借鉴"最后一步刚好完成就算完成、不算超限"的细节，以及"同一调用报同一个错第 3 次时先提醒一次"的思路（提醒成本很低）。不借鉴完整的卡死检测：阈值没有依据，有误报的反映，SWE-smith 的数据说干预重复并不提高解决率，而我们已经有时间上限兜底。不借鉴摘要压缩：多一次模型调用、多一个失败分支，在 100 万 token 的上下文和 60 分钟的运行里大概率用不上。

**Codex CLI 和 Claude Agent SDK。**借鉴"不靠步数上限收尾、让模型自己停"的立场，这和你说的"上限只当保险"一致。不借鉴续跑机制（我们一次处理）和 Codex 的"上下文快满就压缩、所以不怕死循环"（我们没有压缩）。

**Copilot 和 DeepSWE。**借鉴"只用墙钟时间当硬保险"：Copilot 是 59 分钟，DeepSWE 是 9000 秒且只碰到 0.9% 的运行。我们的 60 分钟已经参照 Copilot 定了。

**SWE-smith、FailFast、Complexity Trap 等论文。**借鉴结论，不借鉴方法：SWE-smith 说明重复是症状，FailFast 说明预测失败能省钱但要额外训练一个模型，Complexity Trap 说明简单遮蔽和摘要效果相当。这些都只在 SWE-bench 和少数模型上测过，等我们自己的运行记录多了再看要不要用。

## 五、建议（2026-10-31 已定：上限按 token 总数算、往宽了设，不按费用；其余照下面的建议）

- **怎么结束：**agent 第二次调用 `submit` 时正常结束；回复里没有工具调用就打回，连续 3 次按出错结束。理由：DeepSeek 不能强制调用工具，mini 就是这样处理的。
- **上限：**只设运行时间和费用两道保险，时间由程序内部掐在 Actions 的 60 分钟之前，给收尾留余地；不设紧的步数上限。理由：DeepSeek 在 mini 上成功的运行中位数就要 79 步，固定小步数会切掉正常任务；Actions 超时是直接杀进程，循环来不及收尾。
- **不做卡死检测和失败预测，**只把重复调用记进运行记录。理由：没有证据说它能提高解决率，时间和费用上限已经兜住浪费。
- **到上限或出错：**沿用"不开 PR，在 issue 里说明原因"，按退出原因选留言。理由：没经自查和汇报的半成品不该进 PR。接口临时错误先重试几次再按出错处理，次数写代码时定。
- **上下文：**只做已定的单条输出截断，不做遮蔽和摘要；真的超长就按出错结束。理由：100 万 token 在 60 分钟内大概率用不满，改写历史还要保住思考内容、可能丢掉缓存折扣。
