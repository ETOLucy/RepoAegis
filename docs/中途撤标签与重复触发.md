# 处理中途撤标签、撤了又打：问题与做法

> 状态：调研结论与建议，调研日期 2026-10-24。凡是标"待验证"的，都要在测试仓库里实验后才能当结论用。
>
> 2026-10-25 已按本文方案实现触发和开工前检查并实测，结果见文末"2026-10-25 实测"。2026-10-26 用户定下"只有 Write、Maintain、Admin 的动作才算数"，改变了下文"我们的建议"第 2、3、4 条的做法，见文末"2026-10-26 修订"。正文其余部分保留当时的分析，没有逐句改写。

## 问题是怎么来的

RepoAegis 用 GitHub Actions 实现：有人给一个开着的 issue 打上 `agent-fix`，Actions 启动一次运行，agent 改代码、开草稿 PR、在 issue 里汇报，最后撤掉标签。

麻烦出在"人在中途改主意"。比如 8 号 issue 刚被打上标签，agent 已经开始跑了，这时有人觉得不需要了，把标签撤掉。agent 应该立刻停下吗？如果它已经跑完，回头发现标签没了，还要不要开 PR？再比如，标签撤掉以后又被重新打上，意思大概是"再试一次"，那上一次留下的分支和 PR 怎么办？另外，人能不能从外面直接让正在跑的 agent 停下来？

## GitHub Actions 本身提供了什么

先说 Actions 里一个叫 **concurrency（并发组）** 的设置。它是给运行起的一个名字，名字相同的运行，在整个仓库里同一时刻最多只有一个在跑。官方文档的说法分三层：同组同时最多跑一个；新来的运行发现同组有人在跑，就进入等待，原来已经在等待的那个会被取消，由新来的顶替；如果再加上 `cancel-in-progress: true`，连**正在跑的**那个也会被取消。官方例子是这样写的：

```yaml
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true
```

被取消的运行会怎样，官方文档《workflow cancellation》写得很具体：先给正在执行的步骤发一个相当于 Ctrl-C 的信号，7.5 秒内没退出就再发一次更强的终止信号，再过 2.5 秒直接杀掉整个进程。所以 agent 大约 10 秒内一定会停下。后面还没执行的步骤里，写了 `if: cancelled()` 或 `if: always()` 的仍然会执行，这是做清理的机会，比如在 issue 里留言说明"已取消"。

从外部停止一次运行，有这几种方式：网页上点 **Cancel workflow**（需要写权限）；命令行 `gh run cancel <运行编号>`；或者调用接口 `POST /repos/{owner}/{repo}/actions/runs/{run_id}/cancel`。Actions **没有"暂停后再继续"**的功能，只能取消。另外每个作业默认最多跑 360 分钟，超时会被自动取消，可以用 `timeout-minutes` 改短。

还有几条官方文档里写明、和我们直接相关的规则：

- **新建 issue 时就带着标签，会触发"打标签"**。文档原话：带两个标签新建一个 issue，会启动三次运行，一次是"新建"，两次是"打标签"。所以"新建时直接选了 `agent-fix`"也会被处理，这符合我们的规则。
- **issue 的状态在事件里能直接拿到**：`github.event.issue.state` 是 `open` 或 `closed`，可以写成条件 `if: github.event.issue.state == 'open'`，已关闭的 issue 一开始就不处理。不过这是事件发生那一刻的状态，运行期间如果 issue 被关闭，要重新查一次才知道。
- **用 Actions 自带的令牌（`GITHUB_TOKEN`）撤标签，不会再触发新的运行**，这是 GitHub 为防止循环触发做的规定。但如果改用个人令牌或 GitHub App 的令牌撤标签，就**会**触发（按文档原文推断，待验证）。

## 用 concurrency 实现"撤标签就取消"，可行但有坑

设想是：让"打标签"和"撤标签"两种事件，都进入同一个按 issue 编号命名的并发组，并开启 `cancel-in-progress`。这样一撤标签，正在跑的那次就被取消；一重新打标签，还没结束的上一次也会被取消，由新的一次接替。

按官方文档，这是可行的，但有三个坑：

1. **`issues` 事件在触发这一层不能按标签名过滤。** 所以给 issue 打一个无关的 `bug` 标签，也会产生一次运行。如果并发组写在整个工作流的最外层，这次无关的运行也会进组，把正在跑的 agent 取消掉。有第三方项目报告，把并发组写到具体的作业上、并用条件筛掉无关事件，被筛掉的作业就不会进组（第三方说法，待验证）。
2. **撤标签用什么令牌。** 如果 agent 处理完是用 App 令牌撤的标签，这次撤标签会触发一次运行，有可能把自己正在收尾的那次取消掉。用 `GITHUB_TOKEN` 撤就不会。
3. **取消之前，agent 可能已经推了分支、开了 PR。** 要靠 `if: cancelled()` 的清理步骤去收拾，比如删掉分支、关掉草稿 PR，或者至少在 issue 里说明情况。

## 官方项目是怎么做的

**没有一个官方项目用 concurrency 来实现"撤标签就取消"。** 最常见的做法是：**在开 PR 之前，重新查一次 issue**。

- **SWE-agent**：agent 跑完、准备开 PR 前，检查 issue 是否还开着，不开着就不开 PR；同时检查是否已经指派给别人、是否被锁定、是否已经有提交提到了它。
- **OpenHands 的定时扫描版**（`OpenHands/extensions` 里的 github-issue-to-pr）：开始前重新查一次，标签已经被撤了就不开工；结束时如果 issue 已关闭，就不开 PR。但运行中撤标签不会让它停下。每次打标签只处理一次，重新打标签会开第二个分支和第二个 PR，不覆盖第一个（分支名后面加 `-2`、`-3`……）。超过 2 小时没结束的任务直接放弃。
- **OpenHands 1.5.0 的解决器**：取 issue 时只取开着的，已关闭的会直接报"找不到"；分支名已存在就改成 `-try2`、`-try3`。没有并发控制，也不撤标签。
- **Claude Code 的 GitHub 集成**：没有并发控制、没有取消逻辑、不检查 issue 状态；分支名带时间戳，所以重复触发自然会生成新分支。
- **GitHub Copilot**：会话页面上有一个 **Stop session** 按钮，官方原话是"Stopping a session ends the Actions run and preserves any commits already pushed"，也就是停止会话会结束那次运行，已经推上去的提交保留。

## 几种做法对比

**做法一：只在结尾复查**（SWE-agent、OpenHands 扫描版的做法）。不设并发组。开 PR 前重新查一次 issue：标签没了或者 issue 已关闭，就不开 PR，在 issue 里留言说明，删掉临时分支。好处是简单、不会误取消。坏处是撤标签之后 agent 仍然会跑完，白花运行时间和模型费用；在 agent 还在跑的时候重新打标签，会出现两次运行同时跑、两套分支。

**做法二：用并发组实现撤标签即取消。** 触发类型写"打标签"和"撤标签"（还可以加"关闭"），干活的作业和一个专门负责"停止"的作业共用一个按 issue 编号命名的并发组，并开启 `cancel-in-progress`；干活的作业末尾加 `if: cancelled()` 的清理步骤。好处是撤标签后约 10 秒内停下，重新打标签会自动取代旧运行。坏处是要处理上面三个坑，其中第一个目前只有第三方报告，必须实测。

**做法三：二和一结合。** 以取消为主，结尾复查兜底，覆盖"取消没生效""清理失败"这些情况。代价是两套逻辑都要写。

**做法四：agent 在循环里自己检查。** 每走若干步查一次标签，发现被撤了就自己收尾退出。收尾完全由自己控制，不受 10 秒强制终止的限制；但要改 agent 循环，响应快慢取决于多久查一次，还会增加接口调用。可以和前几种组合。

**上一次的分支和 PR 怎么办**是一个独立的选择：保留旧的、新开一个（OpenHands、Claude Code 集成都是这样），或者新的一次开始时先关掉旧的草稿 PR（没有官方先例）。

## 我们的建议（已采纳：2026-10-24，做法三）

用户明确要求：撤掉标签就表示"不用处理了"，正在跑的 agent 要终止、任务直接结束。做法一做不到这一点，所以建议采用**做法三**（并发组取消为主，开 PR 前复查兜底），具体是：

1. 触发条件写成"打上的是 `agent-fix`，并且 issue 是开着的、不是 PR"，已关闭的一开始就不处理。
2. 打标签和撤标签都触发运行；只有和 `agent-fix` 有关的运行，才进入按"issue 编号 + 标签名"命名的并发组，并开启 `cancel-in-progress`。无关的运行给一个独一无二的组名（例如 `github.run_id`），不进同一个组，避免打别的标签时误伤。撤标签产生的运行进组时，会取消正在跑的那次。
3. 被取消时，由不管成败都会执行的收尾作业在 issue 里留言说明（2026-10-24 改定，留言怎么写待讨论），不自动删除分支或关闭草稿 PR（见下文"撤标签时分情况处理"）。
4. agent 跑完、开 PR 之前，重新查一次 issue：标签还在、issue 还开着，才开 PR；否则按第 3 条收尾。这一条兜住"取消没生效""先后顺序不保证"的情况。
5. 结束时用 `GITHUB_TOKEN` 撤标签，避免自己触发自己、把自己取消。
6. 撤掉后重新打标签，当成"再试一次"：新开一个带编号后缀的分支和新的草稿 PR，在 issue 里附上上一次 PR 的链接，不覆盖旧分支。

用户已确认采用这个"两者结合"的方案。

### 并发组怎么分

组名由每次运行的事件内容算出来，算出的字符串相同的运行在同一组：

```yaml
concurrency:
  group: ${{ github.event.label.name == 'agent-fix' && format('agent-fix-issue-{0}', github.event.issue.number) || format('other-{0}', github.run_id) }}
  cancel-in-progress: true
```

同一个 issue 上打或撤 `agent-fix` 的运行同组，撤标签会取消正在跑的那次；不同 issue 各自一组，可以同时处理；打或撤别的标签的运行各自一个独有的组，不会误伤。

issue 编号在同一个仓库里唯一，issue 和 PR 共用一套编号，子 issue 也有自己的编号；并发组只在一个仓库内生效，所以组名用 issue 编号就够了。

### 按当前状态行动，而不是按触发它的事件

同一个 issue 会有多次运行（每打或撤一次标签就一次），而同组运行的先后顺序不保证。例如"打上（运行甲）→ 撤掉（运行乙）→ 重新打上（运行丙）"，如果丙比乙先进组，乙会把丙取消，结果标签挂着却没人干活。

所以同组里的每次运行，开始时都先用接口查 issue 的**当前**状态：现在有 `agent-fix` 且 issue 开着，就干活；没有，就安静结束。这样不论事件以什么顺序到达、谁取消了谁，最后留在组里的那次运行总按最新状态行动。再加上开 PR 前的复查，时间差的问题都能兜住。

GitHub 偶尔根本没触发运行、或者收尾那一步自己出错的极端情况，由一个定时运行的小工作流兜底（2026-10-24 已定要做）：每隔一段时间找出"挂着标签但没有正在运行的处理"的 issue，在 issue 里说明上次处理没有正常结束，并撤掉标签，由人决定是否重新打标签（OpenHands 的新自动化每 15 分钟轮询一次，超过 2 小时没结束的任务直接放弃）。多久跑一次、留言怎么写，待讨论。

### 撤标签时分情况处理

撤标签会触发一次运行，这次运行本身几乎什么都不做，起作用的是"它进组"：

- agent 正在跑：被并发控制取消，**在 issue 里留言说明已按撤标签停止**（2026-10-24 改定：用户定下"每次处理都要给人反馈"的原则，取代了原先"只记日志、不留言"的决定；留言具体怎么写待讨论）。不自动删除分支或关闭草稿 PR（有开 PR 前复查，残留只会出现在很小的时间窗口里，由人处理）。
- agent 还在排队：排队中的运行被直接顶掉，没开始就不需要收尾。
- agent 已正常做完：收尾时我们已用 `GITHUB_TOKEN` 撤过标签，不触发新运行；人也已无标签可撤。
- 没有任何运行（例如打标签那次失败或被手动取消，标签还挂着，人后来撤掉）：组里无人可取消，撤标签的运行安静结束，只在运行日志里记一句，不在 issue 里留言。
- 撤的是别的标签，或 issue 已关闭：工作流跳过。

> 2026-10-24 补充：用户定下原则"无论发生什么，处理结束时都要在 issue 里给反馈、都要撤标签"，由程序保证（见 README"要做什么"）。本节和下一节里写着"安静结束""只写一行日志"的情况，是否改为留言、怎么写，随留言方式一并讨论。

### issue 突然"没了"的其他情况（已确认，2026-10-24）

除了撤标签，issue 还可能被关闭、删除、转移到别的仓库（不是指派给人）、锁定、指派给某个人、转成讨论帖、在处理中途被编辑，或者标签本身被改名、删除。做法：

- **立即停**：撤标签、关闭（`closed`）、删除（`deleted`）、转移（`transferred`）都加进触发条件，进入同一个 `agent-fix-issue-编号` 组，一发生就取消正在干活的那次。组名的算法要相应扩展。
- **复查时拦住**：指派给人、锁定、转成讨论帖（之后查不到），不立即停，在开 PR 前查当前状态时拦住；任一成立就停下，只写一行日志。SWE-agent 开 PR 前就检查关闭、指派、锁定。
- **中途编辑**：agent 只以开始时读到的内容为准，中途的修改不理会；改动重要时，由人撤掉标签再重新打上，让 agent 按新内容重来。
- **标签改名或被删除**：当作撤标签处理。改名、删除时 GitHub 是否会对每个 issue 发出撤标签事件，写代码时验证。

### 为什么乱序也不会出错

Actions 里没有一直在等通知的程序：每来一条符合条件的通知，GitHub 都会新开一个任务把步骤从头执行一遍；撤标签之所以能让 agent 停下，靠的是"为撤标签开的这个任务"进组，把正在干活的那次顶掉。每个任务开始时都先看 issue 当前有没有标签，有就让 agent 干活，没有就结束，不管自己是被哪条通知叫来的。issue 的当前状态是所有操作按真实先后执行完的结果，所以迟到或乱序的通知看到的也是最新状态，等于自动以最新的为准，不需要比较通知的时间。代价是乱序时 agent 会被多停、多启动一次。

### agent 跑在哪里（建议，待用户确认）

三种做法：agent 跑在 GitHub 自带的临时机器上（官方项目的主流做法；公开仓库免费，私有仓库免费账号每月 2000 分钟）；Actions 只负责通知、agent 跑在自己的服务器上（服务器要能被 GitHub 访问，就需要一个公网地址，不建议）；Actions 管触发、任务交给装在自己电脑上的自托管运行器去跑（运行器主动向外连 GitHub 领任务，只要求能访问 443 端口，不需要公网地址；免费；但电脑要一直开着，沙箱和安全要自己负责）。建议先用第一种，第三种作为以后的升级路线。出处：GitHub 文档《Self-hosted runners》参考页、Actions 计费页（2026-10-24 读取）。

这个方案依赖几条还没实测的 Actions 行为（见下面"尚未查清"的前三条），所以在写正式代码之前，先在测试仓库里用一个最小的工作流把它们逐一验证。如果实测发现并发组的坑绕不过去，再退回做法一，并改用做法四（agent 在循环里定期检查标签）来实现"撤标签就停"。

## 2026-10-25 实测（测试仓库 `ETOLucy/repoaegis-sandbox`）

按本文方案写的可复用工作流和开工前检查（RepoAegis 提交 `1a8a037`：`.github/workflows/agent-fix.yml`、`src/repoaegis/precheck.py`），在 #3 上依次操作：

- 打上 `agent-fix`：从运行创建到作业开始约 4 秒，作业 7 秒跑完，检查结论"开工"。令牌只有 `issues: read` 和 `metadata: read`，查协作者权限够用。
- 打无关标签 `documentation`：产生运行，作业被跳过，没有分配运行机器，前后约 1 秒。
- 撤掉 `agent-fix`：作业执行，结论"issue 上已没有 agent-fix 标签"。
- 重新打上：结论"开工"。
- 关闭挂着标签的 issue：作业执行，说明 `closed` 事件的内容里带着当时的标签；结论"已关闭"。
- 重新打开：不产生运行（`reopened` 不在订阅之列）。

没测到的：撤标签能否取消正在跑的运行（检查几秒就结束，没有东西可以被取消）；作业上的 `if` 为假时是否进并发组；给已关闭的 issue 打标签、新建 issue 时带标签会不会触发。

## 2026-10-26 修订：只有 Write、Maintain、Admin 的动作才算数

用户定下：处理开始后，只有这三种角色撤标签、关闭、删除或转移 issue，正在跑的处理才停止；其他人（Triage、机器人、issue 作者）做同样的动作，一律不理会，处理照常进行，不留言，也不把标签加回去，程序不为这件事动 issue。他们的动作要是让后面某一步做不成（issue 被删、评论发不出去），只在日志里记错误，其余照常。规则写进使用说明，不在 issue 里提示。

能做这几种动作的人（GitHub 文档 `github/docs` 中 issues 相关页面，2026-10-26 读取）：删除只有 Admin（`deleting-an-issue.md`）；转移要两个仓库的写权限（`transferring-an-issue-to-another-repository.md`）；撤标签要 Triage 及以上，有 issue 写权限的机器人和应用也行；关闭要 Triage 及以上，另外"任何人都能关闭自己建的 issue"（`closing-an-issue.md`）。所以这条规则实际管到的是：Triage 或机器人撤标签，Triage 或 issue 作者关闭。后一种情况下 agent 会给一个已关闭的 issue 开草稿 PR，用户接受这个结果。

**对做法的影响：**

- 并发组的 `cancel-in-progress` 在新运行进组那一刻就取消旧运行，那时还没查到撤标签的人是谁，所以自动取消不能再用。改成：同一 issue 的运行仍进同一组，但只排队不取消；每次运行开始先由程序判断"这条事件是谁做的，加上 issue 现在的状态"，判定要停时，调用 `POST /repos/{owner}/{repo}/actions/runs/{run_id}/cancel` 停掉这个 issue 正在跑的那次。这个接口要求 Actions 写权限（`github/docs` 的 `src/rest/data/fpt-2026-03-10/actions.json`），只给检查作业，agent 作业不能有。程序要能找到"这个 issue 正在跑的是哪次运行"，例如给运行起带 issue 编号的名字再按名字查，写代码时定。取消从"GitHub 保证"变成"我们的代码负责"，取消失败时靠开 PR 前的复查兜底。
- "我们的建议"第 4 条，开 PR 前复查"标签还在、issue 还开着"，要改成"没有被三种身份之一叫停"：标签被 Triage 撤掉、issue 被作者关闭，都照样开 PR。
- 修改标题或正文不触发运行（`edited` 不在订阅之列），agent 按打标签那一刻的内容做到底。结束评论写明按哪一刻的内容处理，期间被改过就加一句提示，细则见 README"要做什么"。
- 打标签的人取事件记录里最后一次打上标签的人，不用 `sender`，理由见上文"按当前状态行动"的乱序例子。乱序是 GitHub 文档写明可能发生的（`troubleshooting-webhooks.md`"Webhooks deliveries are out of order"），没有公开的概率数据；实测从动作到作业开始有几秒间隔，两个动作挤在这几秒里才可能被调换顺序（推断）。

**尚未定：** Triage 撤掉标签后 agent 还在跑，这时三种身份之一又打上标签。这是有权限的人的新触发，正在跑的那次是继续做，还是按最新内容重来。
