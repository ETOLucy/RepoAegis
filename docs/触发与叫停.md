# 触发与叫停

> 这一篇管：什么动作会让 RepoAegis 开工，谁的动作算数，处理中途怎么叫停，重新打标签时怎么办。只写现行规则，括号里是定下的日期；被推翻的旧做法和当时的分析见 [调研/撤标签与重复触发的做法对比](调研/撤标签与重复触发的做法对比.md)。叫停以后存档怎么存、留多久，见 [暂停存档与监控](暂停存档与监控.md)。

## 一、什么动作会启动一次运行

要接入的仓库里放一个调用文件（模板是 [examples/agent-fix.yml](../examples/agent-fix.yml)），只订阅 issue 的五种动作：打标签、撤标签、关闭、删除、转移。新建、编辑、评论、指派、重新打开都不产生运行。

运行产生以后，RepoAegis 的工作流（[.github/workflows/agent-fix.yml](../.github/workflows/agent-fix.yml)）先用条件筛一遍：对象必须是 issue 而不是 PR，并且要么打上或撤掉的正是 `agent-fix`，要么被关闭、删除、转移的 issue 身上挂着 `agent-fix`。不满足就跳过，不分配运行机器（2026-10-25 实测：打无关标签产生运行，作业被跳过，前后约 1 秒）。

另外几条：

- **新建 issue 本身不触发。** 新建时直接选了 `agent-fix` 的，按 GitHub 官方文档会同时产生一次"打标签"事件，所以会被处理（未实测）。
- **已关闭的 issue 不处理**，打上标签也跳过。问题要么已解决，要么已决定不做。
- **给 PR 打标签不处理。** 专用标签只针对 issue。
- **自己不触发自己。** 处理结束时用 Actions 自带的令牌（`GITHUB_TOKEN`）撤标签，按 GitHub 规定这类操作不会再启动新的运行。

## 二、谁的动作算数（2026-10-26 定，10-27 补全）

只有仓库里 Write、Maintain、Admin 三种角色的人，他们的动作才算数。

GitHub 规定 Triage 及以上的人就能打标签，而 Triage 能管 issue 和标签、不能改代码，所以"能打标签"不等于"有写权限"。开工前检查用接口 `GET /repos/{owner}/{repo}/collaborators/{用户名}/permission` 查角色，返回的 `permission` 是 `admin` 或 `write` 才算（接口把 Maintain 记作 write、Triage 记作 read）。这和 Copilot、claude-code-action、codex-action、gh-aw 的默认门槛一致。

其他人（Triage、机器人、issue 作者）的动作一律不理会：

- 他们打的标签：不开工、不留言、不撤标签，标签留在 issue 上由有权限的人处理（2026-10-27 定）。
- 他们撤标签、关闭 issue、改标题或正文：不留言、不把标签加回去，处理照常进行。
- 他们的动作让后面某一步做不成（例如评论发不出去）：只在运行日志里记一条错误，其余步骤照常。

这条规则写进使用说明，不在 issue 里提示。代价是 issue 作者自己关掉 issue 后，agent 仍会做完并开草稿 PR。按 GitHub 文档，删除 issue 只有 Admin 能做，转移要两个仓库的写权限；撤标签和关闭要 Triage 及以上，另外任何人都能关闭自己建的 issue。所以这条规则实际管到的是：Triage 或机器人撤标签，Triage 或 issue 作者关闭。

## 三、打标签的人怎么认，运行的身份是什么

**打标签的人**不看触发这次运行的那条事件里的 `sender`，而是翻 issue 的事件记录，取最后一次打上 `agent-fix` 的人（2026-10-26 定）。原因是 GitHub 不保证事件按发生顺序处理（官方文档 `troubleshooting-webhooks.md`"Webhooks deliveries are out of order"，没有公开的概率数据）：一次"撤标签"产生的运行可能最后才轮到，这时标签又被重新打上了，它就得接手干活，而它的 `sender` 是撤标签的人。

**运行的身份**是"issue 编号 + 打标签的时间"（2026-10-27 定），打标签的时间取事件记录里那条 `labeled` 事件的 `created_at`。存档、快照按它找；后面的作业交付、撤标签之前，用它核对自己还算不算数（见第七节）。

## 四、每次运行先看两样，再决定

每次运行都同时看两样：**这条事件是谁做的**，以及 **issue 现在是什么样子**。不管事件以什么顺序到达，issue 的当前状态总是所有操作按真实先后执行完的结果，所以按当前状态行动，迟到或乱序的事件也会以最新的为准。

开工前检查（[src/repoaegis/precheck.py](../src/repoaegis/precheck.py)）按这个顺序走：

1. 这条事件是撤标签、关闭、删除或转移，并且是有权限的人做的：叫停这个 issue 正在跑的运行（第五节）。没权限的人做的，这次运行安静结束。
2. 查 issue 现在的样子：查不到（已被转移或删除），停掉正在跑的，结束；已关闭、已没有 `agent-fix`，不开工。
3. 查最后打标签的人：没有权限，不开工。
4. 内容检查：按打标签的时间整理出要交给 agent 的内容，查修改人、图片和附件（[agent 读到的内容](agent读到的内容.md)）。不通过就不开工，正在跑的一并停掉。事件记录里找不到打标签的那一条时，也不开工，已有的运行继续跑。
5. 拿整理好的内容和正在跑的运行、暂停存档比，决定让旧的继续、接着做，还是从头做（第六节）。

## 五、叫停（2026-10-27 定）

- **有权限的人撤标签或关闭 issue**：正在跑的那次先存档，再停下。这叫暂停，之后可以接着做。
- **有权限的人删除或转移 issue**：直接停下，不存档，因为 issue 已经不在了。

**为什么不用并发组自动取消。** Actions 的并发组（concurrency，名字相同的运行同一时刻最多跑一个）可以写 `cancel-in-progress: true`，新运行一进组就取消旧的。但那一刻还查不到撤标签的人是谁，没权限的人撤标签也会把运行停掉，所以不能用（2026-10-26 定）。

**现在的做法。** 代码里，同一个 issue 的检查作业进同一个并发组，写成 `queue: max`，按先后排队、谁也不取消谁（2026-10-30 实测 GitHub 接受这种写法；要不要保留排队还没拍板，见第九节）。要停时由检查程序调用取消接口 `POST /repos/{owner}/{repo}/actions/runs/{run_id}/cancel`。这个接口要 Actions 写权限，只给检查作业，agent 作业绝不能有。

**怎么找到正在跑的那次。** 检查决定开工时，把整理好的内容存成运行产物（一次运行上传、保存在 GitHub 上的文件），名字是 `repoaegis-issue-编号-内容哈希`。后来的检查列出状态为"正在跑"和"排队中"的运行，看它们的产物名，就知道哪次在处理这个 issue、用的是什么内容。

**取消要等它停完。** 取消接口返回只表示"收到了"。GitHub 先给正在执行的步骤发一个相当于 Ctrl-C 的信号，7.5 秒后再发一次更强的终止信号，再过 2.5 秒直接杀掉进程；之后写了 `if: cancelled()` 或 `if: always()` 的步骤和作业仍会执行（官方文档 `workflow-cancellation.md`）。检查程序停掉运行后等它完全结束，最多 7 分钟，检查作业的时限相应放宽到 10 分钟。

## 六、重新打标签（2026-10-27 定，10-30 补全）

有权限的人打上标签时，拿这一刻的内容和"上一次处理用的内容"比。中间是谁撤的标签、撤没撤，都不影响这一步。

"内容"指内容检查按打标签的时间整理出的那一份：被打标签 issue 的编号、标题和正文。它引用的其他 issue 不算在内，agent 运行中按需去读（[agent 读到的内容](agent读到的内容.md) 第五节）。

- **上一次还在跑**：一致就不动它，新运行安静结束；不一致就停掉它，按新内容从头做。
- **上一次已经暂停、存档还在**：一致就从存档接着做；不一致就删掉存档，按新内容从头做。

举个例子。10:00 有权限的人给 8 号 issue 打上标签，运行甲开工。10:30 有权限的人撤掉标签，触发的运行乙把甲停掉，甲停下前把进度存成存档，并在 issue 里留一句"已暂停"。第二天 9:00 有权限的人重新打上标签，运行丙发现内容和存档一致，就取出存档接着做。

**改标题或正文不触发运行。** `edited` 不在订阅之列，agent 始终按打标签那一刻的内容做到底。要按新内容做，有权限的人撤掉标签再重新打上。处理期间被改过时，结束评论里加一句提示（见 [暂停存档与监控](暂停存档与监控.md)"收尾和留言"）。

## 七、时间差要防的几件事

- **取消不是瞬间生效的。** 旧运行最多还要约 10 秒才停，这段时间里新旧两个 agent 可能同时在跑。所以交付作业推分支、开 PR 前要核对自己还算不算数，不算就停手。
- **被取消的运行，收尾作业照样会跑。** 旧运行的收尾不能把新运行需要的标签撤掉，撤标签前也要先核对。
- **核对的标准。** 因为"内容一致就让旧的继续"，旧运行可能一直跑着，而最新一次打标签的时间已经变了，所以不能只看"最后一次打标签的时间是不是我的"，要看"从我开工到现在，有没有有权限的人叫停过，或者有没有内容不同的新打标签"。具体写法在写交付和收尾时定。
- **撤了马上又打。** 新运行可能比旧运行上传存档还早，所以看到旧运行还在停止过程中，要等它停完再去找存档（已写进检查程序）。

## 八、其他情况

- **开 PR 前复查**：没有被三种身份之一叫停，才开 PR。标签被 Triage 撤掉、issue 被作者关闭，照样开。
- **指派给人、锁定、转成讨论帖**：不立即停，开 PR 前查当前状态时拦住，任一成立就停下，只写一行日志（2026-10-24 定）。这些动作要不要也看是谁做的，还没定。
- **标签被改名或删除**：当作撤标签处理。改名、删除时 GitHub 会不会对每个 issue 发出撤标签事件，待验证。
- **上一次的分支和 PR**：叫停时不自动删除分支、不关闭草稿 PR，由人处理；开 PR 前的复查已经把残留压到很小的时间窗口里。

## 九、待定和待实测

- 同一个 issue 的开工前检查要不要排队：现在的代码是排队，一个一个跑；另一种是不排队，只有"事件记录里最新一个有权限动作"对应的检查才出手，其余让路。建议保留排队，待拍板。
- **检查没通过时没有人留言（代码的缺口）。** 结论是 `stop` 时 agent 作业被跳过，而收尾作业现在只在 agent 作业跑过时才执行（`agent-fix.yml` 收尾作业的条件），所以"修改人没有权限""带图片"这类不开工的情况，issue 里收不到任何说明，标签也不会撤。检查作业又只有 `issues: read`，发不了提醒留言，被修改人检查拦下的 issue 就一直放不过去。收尾要放在哪个作业、怎么接住 `stop`，需你定。
- **检查没通过时，旧运行的暂停存档留不留。** 10-30 的方案写的是"停掉旧运行，不留接着做的机会"，你回了"按方案改"；现在的代码停掉运行但不删存档，之后内容一致时还能接着做。需你定。
- **接着做时可能读到同一篇 issue 的两个版本。** 存档里的对话可能有上次按旧的打标签时间读到的引用，这次再读按新的打标签时间，两份可能不同；被引用的 issue 被改过，指纹也不会变，正在跑的照样继续。要不要处理，待定。
- 待实测，按要紧程度排：
  1. 运行还没结束时，接口能不能列出它已经上传的产物。列不出来，检查程序就找不到正在跑的那次，第五节的整套做法失效，要最先测。
  2. 取消后运行是否真能停住，从撤标签到停下实际要多久。
  3. 取消正好打断收尾作业时，会不会把标签留下。
  4. 并发组写在作业上、条件为假时是否完全不进组。
  5. 给已关闭的 issue 打标签会不会触发；新建 issue 时就带标签会不会触发（第一节）。
  6. 事件记录的延迟有多大。
