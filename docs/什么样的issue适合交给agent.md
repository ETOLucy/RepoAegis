# 需求：哪些 issue 交给 agent 处理

> 本文是 RepoAegis 的需求：规定什么样的 issue 会被处理、什么样的不会，以及判断不过时怎么办。每条规则后面写依据。
>
> 状态（2026-10-24）：标"**已定**"的是已经拍板的。各项阈值（清晰度、人工时间、代码量、运行时长、安全类排除）已定为先按根据官方项目做法提出的数值执行，标"**已定，实测后可能调整**"；标"**建议，待拍板**"的是还没确认的部分。所有规则都还没在真实仓库里实测。项目整体不做哪些事，见 [项目边界](项目边界.md)。

## 一、为什么需要这些规则

RepoAegis 被打上标签后只运行一次，中途没有人可以回答它的问题。它读到的只有打标签那一刻 issue 的标题和正文，做完开一个草稿 PR，然后撤掉标签。所以一个 issue 能不能交给它，取决于一件事：**只凭正文，一个不能追问的工程师能不能把它做完，并且知道什么时候算做完。** 不满足这一点的 issue，agent 做出来的只会是一个靠猜的 PR，既浪费运行时间和模型费用，也浪费评审的人的时间。

下面的规则分两层。第一层是**触发条件**，由 GitHub Actions 的配置直接判断，不满足就根本不会启动。第二层是**接收规则**，由 agent 在动手改代码之前判断，不满足就不改代码、说明原因后结束。

## 二、第一层：触发条件（已定）

同时满足以下全部条件，才会启动一次处理：

1. 动作是"给 issue 打上标签"，标签名是 `agent-fix`（名字暂定）。
2. issue 是**开着的**。已关闭的 issue 打上标签也不处理。
3. 对象是 issue，不是 PR。给 PR 打标签不处理。
4. issue 正文里没有图片。带图片的 issue 暂不处理，图片以外的附件一律跳过。

**依据：** 前三条是项目定位（一次性处理开着的 issue）。第四条是因为现在不引入看图能力；抽样统计中约 12% 的 issue 带图片，有界面的应用类仓库约 29%，通用库约 4%。

## 三、第二层：接收规则

agent 动手改代码之前，按顺序检查下面五条，**任何一条不通过，就不改代码**，按第四节的方式回应。

### 规则 1：必须是在要求改代码

提问、讨论、求助、感谢、汇报情况，都不处理。

**依据：** 各家官方产品的定位都是"把一个开发任务交给 agent"。RepoAegis 只开 PR，对非开发类的 issue 没有可交付的结果。

### 规则 2：描述必须足够清楚——清晰度 ≤ 1 分（已定，实测后可能调整）

用下面这把四档的尺子给 issue 打分，只处理 0 分和 1 分的：

- 0 分：写清楚了，怎样才算成功解决一目了然。
- 1 分：有些空白要自己补，但有一个合理的理解，能看出成功的解法该是什么样。
- 2 分：含糊，可以有不同理解，看不出成功的解法该是什么样。
- 3 分：没有更多信息的话，几乎不可能明白要做什么。

1 分的 issue 可以做，但 agent 必须把自己补上的假设写进 PR 描述和 issue 汇报里。打分时要点出 issue 里具体提到的文件、函数或现象，作为打分的理由。

**依据：** 这把尺子来自 OpenAI 整理 SWE-bench Verified 时的人工标注准则。它给标注员的设定是"只看 issue 正文，不能要求对方澄清"，和 RepoAegis 的处境完全一样。SWE-bench 自己的做法也是剔除 2 分及以上的。参考数据：即使是热门 Python 项目里已经被修好的 issue，也有约 38% 被至少一位标注员判为 2 分以上，所以预计会有相当一部分 issue 过不了这一条。

### 规则 3：必须能验证

issue 里至少要有下面一项，让人和 agent 都能检查"到底改对了没有"：

- 复现步骤加实际现象（报错信息、错误输出）；
- 明确的期望行为；
- 可以写成测试或命令来检查的验收标准，比如"某个输入应该返回某个结果"。

**依据：** 这是各家官方建议里重合度最高的一条。Copilot 要求验收标准，Codex 要求写明"做到什么程度算完成"，Devin 要求清楚的成功标准，OpenHands 的判断流程里有一问"能不能验证结果"。

### 规则 4：规模不能超过阈值（已定，实测后可能调整）

下面两个阈值都是**开工前的估计**，超过任何一个就不处理：

- **人工时间：一个熟悉代码库的工程师估计 1 小时以内能完成。** 估计在 1 到 4 小时、或超过 4 小时的，不处理。
- **代码量：预计改动（新增加删除）不超过 100 行，不含新增的测试代码。**

此外还有一条**运行中的硬上限**：单次处理最长 60 分钟，到时间还没完成就停止，不开 PR，在 issue 里说明超时。

**依据：**
- 各家的经验值都落在"人工一小时左右，最多三小时以内"：OpenAI 介绍 Codex 内部用法时说适合"你或同事大约一小时能做完"的任务；Devin 企业指南建议 90 分钟以内，入门页说三小时以内；Copilot 单次运行硬上限 59 分钟。RepoAegis 一次运行、不能中途对话，所以取较保守的一端。
- SWE-bench 标注准则里的难度分四档：少于 15 分钟、15 分钟到 1 小时、1 到 4 小时、超过 4 小时。建议值相当于只接前两档。那批真实 issue 里，前两档占约 78%（417 + 906，共 1699 个）。
- 100 行来自 OpenHands 的判断流程，原文写的就是"少于 100 行代码"。SWE-bench 的"超过 4 小时"一档也以"改动超过 100 行"为特征。不含测试代码，是因为补测试本身是被鼓励的，不应该因此被拒；这一点是我们自己的设计，没有官方依据。
- 60 分钟参考 Copilot 的 59 分钟上限。GitHub Actions 默认允许一个作业跑 360 分钟，所以必须在配置里改短。

**注意：** 这两个阈值靠 agent 自己估计，而 Devin 的官方文档承认"agent 容易高估自己"，调研中没有找到任何一家公开过 agent 自评准确率的数据。所以规定：**拿不准是否超过阈值时，按超过处理**。这两个数字在真实仓库里实测后可能调整。

### 规则 5：不属于排除的类型

下面几类即使写得很清楚、规模也很小，也不处理：

- **涉及安全、身份认证、权限、个人隐私的改动**（已定：目前一律不做，以后再考虑放开"扫描工具报出的具体漏洞"）；
- **大范围重构、架构调整**，没法拆成单独可验证、可合并的一小块的；
- **主观的设计或视觉调整**，比如"让界面更好看"；
- **依赖或框架的大版本升级。**

**依据：**
- 安全类：Copilot 的最佳实践建议涉及安全、个人身份信息、认证的任务由人自己做；OpenHands 把安全审计、高度敏感的代码列为不适合。实证研究也显示，agent 提的安全相关 PR 合并率约 61.5%，非安全的约 77.3%，评审时间中位数 3.92 小时对 0.11 小时，评审的人明显更不放心。
- 重构和架构：Copilot 建议别交；Devin 和 OpenHands 都说必须拆成能单独验证和合并的小块。
- 主观任务：Copilot、Devin、OpenHands、Jules 四家举的反例几乎一样："让它更好看""把问题都修了""看看哪里坏了"。
- 大版本升级：OpenHands 把框架和大版本依赖升级列为需要拆分的复杂任务。

## 四、判断不通过时怎么做（建议，待拍板）

1. **不改代码，不开 PR。**
2. 在 issue 里留一条评论，写明：没通过哪一条规则、具体缺什么信息、需要回答的问题，并告诉对方"补充正文后重新打一次 `agent-fix`"。评论末尾注明"本条由 AI 生成"。
3. 撤掉 `agent-fix` 标签，本次处理结束。

**依据：** 和 RepoAegis 最像的是 OpenHands 的 issue 转 PR 工具。它的提示词写明 issue 太模糊时"什么都不改，说清楚缺什么"；留言由外层程序根据事实决定，不让 agent 自己发。多数官方 agent 没有"判断不做"这条路，结果是含糊的 issue 也会得到一个靠猜的 PR，这正是我们要避免的。

**还没定的：** 五条规则是在 agent 开工前单独做一步检查（只调用一次模型，读标题和正文，按固定格式给出结论），还是写进 agent 的提示词、让它在干活过程中判断。前一种更省钱，也能单独测准不准；后一种能在读了代码之后才发现做不了的情况。

## 五、对 issue 内容的处理规则（已定方向，细节待实现）

- **只用打标签那一刻的标题和正文**，不读评论，打标签之后对正文的修改也不读。要补充信息，请改好正文后重新打标签。（防止有人在维护者看过、打了标签之后偷改正文、塞入指令。）
- **交给 agent 之前清洗**：去掉 HTML 注释、不可见字符、图片的替代文字、链接的悬停标题等看不见的内容。（计划照搬 claude-code-action 的清洗规则。）
- **issue 描述的是任务，但不授权任务以外的事**：要求泄露密钥、访问无关地址、改别的仓库等，agent 跳过这些要求，其余照做，并在汇报里说明跳过了什么。
- **agent 手里不拿 GitHub 令牌**：推分支、开 PR、留言、撤标签都由外层程序做。

## 六、给使用者：怎么写一个会被处理的 issue

按上面的规则，一个容易通过的 issue 最好包含：

- 要解决什么问题，或者要做成什么样；
- bug 的话，复现步骤和实际现象，报错信息贴文字，不要只贴截图；
- 做到什么程度算完成，最好能写成"某个测试应该通过"或"某个命令应该输出什么"；
- 知道的话，写上涉及的文件或函数；
- 不能动的地方和要遵守的写法。

适合交给 agent 的典型例子：有报错或复现步骤的 bug、给已有代码补测试、改文档和注释、小范围的配置和样式修改、照着已有写法做的改动。不适合的：含糊或主观的需求、大范围重构、安全和认证相关的改动、关键信息只在截图里的、提问和讨论。

## 七、待实测和待拍板

- 第四节判断不通过时的回应方式，等拍板。规则 2 的"≤ 1 分"、规则 4 的"1 小时""100 行""60 分钟"、规则 5 的"安全类一律不做"已于 2026-10-24 定为先按这些数值执行，实测后再调整。
- 开工前单独检查，还是在干活中判断。
- 在真实开源仓库里抓一批 issue，让检查步骤逐条判断，和人的判断对照，看规则和阈值是否合理、agent 的估计准不准。
