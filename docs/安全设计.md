# 安全设计：在 Actions 里跑一个能执行命令的 agent

> 状态（2026-10-24）：整体结构和必做项已定；DeepSeek 密钥用 AWF 保管，先实测；发布用什么身份留到讨论交付环节时再定。本文的事实来自 2026-10-24 调研子 agent 读过的源码和官方文档（报告原文 `research-security.md`、`research-triage-content.md` 在会话笔记目录），本文没有逐条再复核。

## 问题是怎么来的

RepoAegis 的 agent 要在运行机上读代码、跑测试、改代码，所以它必须能执行任意命令。而它读的 issue 可能是任何人写的。只要 issue 里藏一段话骗过模型（这叫**提示词注入**），agent 就会拿着它能碰到的一切去做坏事：读出模型密钥、拿 GitHub 令牌改别的东西、把内容发到外面。

公开事故说明这不是假设。2026 年 2 月的 Clinejection：Cline 仓库用 claude-code-action 给 issue 分类，允许任何人触发，agent 能执行命令，攻击者在 issue 标题里写指令，最后通过污染 Actions 缓存偷到了 npm 发布令牌，被篡改的 `cline@2.3.0` 真的发布了出去。2025 年 12 月的 PromptPwnd：Gemini CLI 的分诊步骤里模型拿着能改 issue 的令牌，被骗着把密钥贴进了公开的 issue。

各家都承认，清洗输入、在提示词里写"别听坏话"都挡不住注入（claude-code-action `docs/security.md` 第 78 行附近）。真正兜底的办法只有一个：**就算 agent 被骗了，它手里也没有能造成损害的东西。** 下面的设计都围绕这一点。

## 整体结构：一次运行拆成四个作业

GitHub Actions 的一个**作业**（job）跑在一台全新的机器上，作业之间不共享内存和文件，只能传文件。利用这一点，把"能执行命令的 agent"和"有写权限的令牌"放到不同的机器上（学 gh-aw 的"agent 作业只读、写操作由另一个作业做"，以及 codex-action 的"agent 跑过的机器不可信，后续工作换新作业"）：

1. **检查作业**：再查一次打标签人的角色（只认 Write、Maintain、Admin）；确认 issue 开着、没有图片、没有已关联的 PR 或提交；从事件里取出打标签那一刻的标题和正文，清洗后交给检查模型判断能不能做（见 [什么样的 issue 适合交给 agent](什么样的issue适合交给agent.md)）。
2. **agent 作业**：agent 在沙箱里改代码，只交出一份补丁和一份固定格式的汇报，不做任何 GitHub 写操作。
3. **产出检查作业**：不拿任何密钥，检查补丁和汇报，不合规就不发布。
4. **发布作业**：只拿必要的写权限，应用补丁、推新分支、开草稿 PR。

最后还有一个不管前面成功、失败还是被取消都会执行的**收尾作业**：按事实在 issue 里留言、撤掉标签（见 README"要做什么"）。另有一个定时运行的小工作流做兜底。

## 必做项

**标题和正文不直接写进脚本。** 工作流里写 `${{ github.event.issue.title }}` 会在脚本生成前被原样替换，标题里带 `"; 命令` 就能执行任意命令。一律先放进 `env:`，再在程序里读。（GitHub 官方文档 `content/actions/concepts/security/script-injections.md`；codex-action `docs/security.md` 第 48–60 行。）这挡的是"脚本注入"，和提示词注入是两回事。

**再查打标签人的角色。** Triage 角色也能打标签，所以不能把"能打标签"当作"有写权限"。（claude-code-action `src/github/validation/permissions.ts` 做的是同一件事。）

**每个作业只给最小权限。** 工作流顶层写 `permissions: {}`，每个作业单独声明自己需要的那几项。（GitHub 官方 `secure-use.md`；gh-aw `architecture.mdx`。）

**清洗交给模型的文字。** 照搬 claude-code-action 的 `src/github/utils/sanitizer.ts`（MIT 许可证，保留版权声明）：去掉 HTML 注释、不可见字符、图片替代文字、链接悬停标题、隐藏属性，还原 HTML 实体，抹掉令牌。Copilot 文档也写明会先过滤隐藏字符。

**agent 手里没有 GitHub 令牌。** agent 作业不放 `GITHUB_TOKEN`；克隆代码时设 `persist-credentials: false`，否则 `actions/checkout` 会把令牌留在本地 git 配置里，agent 能读到。

**agent 没有 sudo。** GitHub 免费运行机默认有不需要密码的 sudo，有了它就能读同一台机器上其他进程的内存，密钥藏在哪都没用（codex-action `docs/security.md` 第 68–72 行）。

**DeepSeek 密钥走密钥代理，agent 只拿到一个占位值。** 见下一节。

**发布前检查产出。** 补丁不许改 `.github/` 目录、依赖清单、agent 指令文件（`AGENTS.md`、`CLAUDE.md` 等），限制改动的文件数和大小；补丁和汇报里不许出现密钥格式的字符串；汇报文字清洗后再填进留言模板（学 gh-aw 的受保护文件规则和输出清洗）。如果目标仓库是公开的，PR 一开出来所有人就能看见，所以这一步必须在发布前做完，不能指望人审兜底。

**发布作业不运行仓库里的任何代码**，只应用补丁、推送、调接口。

**agent 作业不读写 Actions 缓存**，不和仓库里其他工作流共用缓存（Clinejection 的攻击路径）。

**第三方 Action 固定到完整的提交号**，不用会被挪动的版本标签（GitHub 官方 `secure-use.md`）。

**PR 永远是草稿，合并只能由人做。**

## DeepSeek 密钥怎么藏

agent 能执行命令，敲一句 `env` 就能看到环境变量里的密钥，所以"只在 agent 那一步给密钥"不够。codex-action 和 gh-aw 都用**密钥代理**解决：密钥只交给一个单独的小程序，agent 把请求发给这个小程序，由它加上密钥再转发给模型服务，agent 从头到尾看不到密钥。

**已定：用 gh-aw 的防火墙组件 AWF（`github/gh-aw-firewall`）。** 它有现成的 Action，免费运行机上就能跑，一次解决两件事：网络白名单（agent 只能访问名单里的网址）和密钥代理（密钥放在单独的容器里，agent 的容器里只有占位值），并且支持任何与 OpenAI 兼容的模型服务（`docs/api-proxy-sidecar.md`）。能不能完整接上 DeepSeek（包括流式输出和工具调用）还没实测；测不通，就退回照 codex-action 的做法自己搭一个小代理，网络白名单也要自己做。

不管用哪种，都要：给 RepoAegis 单独建一个 DeepSeek 密钥，不和别的项目共用，并控制账户余额（代理挡得住"读出密钥"，挡不住"借代理把余额花光"）；密钥存成仓库的 Actions 密钥，只在需要的那一步引用；不开调试日志；发现泄露立刻作废重建。

## 暂不做的

**AI 复查产出**（学 gh-aw 的威胁检测，让模型再看一遍补丁和汇报）：先不加，先把规则检查做扎实。它要多一次模型调用，而且复查的模型本身也可能被补丁里的文字骗。

## 待定

**发布用什么身份。** 用 `GITHUB_TOKEN`：天然改不了工作流文件（它可设置的权限里根本没有 `workflows` 这一项），作业结束就失效；但它推的代码不会触发仓库的 CI，还要在仓库设置里打开"允许 GitHub Actions 创建拉取请求"。用 GitHub App：CI 能正常跑；但要管理 App 的私钥。留到讨论交付环节时再定。

## 待实测（在 `ETOLucy/repoaegis-sandbox` 里）

- AWF 能否接上 DeepSeek 的 chat completions，包括流式输出和工具调用。
- 在 AWF 的容器里执行 `env`、读 `/proc/*/environ`、`sudo -n true`，确认看不到真密钥、没有 sudo。
- AWF 在免费运行机上的启动耗时，以及装依赖需要放行哪些网址。
- 用 `GITHUB_TOKEN` 推送一个改了 `.github/workflows/` 下文件的分支，看是否被拒、报什么错。
- 用 `GITHUB_TOKEN` 查打标签人的角色，需要声明哪项权限。
- 个人仓库里有没有 Triage 角色。
- DeepSeek 后台能不能给单个密钥设额度。
