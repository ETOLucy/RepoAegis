# 安全设计：在 Actions 里跑一个能执行命令的 agent

> 这一篇管：agent 能执行任意命令、读的 issue 可能是任何人写的，怎样让它即使被骗也造不成损害。整体结构和必做项已定；模型密钥用 AWF 保管；发布用什么身份留到讨论交付环节时再定。依据见 [调研/Actions里运行agent的安全做法](调研/Actions里运行agent的安全做法.md)、[调研/分诊工作流如何处理问题内容](调研/分诊工作流如何处理问题内容.md)、[调研/AWF沙箱实测](调研/AWF沙箱实测.md)、[调研/产出检查规则](调研/产出检查规则.md)。

## 问题是怎么来的

RepoAegis 的 agent 要在运行机上读代码、跑测试、改代码，所以它必须能执行任意命令。而它读的 issue 可能是任何人写的。只要 issue 里藏一段话骗过模型（这叫**提示词注入**），agent 就会拿着它能碰到的一切去做坏事：读出模型密钥、拿 GitHub 令牌改别的东西、把内容发到外面。

公开事故说明这不是假设。2026 年 2 月的 Clinejection：Cline 仓库用 claude-code-action 给 issue 分类，允许任何人触发，agent 能执行命令，攻击者在 issue 标题里写指令，最后通过污染 Actions 缓存偷到了 npm 发布令牌，被篡改的 `cline@2.3.0` 真的发布了出去。2025 年 12 月的 PromptPwnd：Gemini CLI 的分诊步骤里模型拿着能改 issue 的令牌，被骗着把密钥贴进了公开的 issue。

各家都承认，清洗输入、在提示词里写"别听坏话"都挡不住注入（claude-code-action `docs/security.md` 第 78 行附近）。真正兜底的办法只有一个：**就算 agent 被骗了，它手里也没有能造成损害的东西。** 下面的设计都围绕这一点。

## 整体结构：一次运行拆成四个作业

GitHub Actions 的一个**作业**（job）跑在一台全新的机器上，作业之间不共享内存和文件，只能传文件。利用这一点，把"能执行命令的 agent"和"有写权限的令牌"放到不同的机器上（学 gh-aw 的"agent 作业只读、写操作由另一个作业做"，以及 codex-action 的"agent 跑过的机器不可信，后续工作换新作业"）：

1. **检查作业**：查打标签人的角色，按需停掉这个 issue 正在跑的运行（[触发与叫停](触发与叫停.md)）；从修改记录倒推打标签那一刻的版本，查修改人、图片和附件，清洗（[agent 读到的内容](agent读到的内容.md)）；交给检查模型判断能不能做（[接收哪些 issue](接收哪些issue.md)）。
2. **agent 作业**：agent 在沙箱里改代码，最后交出一份补丁（可以为空）和一份固定格式的汇报；不做任何 GitHub 写操作。运行中想读本仓库别的 issue，托沙箱外的读 issue 服务读（见下文"agent 手里没有 GitHub 令牌"）。
3. **产出检查作业**：不拿任何密钥，检查补丁和汇报，不合规就不发布。
4. **发布作业**：只拿必要的写权限，应用补丁、推新分支、开草稿 PR。

最后还有一个不管前面成功、失败还是被取消都会执行的**收尾作业**：按事实在 issue 里留言、撤掉标签、上传 Langfuse（见 [暂停存档与监控](暂停存档与监控.md)"收尾和留言"）。它不在 AWF 容器里，也不运行仓库里的代码。另有一个定时运行的小工作流做兜底。现在工作流里已有检查作业、agent 作业和收尾作业；产出检查作业和发布作业还没写，收尾作业的运行条件也还要改（[暂停存档与监控](暂停存档与监控.md) 第八节）。

## 必做项

**标题和正文不直接写进脚本。** 工作流里写 `${{ github.event.issue.title }}` 会在脚本生成前被原样替换，标题里带 `"; 命令` 就能执行任意命令。一律先放进 `env:`，再在程序里读。（GitHub 官方文档 `content/actions/concepts/security/script-injections.md`；codex-action `docs/security.md` 第 48–60 行。）这挡的是"脚本注入"，和提示词注入是两回事。

**再查打标签人的角色。** Triage 角色也能打标签，所以不能把"能打标签"当作"有写权限"。（claude-code-action `src/github/validation/permissions.ts` 做的是同一件事。）

**每个作业只给最小权限。** 工作流顶层写 `permissions: {}`，每个作业单独声明自己需要的那几项。（GitHub 官方 `secure-use.md`；gh-aw `architecture.mdx`。）检查作业有 `actions: write`，用来列出运行和产物、停掉该停的运行；agent 作业绝不能有这项权限。调用模板 [examples/agent-fix.yml](../examples/agent-fix.yml) 的顶层写了 `permissions: {}`，RepoAegis 自己的工作流顶层还没写，要不要补，待定。

**清洗交给模型的文字。** 以 GitHub 官方 MCP 服务器的做法为准，再加删 HTML 注释（2026-10-27 定），规则见 [agent 读到的内容](agent读到的内容.md) 第三节。清洗挡不住直接写出来的注入（PromptPwnd、Clinejection 注入的都是肉眼可见的文字），兜底仍靠本文的作业拆分和权限。

**不设命令黑白名单。** agent 的 bash 想执行什么都可以，安全靠沙箱和产出检查（2026-10-26 定）。没有一家官方项目用命令名单做安全边界，Codex 用操作系统级沙箱，gh-aw 用容器加防火墙（依据见 [调研/agent工具清单](调研/agent工具清单.md)）。agent 命令能看到的环境变量只有白名单里的几类，见 [agent 怎么干活](agent怎么干活.md)"bash"。

**agent 手里没有 GitHub 令牌。** 克隆代码时设 `persist-credentials: false`，否则 `actions/checkout` 会把令牌留在本地 git 配置里，agent 能读到。agent 作业的令牌只有读权限（`contents`、`issues`、`pull-requests`），只交给 AWF 容器外运行机上的读 issue 服务，agent 托它按编号读本仓库的 issue，服务替它把关、清洗（2026-11-01 定，学 gh-aw 把令牌放进 agent 容器外的网关）。2026-11-02 实测：容器里经 AWF 代理只能访问运行机上放行的那一个端口，直接连 GitHub 连不上，也找不到这个令牌（[调研/agent运行中读issue](调研/agent运行中读issue.md) 第五之二节）。服务只认 `/issue/编号` 这一种请求，其余一律回"找不到"；它对容器里的任何命令开放，所以把关规则全在服务里执行（[agent 读到的内容](agent读到的内容.md) 第五节）。

**agent 没有 sudo。** GitHub 免费运行机默认有不需要密码的 sudo，有了它就能读同一台机器上其他进程的内存，密钥藏在哪都没用（codex-action `docs/security.md` 第 68–72 行）。

**模型密钥走密钥代理，agent 只拿到一个占位值。** 见下一节。

**发布前检查产出。** 补丁不许碰受保护的文件（`.github/` 目录、agent 指令文件 `AGENTS.md`、`CLAUDE.md` 等），限制改动的文件数和大小；补丁和汇报里不许出现密钥格式的字符串；汇报文字清洗后再填进留言模板（学 gh-aw 的受保护文件规则和输出清洗）。每条规则的结果是"拦下"（不开 PR，在 issue 里留言说明）或"标出"（照开草稿 PR，在描述顶部列出）。依赖清单是拦下还是只在 PR 里标出、其余细则，见下文"待定"。

碰了就拦下的文件（2026-11-03 定）：`.github/` 以及仓库根目录下所有以点开头的目录（`.husky/`、`.githooks/`、`.claude/` 等）里的文件；任意深度的 `AGENTS.md`、`CLAUDE.md`、`GEMINI.md`；任意深度的 `CODEOWNERS`。匹配照 gh-aw：文件名精确比较、区分大小写，目录按路径前缀，改名时新旧路径都查，补丁头解析不了就整个拦下。`README.md` 等文档不算受保护（gh-aw 算），因为修文档是常见的 issue，PR 又都要人审。根目录的单个点文件（`.env`、`.gitattributes`）不在这条里。如果目标仓库是公开的，PR 一开出来所有人就能看见，所以这一步必须在发布前做完，不能指望人审兜底。规则还没写成代码；submit 已经留好调用它的位置。

**发布作业不运行仓库里的任何代码**，只应用补丁、推送、调接口。

**agent 作业不读写 Actions 缓存**，不和仓库里其他工作流共用缓存（Clinejection 的攻击路径）。

**第三方 Action 固定到完整的提交号**，不用会被挪动的版本标签（GitHub 官方 `secure-use.md`）。

**PR 永远是草稿，合并只能由人做。**

## 模型密钥怎么藏

agent 能执行命令，敲一句 `env` 就能看到环境变量里的密钥，所以"只在 agent 那一步给密钥"不够。codex-action 和 gh-aw 都用**密钥代理**解决：密钥只交给一个单独的小程序，agent 把请求发给这个小程序，由它加上密钥再转发给模型服务，agent 从头到尾看不到密钥。

**已定：用 gh-aw 的防火墙组件 AWF（`github/gh-aw-firewall`）。** 它有现成的 Action，免费运行机上就能跑，一次解决两件事：网络白名单（agent 只能访问名单里的网址）和密钥代理（密钥放在单独的容器里，agent 的容器里只有占位值），并且支持任何与 OpenAI 兼容的模型服务（`docs/api-proxy-sidecar.md`）。版本固定在 v0.29.0，装失败时重装一次（官方安装步骤约 4% 的概率误判失败，见 [调研/AWF沙箱实测](调研/AWF沙箱实测.md)）。能不能完整接上 DeepSeek（包括流式输出和工具调用）还没在 Actions 上实测；测不通，就退回照 codex-action 的做法自己搭一个小代理，网络白名单也要自己做。

**AWF 包住整个 agent 程序（2026-10-30 定）。** agent 作业里只启动一次 AWF，写成 `sudo -E "$(command -v awf)" ... -- python -m <agent 入口>`：我们的主程序（调模型、记日志）和 agent 执行的每条命令都在同一个容器里，命令是主程序开的子进程。另一种做法是主程序留在运行机上、每条命令单独启动一次 AWF，它能把主程序和 agent 真正隔开，但每条命令都要多付一次 AWF 的启动时间，没有采用（单纯启动一次要多久没有单独测过，2026-10-28 实测的 27 秒里包括装包）。这样定的后果：容器里主程序和命令是同一个用户，换用户做不到（实测见 [AWF沙箱实测](调研/AWF沙箱实测.md)），agent 能读到主程序启动时的环境，所以主程序里不能放任何真密钥，模型的 key 只能交给密钥代理；Langfuse 的 key 只给不在容器里的收尾作业（2026-10-30 定，见 [暂停存档与监控](暂停存档与监控.md)"监控"）；主程序自己要访问的网址也得放进网络白名单，agent 同样能访问。

不管用哪种，都要：给 RepoAegis 单独建一个模型密钥，不和别的项目共用，并控制账户余额（代理挡得住"读出密钥"，挡不住"借代理把余额花光"）；密钥存成仓库的 Actions 密钥，只在需要的那一步引用；不开调试日志；发现泄露立刻作废重建。

## 本仓库提交前扫描密钥（2026-10-30 定）

开发时本机 `.env` 里有 DeepSeek、Langfuse 的密钥，RepoAegis 又是公开仓库，所以提交前用 gitleaks 自动拦：仓库根目录的 `.gitleaks.toml` 沿用 gitleaks 自带规则，另加 DeepSeek 密钥、Langfuse 密钥两条内容规则，以及 `.env` 类文件、私钥和证书容器文件两条只看文件名的规则；本机 `.git/hooks/` 的提交前和写提交说明两个钩子都扫，找不到 gitleaks 或规则文件也拒绝提交。依据和已知漏洞见 [调研/提交前敏感内容扫描](调研/提交前敏感内容扫描.md)。

## 暂不做的

**AI 复查产出**（学 gh-aw 的威胁检测，让模型再看一遍补丁和汇报）：先不加，先把规则检查做扎实。它要多一次模型调用，而且复查的模型本身也可能被补丁里的文字骗。

## 待定

**产出检查的具体规则。** 哪些文件拦下、哪些只在 PR 里标出，补丁大小上限，像密钥的字符串怎么认，汇报文字怎么清洗，建议写在 [调研/产出检查规则](调研/产出检查规则.md) 第五节，第 1 条（拦下哪些文件）2026-11-03 已定，见上文"发布前检查产出"，接着讨论第 2 条。其中"新增被 `.gitignore` 忽略的文件就拦下"是你 2026-10-30 提出的。助手还提过把编辑器拒改的范围扩大到整份受保护名单、名单只在代码里写一份，你没回。

**存档和轨迹里的密钥。** 运行产物里有完整的命令输出，公开仓库里谁登录都能下载；万一输出里混进密钥，就会公开。要在写轨迹时遮掉，规则还没定（[暂停存档与监控](暂停存档与监控.md) 第八节）。

**模型是否一直用 DeepSeek。** 现在暂定 DeepSeek（[agent 怎么干活](agent怎么干活.md) 第一节）。本文按"模型密钥"写，换模型时密钥代理的做法不变。

**发布用什么身份。** 用 `GITHUB_TOKEN`：天然改不了工作流文件（它可设置的权限里根本没有 `workflows` 这一项），作业结束就失效；但它推的代码不会触发仓库的 CI，还要在仓库设置里打开"允许 GitHub Actions 创建拉取请求"。用 GitHub App：CI 能正常跑；但要管理 App 的私钥。留到讨论交付环节时再定。

## 待实测（在 `ETOLucy/repoaegis-sandbox` 里）

- AWF 能否接上 DeepSeek 的 chat completions，包括流式输出和工具调用（AWF 启动时会请求一次 `/v1/models`，DeepSeek 支不支持也要看）。
- 装用户项目的依赖需要放行哪些网址。
- 个人仓库里有没有 Triage 角色。
- DeepSeek 后台能不能给单个密钥设额度。

已测：

- 用 `GITHUB_TOKEN` 查打标签人的角色，只声明 `issues: read` 就够，查协作者权限用的是令牌总会带着的 `metadata: read`（2026-10-25）。
- AWF 容器里：命令以普通用户运行，特殊权限全部拿掉、不能再提权，`sudo` 用不了；`/proc` 只看得到同一用户的进程；运行机上的假密钥在容器的环境和所有 `/proc/*/environ` 里都找不到。安装加预拉镜像约 33 秒，镜像就绪后启动到结束约 27 秒（含装包）。换一个只能写仓库目录的用户做不到，主程序和命令是同一个用户（2026-10-28、10-30，[调研/AWF沙箱实测](调研/AWF沙箱实测.md)）。
- 用 `GITHUB_TOKEN` 推送改了 `.github/workflows/` 下文件的分支：整次推送被拒，报 "refusing to allow a GitHub App to create or update workflow ... without `workflows` permission"，同一次推送里的普通提交也没推上去（2026-10-30，测试仓库运行 41053737983）。
